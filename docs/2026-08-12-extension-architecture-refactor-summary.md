# 扩展架构重构阶段总结

> 类别：历史决策  
> 状态：本轮主体已实施，遗留事项见本文待办  
> 日期：2026-08-12

## 本轮目标

本轮围绕动态配置、采集插件、能力与工具关系、流水线失败治理和管理界面完成了一次系统性重构。核心边界统一为：**项目可以调用插件，插件不得反向依赖项目 `lib/` 实现**。

## 已完成

### 1. 动态配置与旧配置迁移

- 将模型、GitHub、图片上传、文档检索等能力所需配置迁入统一配置资源。
- 移除运行时对 `.env` 的业务配置依赖和固定工作台配置表单。
- 补充旧配置扫描、迁移脚本、迁移覆盖率和 Legacy fallback 状态诊断。
- 本机配置页与技能/工具页按“能力配置”和“工具运行”重新组织。

### 2. 能力目录与调用链治理

- 新增统一能力目录 `config/capabilities.json`，提供稳定的能力 ID、中文名称与说明。
- 能力图按“能力目录 → 消费者声明 → 工具 Manifest → 路由策略”聚合。
- 一个能力允许由多个工具实现，并支持优先级、启停、依赖检查、兜底路径和停用影响分析。
- 对编码触发与技能触发建立统一审计视图，避免工具停用后静默破坏功能或技能。

### 3. 插件物理隔离与 Manifest 统一

- 将 RSSHub、GitHub、Reddit 等采集器的实现物理迁入 `plugins/collectors/`。
- 将原先散落在 `lib/integrations/`、`lib/collectors/` 的具体工具实现迁入插件目录。
- 为采集插件与信息工具统一 Manifest 基础结构，采集器只保留领域扩展字段。
- 增加插件分层门禁，保证插件不直接引用项目 `lib/`。

### 4. 采集与批次流水线

- 采集失败按“当前批次 + 采集源”记录，支持重试和跳过。
- 批次按采集、打标、事件卡、研判等环节顺序执行；当前环节存在待处理失败时阻断后续环节。
- 失败记录跳过后会重新计算下一环节可用状态，避免问题数据永久阻塞批次。
- 修复 GitHub 内置采集插件加载与采集源配置问题。
- Reddit 采集支持按需自动启动和关闭浏览器，同时保留手动诊断脚本。

### 5. 页面与交互整理

- 能力配置页聚合能力、消费者、候选工具和兜底关系。
- 工具运行页统一展示信息工具和采集工具，并以工具名称和工具 ID 为主信息。
- 统一依赖检查、配置、启停、优先级、影响范围和执行历史的交互方式。
- 修复配置深链、执行历史位置、标签样式、按钮组和无效遗留区块等问题。

## 待办

### P1：让采集工具“执行历史”读取真实采集运行

当前采集工具卡片的“执行历史”读取 `collector-plugin-events.jsonl`。该文件只记录安装、启用、停用、授权和卸载等管理事件；内置采集器通常不会产生这些事件，因此页面默认为空，并且仅正常执行采集时会一直为空。

后续应改为：

- 以工具/插件 ID 查询 `subscription_runs`，展示批次、采集源、状态、数据量、耗时、错误、重试和兜底信息。
- 与 `pipeline_failures` 关联，允许从失败运行定位到可重试或可跳过的失败记录。
- 将安装、启停、授权等管理事件保留在扩展管理审计中，不再冒充工具执行历史。
- 信息工具和采集工具共用执行历史的视觉与交互契约，但允许各自展示领域字段。

### P2：继续收敛共享基础设施

- 复查 Manifest 加载、配置解析和执行审计中仍可共享的基础模块。
- 保持共享模块只提供协议和基础设施，不把具体插件实现重新放回项目层。
- 将插件分层、Manifest 契约、能力目录完整性和流水线门禁持续纳入测试。
