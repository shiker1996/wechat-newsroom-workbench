# 账号双分发内容策略与写作技能对齐计划

## 实施进度

- Phase 0：方案与文档索引已落地。
- Phase 1：本地私有账号配置已完成首轮校准；历史候选离线复排与真实发布观察并入 Phase 5 持续执行。
- Phase 2：双分发字段已进入默认值、示例配置、格式化输出和配置文档。
- Phase 3：脑暴、编辑会、候选持久化和选题报告已贯通分发池与读者利益；通知池缺少明确读者利益或匹配不足时确定性降为实验池。
- Phase 4：标题、热点快评、深度分析和成稿编排契约已对齐，锁定简报、作者素材、大纲与标题文件均携带分发字段。
- Phase 5：尚不调整总分权重；至少观察两个完整内容周期后再复盘。

验证记录：6 个相关技能均通过 `skill-creator` 结构校验；项目全量测试 763 项全部通过。真实 `account-context.json` 继续由 Git 忽略，不进入仓库。

## 1. 背景与结论

近期运营复盘显示，账号已经形成两种不同的内容分发机制：

- 工具、开源项目和具体效率方案更适合进入推荐流，通过场景痛点、可信证据和可直接获得的结果拉新，并持续产生搜索长尾。
- 职场情绪、平台事件和技术商业变化只有与开发者的工作、收入、岗位、成本或选择建立直接关系时，才适合使用通知额度维护存量读者。
- 抽象的大厂战略、融资、参数规模和行业综述即使事实完整，如果没有明确的读者利益点，也不应因为分类偏好而自动获得高优先级。

现有配置仍以“热点深度解读”为主，选题评分偏好大厂战略，写作链也只区分搜索型、分享型和观点型，没有显式区分通知池与推荐池。结果是运营策略已经变化，但账号上下文、选题评分、标题包装和成稿技能仍按旧方向运行。

本次调整采用“配置优先、技能承接、少量代码固化”的原则。语义规则主要进入本地账号配置与技能；代码只负责让新字段可被格式化、传递、验证和测试。

## 2. 目标

1. 把账号定位从单一的科技热点解读，调整为“实用工具增长 + 切身影响通知”的双分发模型。
2. 让选题阶段在锁题前明确内容进入通知池还是推荐池，以及读者为什么现在要读。
3. 让标题和正文按分发目标采用不同包装，不再用同一套热点标题处理全部内容。
4. 保留事实核验、作者立场、风险门禁和现有内容角色，不让增长目标覆盖内容质量。
5. 通过配置覆盖真实账号偏好，避免把私有运营数据或账号画像提交到仓库。

## 3. 非目标

- 不自动决定是否群发，不连接公众号发布动作。
- 不把所有工具文视为高质量内容；工具文仍须通过事实、体验、限制和标题兑现门禁。
- 不把职场情绪等同于制造焦虑或标题党。
- 不因短期样本彻底删除大厂、行业或技术深解内容。
- 不扩张 `wechat-mp-gossip-chill` 的职责；严肃职场议题继续由热点快评或深度分析技能承担。

## 4. 双分发内容模型

### 4.1 推荐池

主要任务：拉新、分享、收藏和搜索长尾。

优先内容：

- 开源项目、AI 工具、开发工具和工程效率方案。
- 能解决明确工作场景的教程、清单、对比和实践总结。
- 有可信背书的技术产品，例如官方主体、可核验 Star 数、性能数据或真实体验。

包装要求：

- 标题优先使用“场景痛点 + 可信证据 + 可获得结果”。
- 首屏尽快说明解决什么问题、适合谁、得到什么。
- 自然覆盖稳定搜索词，不使用只有圈内人才认识的项目名作为唯一入口。
- 正文提供可保存的实用增量，并明确适用边界。

### 4.2 通知池

主要任务：维护存量读者、建立认同和表达账号判断。

优先内容：

- 开发者职场情绪、岗位变化、工作方式和职业选择。
- 平台或大厂事件对开发者收入、成本、技能、岗位和决策的直接影响。
- 有广泛个人利益、明确冲突或重要判断的科技事件。

通知资格至少满足以下两项：

1. 会影响读者的钱、工作、岗位、效率、成本或选择。
2. 标题能直接说明“为什么与开发者有关”。
3. 除了新闻复述，文章有明确判断、观察框架或行动建议。

包装要求：

- 标题优先使用“事件 + 切身影响”或“具体问题 + 答案方向”。
- 前 200 字回答谁受影响、影响什么、作者的核心判断是什么。
- 不把宏观公司叙事当作读者价值，必须完成对个人处境的转换。

### 4.3 实验内容

保留少量实验比例，用于验证新形式、跨圈层事件和原创认知。实验内容必须明确假设和观察指标，不因一次失败立即改变账号定位。

## 5. 账号上下文调整

### 5.1 本地真实配置

真实账号配置继续保存在被 Git 忽略的 `account-context.json`。建议调整：

- 重排 `contentPillars`，把开源工具与工程实践放到首位。
- 在 `readerProfile` 中补充开发者对工作效率、工具成本、岗位变化和职业选择的需求。
- 将 `contentRatio` 调整为工具与工程实践约 60%、开发者职场与切身利益约 20%、平台事件影响约 15%、技术认知与原创长文约 5%。该比例是初始校准值，后续按数据滚动调整。
- 在 `followReason` 中同时表达“获得可用工具”和“理解行业变化对自己的影响”。
- 在 `voiceGuardrails` 中增加：平台新闻必须完成读者利益转换；不得用公司主体或宏观规模替代实际影响。
- 调整 `scoring.categoryPreference`、`pBase` 和 `hBase`，提高 `github_tool`、`ai_tool_test`、`career_anxiety` 和 `worker_social`，降低纯融资与无切身影响的大厂新闻。
- 暂不调整总分权重，避免同时修改过多变量导致无法归因。

### 5.2 新增结构化字段

为避免把分发策略塞进自由文本，新增可选字段：

```json
{
  "distributionStrategy": {
    "recommendation": {
      "purpose": "拉新、分享、收藏、搜索",
      "preferredTopics": ["工具", "开源项目", "工程实践", "效率方案"],
      "titleRule": "场景痛点 + 可信证据 + 可获得结果"
    },
    "notification": {
      "purpose": "维护存量读者和表达账号判断",
      "preferredTopics": ["职场情绪", "平台事件", "开发者切身利益"],
      "titleRule": "事件 + 对开发者的直接影响"
    },
    "experiment": {
      "purpose": "验证新栏目、新角度和不确定需求",
      "preferredTopics": ["新技术认知", "弱相关热点的新切口"],
      "titleRule": "明确待验证的问题，不伪装成已确认需求"
    }
  },
  "notificationPolicy": {
    "minimumMatchedCriteria": 2,
    "readerStakes": ["工作", "收入", "岗位", "效率", "成本", "选择"],
    "criteria": [
      "影响读者的工作或选择",
      "标题能说明为什么与读者有关",
      "除新闻复述外有明确判断或行动增量"
    ]
  }
}
```

这些字段是内容规划约束，不代表系统获得自动群发权限。

## 6. 选题与成稿契约调整

### 6.1 `hotspot-brainstorm`

在 `packaging` 中新增：

- `distributionLane`：`推荐池|通知池|实验池`
- `readerStake`：本题影响读者的具体利益；没有则为空字符串
- `notificationFit`：0–5
- `notificationReason`：满足了哪些通知资格

要求推荐池题目给出可搜索问题或可保存模块；通知池题目必须明确开发者切身影响。没有读者利益点的宏观事件不能仅凭主体知名度获得高 `audienceRelevance`。

### 6.2 `editorial-room`

锁题前补充以下门禁：

- 通知池：确认“这件事具体改变开发者什么”，不满足时改为推荐池、实验池或放弃。
- 推荐池：确认真实场景、可信证据、可获得结果和限制。
- 编辑决策记录最终 `distributionLane`、`readerStake` 和放弃的包装方向。

一次仍只问一个最能改变文章方向的问题，不增加无效访谈轮次。

### 6.3 `title-generator`

按分发池生成候选：

- 推荐池：场景痛点、可信证据、明确收益、搜索关键词。
- 通知池：事件主体、直接影响、冲突或决策问题。
- 实验池：明确假设和新角度，不承诺未经验证的传播结果。

标题评分中的“适配”需同时检查账号受众和分发池；通知池标题没有读者利益点时不能入选。

### 6.4 `wechat-mp-tech-hotspot`

强化以下要求：

- 前 200 字说明谁受影响、影响工作中的什么，以及作者判断。
- 至少提供一项具体影响清单、成本变化、决策框架或观察信号。
- 禁止用融资额、参数规模、公司口号或产品发布本身冒充读者价值。
- 如果事实基座无法支持切身影响，缩小命题或降级为短评，不补造结论。

### 6.5 `wechat-mp-deep-dive`

补充开发者利益视角：

- 职场或平台事件需说明谁获得收益、谁承担成本，以及普通开发者能观察什么。
- 情绪只能作为入口，核心判断仍须由事实、机制和边界支撑。
- 至少输出一个可执行的核对清单、决策框架或后续信号。

### 6.6 暂不修改的技能

- `wechat-mp-gossip-chill`：继续只处理轻松职场趣闻和制度反差。
- `wechat-mp-tech-deep`：原理与可复算技术内容不依赖通知策略，先保持不变。
- `wechat-mp-personal-writing`：只有真实作者经历时使用，不替公共职场事件兜底。

## 7. 必要的代码承接

代码改动应少于配置和技能改动，只处理以下确定性职责：

1. `server/domain/account-context.mjs`
   - 格式化 `distributionStrategy` 与 `notificationPolicy`，使编辑会和成稿链能够读取。
   - 对字段缺失保持向后兼容。
2. `server/platform/llm/research-pipeline.mjs`
   - 接受并保存脑暴输出中的分发字段。
   - 在研判报告中展示分发池和读者利益点，但不自动替代最终排名。
3. 编辑决策与文章简报传递
   - 将 `distributionLane` 和 `readerStake` 从探索卡传递到锁定简报、作者素材和大纲。
4. `server/platform/llm/article-pipeline.mjs`
   - 把分发字段提供给标题与写作阶段。
   - 不改变现有 writer skill 路由的安全判断。

如果实践证明技能覆盖层已经能稳定传递所需信息，可缩减第 2–4 项代码改动；但不能只在 JSON 中新增字段而不让格式化器消费。

## 8. 分阶段实施

### Phase 0：方案冻结

范围：本文件与文档索引。

验收：

- 明确双分发模型、字段、技能边界和非目标。
- 不提交真实账号数据。

### Phase 1：本地账号配置校准

范围：本地 `account-context.json`，不进入 Git。

改动：

- 更新读者画像、内容支柱、内容配比、关注理由和风格约束。
- 覆盖分类偏好、P 基分和 H 画像基分。
- 加入双分发策略与通知资格字段。

验收：

- 格式正确，旧字段仍可读取。
- 使用同一批历史候选做离线复排，工具、开发者影响和职场相关题目获得合理提升。
- 大厂与融资题不会仅因分类获得高位。

回滚：恢复本地配置备份，不涉及代码。

### Phase 2：账号字段一等支持

范围：

- `server/domain/account-context.mjs`
- `account-context.example.json`
- `docs/configuration.md`
- 账号上下文相关测试

验收：

- 新字段能够进入 `formatAccountContext()` 输出。
- 缺失新字段时行为与当前版本一致。
- 示例配置不包含真实账号信息。

### Phase 3：选题链分发意识

范围：

- `skills/hotspot-brainstorm/SKILL.md`
- `skills/editorial-room/SKILL.md`
- 必要的选题契约、报告和测试

验收：

- 每个候选都有分发池；通知池候选有明确 `readerStake`。
- 无切身影响的宏观题不会被包装成通知池。
- 工具候选包含具体场景、证据、结果和限制。

### Phase 4：标题与成稿对齐

范围：

- `skills/title-generator/SKILL.md`
- `skills/wechat-mp-tech-hotspot/SKILL.md`
- `skills/wechat-mp-deep-dive/SKILL.md`
- `skills/wechat-mp-topic-to-article/` 的相关契约
- `server/platform/llm/article-pipeline.mjs` 的最小字段传递

验收：

- 推荐池与通知池生成明显不同的标题方向。
- 通知池正文前 200 字兑现读者影响。
- 推荐池正文提供可保存的实用增量和搜索词。
- 事实、来源、作者经历和长度门禁不退化。

### Phase 5：校准与观察

范围：离线样本、真实运营观察和参数微调。

建议观察：

- 推荐池：阅读、分享率、收藏、搜索长尾和旧文复活。
- 通知池：通知人数与阅读人数的粗略比值、留言、关注和负反馈。
- 选题链：通知池候选命中率、人工改池次数、因读者利益不足被降级的数量。

至少观察两个完整内容周期后再调整总分权重。优先微调分类、P 基分与 H 画像基分，避免同时修改多个参数。

## 9. 改动规模判断

本方案应当是“配置与技能改动多于代码改动”：

| 类型 | 主要职责 | 预计规模 |
|---|---|---|
| 本地账号配置 | 内容方向、配比、评分偏好、分发策略 | 最大 |
| 技能与契约 | 选题、编辑、标题和成稿规则 | 较大 |
| 代码 | 新字段格式化、传递、报告和兼容 | 较小 |
| 测试与文档 | 固化契约、避免回归和说明配置 | 必要 |

代码不判断某个具体事件“值不值得通知”，只执行账号配置声明的确定性底线：适配分、事实支持分、风险禁入、具体读者动作结构和批次上限。具体利益是否成立仍由技能提出、来源材料支撑并由人工编辑确认。

## 10. 风险与防护

| 风险 | 防护 |
|---|---|
| 根据短期数据过拟合 | 保留实验池，暂不改总分权重，分阶段观察 |
| 把职场情绪写成焦虑营销 | 保留事实、机制、反例和边界门禁 |
| 工具文同质化 | 要求真实场景、可信证据、限制和搜索问题 |
| 配置新增但下游不消费 | Phase 2 先完成格式化与测试，再改技能 |
| 分发池变成自动发布决策 | 明确只做内容规划，不授予群发或发布权限 |
| 私有运营信息进入仓库 | 真实值只写忽略文件，示例与测试使用虚构数据 |
