# 主题元素级可配置能力现状与扩展方案

> 类别：未来计划  
> 状态：P0–P5 已实施并通过全量回归（2026-08-02）  
> 制定日期：2026-08-02  
> 适用范围：主题中心、AI 创建主题、文章主题编译器、图文主题编译器、正式样稿与发布门禁  
> 相关文档：[主题可配置能力与编辑器扩展实施方案](./theme-config-editor-expansion-plan.md)、[主题视觉能力覆盖矩阵](./theme-style-capability-inventory.md)

## 1. 背景与结论

## 实施补充：正式渲染节奏配方（P5）

本轮 UX 实施把静态选择器无法表达的视觉差异，落到了 `theme-live-preview` 与生产编译链：

- 文章新增 `rhythm`：`airy`（舒展长文）、`standard`（标准叙事）、`dense`（高密度快讯），联动段落间距、章节间距和行高；
- 图文新增 `skeleton`：`stacked`、`editorial-split`、`terminal-rail`、`paper-offset`、`impact-band`，联动页面内容栈的结构，而不只是换颜色；
- 图文新增 `coverSupport`：`none`、`lead`、`statement`、`metric`，封面可承载导语、结论卡或指标锚点，减少下半屏空白；
- 新配方已进入 AI 白名单、编辑器目录、正式预览高亮、主题发布门禁和固定样稿覆盖矩阵；旧主题缺少新字段时仍按兼容默认值编译。

真实渲染证据见：[主题视觉审计](./audits/theme-ux.md)（截图已移除，可按文中说明重新截取）。

当前主题系统已经开放颜色、字体角色、四级字号、间距、圆角、边线、阴影和受控组件配方，并保证编辑器预览与正式生产使用同一编译链路。但这些能力主要停留在**全局语义 token**和**整体组件配方**两层，并不等于每种文字、边框和卡片都能独立配置。

现状可以概括为：

```text
全局 token
  颜色角色、正文字体、标题字体、四级字号、统一边线/圆角/阴影
      ↓
组件配方
  选择整体造型，配方内部仍包含固定字重、字号、边框和混色比例
      ↓
生产 CSS
  多个具体元素共享同一 token，少数组件仍使用固定值
```

因此：

- 用户和 AI 可以改变整体主题语言；
- 不能分别控制封面标题、眉题、数据卡、列表、提示卡等元素的字体与颜色；
- 多个元素复用同一语义颜色或字号，修改一个 token 会同时影响多个节点；
- 部分配方通过固定 CSS 建立辨识度，AI 只能选择配方，不能调整配方内部属性。

后续扩展不应开放任意 CSS。建议在全局 token 与组件配方之间新增一层**受控组件属性**：配方负责造型，组件属性负责字体角色、字重、字号档位和颜色角色。

### P0 实施结果（2026-08-02）

- 新增机器可读矩阵 `test/fixtures/theme-element-coverage.json`，覆盖封面标题、内容页标题、结尾页标题、眉题、导语、内容块标题、正文、数据卡、步骤、对比表、代码、内容框、列表和提示卡共 15 类元素。
- 每类元素均登记字体、字号、颜色、表面、边框和阴影六种当前来源，来源明确区分全局 token、组件配方、固定值与不适用。
- 37 个 P1–P3 组件字段已绑定稳定的正式样稿角色，作为 Schema、编辑器高亮与编译器 `usageMap` 的共同契约。
- 文章与图文编译器已为全部现有 token、配方、行为和效果字段补齐 `usageMap`。
- 发布门禁不再维护手写 token 清单，而是自动遍历主题定义中的全部配置叶子字段；任一 Schema 已接受字段缺少正式消费映射时，以 `UNCONSUMED` 阻止发布。
- 新增 `test/theme-element-coverage.test.mjs`，验证矩阵完整性、当前来源消费、计划字段样稿映射、两类主题全字段覆盖及未消费字段识别。

### P1 实施结果（2026-08-02）

- 新增可选 `social.components` 契约，首批覆盖 `coverTitle`、`eyebrow`、`lead`；旧主题和历史任务快照缺少该字段时继续使用配方默认效果。
- 封面标题开放字体角色、500–900 字重、紧凑/标准/展示字号档位、文字颜色角色和装饰边线颜色角色；眉题开放字体角色、字重和颜色角色；封面导语开放字号档位和颜色角色。
- 新增统一组件目录 `server/shared/themes/component-catalog.mjs`，Schema、主题详情 API、主题编辑器、AI 提示、AI 规范化和编译器共用同一白名单与默认值。
- 图文编译器在配方之后应用组件属性，只作用于 `.page-cover h1`、`.eyebrow` 和 `.page-cover .lead`；字号档位由编译器结合全局字号计算，不保存任意像素值。
- 主题中心新增“组件细节”折叠组，使用原生选择控件、正式预览字段定位、配方推荐值恢复和窄屏单列布局。
- AI 创建图文主题会显式生成三组组件属性；任意字体、颜色、尺寸或非法枚举会回退安全值，低对比颜色角色和过密展示字号会在规范化阶段修复。
- 发布门禁新增组件实际表面对比度和组件展示字号密度检查；组件属性进入 AI 主题视觉签名与相似度差异摘要。
- 新增 `test/theme-component-details.test.mjs`，覆盖契约、编译作用域、正式预览、AI 修复、对比度、密度、历史兼容、主题中心 UI 和真实 Chromium `375×667` 长标题审计。

## 2. 当前数据契约

### 2.1 全局颜色

主题编辑器开放 10 个颜色角色：

| 字段 | 当前主要消费节点 | 当前限制 |
|---|---|---|
| `background` | 宿主背景 | 不能按页面类型区分 |
| `page` | 图文画布 | 文章主题不适用 |
| `surface` | 内容栈、部分卡片 | 多类卡片共享 |
| `text` | 正文、普通标题 | 不能单独指定封面或内容页标题 |
| `muted` | 导语、说明、页脚 | 多类辅助文字共享 |
| `accent` | 品牌、二级标题、结尾页、部分边框 | 修改影响范围较大 |
| `accentSecondary` | 眉题、列表标记、部分装饰 | 不能按组件独立选择 |
| `line` | 内容框、列表、代码框、表格 | 所有边线共用 |
| `inverseText` | 代码、结尾页、反白组件 | 不能按反白组件区分 |
| `codeBackground` | 代码面板、部分深色结尾页 | 与代码以外的深色表面存在复用 |

颜色本身可调整，但元素只能使用编译器预先分配的角色。当前没有“封面标题颜色”“列表边线颜色”之类的元素级字段。

### 2.2 字体与字阶

| 字段 | 当前作用 | 当前限制 |
|---|---|---|
| `family` | 正文整体字体角色 | 只能选择无衬线、衬线、等宽 |
| `headingFamily` | `h1/h2/h3` 标题字体角色 | 所有标题共享；部分配方会覆盖 |
| `bodyPx` | 正文与列表字号 | 不覆盖所有内容块文字 |
| `h1Px` | 图文各页一级标题 | 封面、内容页、结尾页共享 |
| `h2Px` | 内容块二级标题 | 不覆盖步骤标题、数据标签等固定节点 |
| `captionPx` | 眉题、品牌、页码、页脚 | 多种职责共用一个字号 |
| `codePx` | 代码块字号（可选，缺省回退 `captionPx`） | 内置社交主题统一 11px |
| `lineHeight` | 正文与列表行高 | 部分标题和特殊组件另有固定行高 |
| `letterSpacingEm` | 整体及一级标题字间距 | 部分配方会覆盖 |

当前没有开放字重字段，也不能为具体组件单独选择字体、字号或字间距。

### 2.3 形状、边框与阴影

| 字段 | 当前作用 | 当前限制 |
|---|---|---|
| `radiusPx` | 内容栈、列表、代码等主要组件 | 数据卡等节点仍有固定圆角 |
| `borderWidthPx` | 内容栈、列表、代码等主要边线 | 提示卡、数据卡、野兽派组件存在固定宽度 |
| `shadow` | 内容栈及部分配方 | 不能为不同组件分别选择阴影 |
| `line` | 全局边线颜色 | 页面框、列表、代码、表格不能独立选色 |

### 2.4 组件配方

文章主题现有 10 组配方；图文主题现有 8 组配方：`surface`、`frame`、`decoration`、`eyebrow`、`coverTitle`、`ending`、`list`、`code`。

配方由白名单约束，能够改变组件造型，但配方内部仍有固定属性。例如：

- `coverTitle=classic` 使用克制的左侧强调线、平衡换行和较松行高，适合作为通用稳定基线；
- `coverTitle=editorial` 使用衬线字体、`700` 字重、顶部双线与底部细线，形成杂志刊头式层次；
- `coverTitle=poster` 使用 `900` 字重、紧凑行高、硬边偏移阴影与粗底线，强化海报冲击力；
- `coverTitle=highlight-block` 将标题确定性切分为多条模块化色带，交替使用强调色与深色表面，并保留完整可读文本；
- 野兽派内容框、列表和代码面板使用固定的粗边线与硬阴影；
- 柔光、扫描线、纸张等配方使用固定混色比例和装饰尺寸。

## 3. 图文生产中仍然固定或联动的元素

| 元素 | 当前字体/字号 | 当前颜色 | 当前边框/表面 | 可调结论 |
|---|---|---|---|---|
| 封面主标题 | 共用 `h1Px`；配方可能固定字体与字重 | 默认正文色；色块配方固定反白色 | 杂志下边线、色块由配方固定 | 部分可调，不能独立调 |
| 内容页主标题 | 共用 `h1Px`、`headingFamily` | 正文色 | 无独立配置 | 仅全局可调 |
| 结尾页主标题 | 共用 `h1Px`、`headingFamily` | 随结尾页反白 | 随 `ending` 配方 | 仅全局与配方可调 |
| 眉题 | 共用 `captionPx` | 次强调色或配方覆盖 | 印章、下划线由配方固定 | 部分可调 |
| 导语 | 基础样式仍为固定字号 | 弱化文字色 | 无独立配置 | 颜色联动，字号不可独立调 |
| 内容块标题 | `h2Px` | 主强调色 | 无独立配置 | 仅全局可调 |
| 正文/列表正文 | `bodyPx` | 正文色 | 列表由配方控制 | 部分可调 |
| 数据卡数字 | 生产基础样式使用固定字号 | 主强调色 | 固定或继承表面 | 颜色联动，字号不可调 |
| 数据卡标签 | 固定小字号 | 弱化文字色 | 同上 | 不能独立调 |
| 步骤标题与正文 | 部分固定字号 | 正文色/弱化色 | 序号使用强调色 | 不能独立调 |
| 对比表表头 | 固定小字号 | 反白色 | 主强调色背景 | 不能独立调 |
| 代码文字 | 共用 `captionPx`、等宽字体 | 反白色或配方覆盖 | `code` 配方 | 部分可调 |
| 内容框 | 不适用 | 全局边线色 | 全局宽度、圆角、阴影；配方可覆盖 | 不能独立调 |
| 列表卡片 | 正文共用 `bodyPx` | 正文色 | 全局边线与 `list` 配方 | 不能独立选色/粗细 |
| 提示卡 | 正文字号 | 正文色 | 左边线和混色比例部分固定 | 不能独立调 |

文章端也存在类似问题：全局 token 已进入生产编译，但标题、引用、表格、图片等组件的细节主要由整体配方决定，不能在配方内部继续调整字体角色、颜色角色与边框档位。

## 4. 扩展目标与非目标

### 4.1 目标

1. 让用户和 AI 能在安全范围内细化具体组件，而不是只能选择整体预设。
2. 保持主题定义可校验、可预览、可冻结、可迁移和可审计。
3. 继续使用语义颜色和字体角色，不允许模型输出 CSS、选择器或外部字体资源。
4. 每个新增字段必须被正式编译器、正式样稿、字段高亮和发布门禁同时消费。
5. 图文固定画布继续遵守密度预算和 `375×667` 溢出门禁。

### 4.2 非目标

- 不建设通用 CSS 编辑器；
- 不允许任意字体名称、字体文件或远程字体 URL；
- 不允许任意 HEX 直接写入组件属性，组件只能引用全局颜色角色；
- 不允许通过主题修改故事板页面数量、网格、定位和内容结构；
- 不在第一批开放每一个 DOM 节点，避免配置项失控。

## 5. 推荐数据模型

建议保留现有 `recipes`，新增可选的 `components`：

```json
{
  "social": {
    "recipes": {
      "coverTitle": "editorial",
      "eyebrow": "underline",
      "list": "outlined-card"
    },
    "components": {
      "coverTitle": {
        "fontFamily": "serif",
        "fontWeight": 600,
        "sizeScale": "display",
        "colorRole": "text",
        "borderColorRole": "accent"
      },
      "eyebrow": {
        "fontFamily": "sans",
        "fontWeight": 700,
        "colorRole": "accentSecondary"
      },
      "list": {
        "textColorRole": "text",
        "surfaceRole": "surface",
        "borderColorRole": "line",
        "borderWeight": "thin"
      }
    }
  }
}
```

推荐枚举：

| 属性 | 允许值 |
|---|---|
| `fontFamily` | `inherit`、`sans`、`serif`、`mono` |
| `fontWeight` | `500`、`600`、`700`、`800`、`900` |
| `sizeScale` | `compact`、`standard`、`display` |
| `colorRole` | `text`、`muted`、`accent`、`accentSecondary`、`inverseText` |
| `surfaceRole` | `transparent`、`surface`、`page`、`accent`、`accentSecondary`、`codeBackground` |
| `borderColorRole` | `line`、`text`、`accent`、`accentSecondary` |
| `borderWeight` | `none`、`thin`、`medium`、`heavy` |
| `radiusScale` | `none`、`subtle`、`standard`、`rounded`、`pill` |
| `shadowRole` | `none`、`theme`、`soft`、`hard`、`glow` |

`sizeScale`、`borderWeight` 和 `radiusScale` 应由编译器结合现有全局 token 计算，不能直接保存任意像素值。

## 6. 配方与组件属性的优先级

建议采用确定性优先级：

```text
安全系统默认值
  < 全局 token
  < 组件配方默认属性
  < components 中的显式白名单覆盖
  < 发布门禁的安全修复或拒绝
```

规则：

1. 配方继续负责结构化视觉语言，如杂志下边线、海报紧凑排版、列表卡片造型。
2. 组件属性只覆盖配方明确允许开放的属性。
3. 配方可以声明禁用某些覆盖。例如强调色块标题的文字色只能选择通过对比度门禁的角色。
4. 缺少 `components` 的旧主题完全沿用当前配方效果，不要求迁移。
5. AI 新建主题显式输出第一批开放组件；非法或缺失属性由规范化阶段补为配方默认值。

### P1：封面文字系统

首批只开放：

- [x] `coverTitle`：字体角色、字重、字号档位、文字颜色角色、装饰边线颜色角色；
- [x] `eyebrow`：字体角色、字重、颜色角色；
- [x] `lead`：字号档位和颜色角色。

这一阶段价值最高、影响面最小，并能直接提升 AI 创建主题的组合空间。

### P2：信息组件

实施状态：已完成。主题中心与 AI 创建均已接入下列受控属性；旧主题通过“继承配方”默认值保持原视觉。

- 数据卡：数字字体、字重、字号、颜色；标签字号、颜色。
- 步骤：标题颜色、正文颜色、序号底色。
- 对比表：表头文字与底色、正文颜色、边线颜色。
- 列表与提示框：文字、表面、边线颜色和安全边线粗细。
- 固定图文样稿由 3 页扩为 5 页，正式覆盖数据卡、列表、提示框、步骤和对比表；页数门禁从样稿定义动态读取。

开放：

- 数据卡数字与标签；
- 步骤标题、正文与序号；
- 对比表表头与单元格；
- 列表文字、表面与边线；
- 提示卡文字、表面与强调边线。

需要同步扩大固定样稿，确保每个组件至少出现一次。

### P3：内容页与结尾页文字

实施状态：已完成。

- 内容页标题与结尾页标题分别开放字体角色、字号档位和语义颜色。
- 编译器使用互斥选择器隔离封面、内容页和结尾页标题，避免全局 `h1` 规则串扰。
- AI 创建、主题编辑器、字段高亮、相似度计算、密度预算和实际表面对比度门禁均复用组件目录。
- 缺少 P3 字段的旧主题继续继承原有标题字体、字号与反白规则。

- 内容页主标题与封面标题解耦；
- 结尾页标题、导语和行动提示独立配置；
- 对深色结尾页执行独立对比度检查；
- 保持标题字段不改变页面结构和故事板语义。

### P4：文章组件细化

在图文端验证数据模型稳定后，再将同一套组件属性机制扩展到文章标题、导语、引用、列表、表格、代码和图片说明，避免文章与图文各自形成第二套契约。

实施状态：已完成。

- 新增文章组件目录，覆盖主标题、导语、引用、列表、表格、代码面板和图片说明。
- 文章与图文共用字体、字号档位、语义颜色、表面和边线枚举；Schema 与校验器使用同一目录模型。
- 文章组件属性由正式公众号渲染器输出为内联样式，并进入编译器 `usageMap`。
- 主题中心按当前目标动态展示文章或图文组件卡，AI 创建获得对应目标的精确属性目录。
- 发布门禁按文章背景、引用表面、表头表面和代码表面检查真实对比度。
- 历史文章主题缺少 `components` 时保持原有渲染；图片说明仅在显式配置后显示，避免旧文章突然出现说明文本。

## 8. 主题编辑器方案

主题中心不应一次展示所有组件。建议：

1. 保留现有“颜色系统、字体与字阶、间距节奏、形状与层次、组件配方”。
2. 新增“组件细节”折叠组，按封面、内容、信息组件、结尾分区。
3. 只有当前配方允许覆盖的字段才显示，禁用项明确解释原因。
4. 控件聚焦时通过正式预览定位具体节点，而非整页高亮。
5. 每组提供“恢复配方默认值”，不直接删除全局 token。
6. 预览同时提供短标题与长标题、浅色与深色组件状态。

## 9. AI 创建主题方案

AI 仍只生成结构化 JSON：

- 模型获得组件属性的精确枚举目录；
- 禁止输出选择器、CSS、HTML、字体名称、URL、定位和任意尺寸；
- 先选择组件配方，再选择允许覆盖的组件属性；
- 规范化阶段补齐缺失字段、移除未知字段、修正非法组合；
- AI 设计摘要应说明关键组件选择，而不是复述颜色值；
- 与内置主题比较时，把组件属性纳入视觉签名，避免只换色。

## 10. 发布门禁

扩展后的发布门禁至少包含：

1. **Schema**：字段、枚举和组件白名单合法。
2. **消费覆盖**：每个显式字段进入编译结果和 `usageMap`。
3. **对比度**：按组件实际前景色与表面色计算，而不是只检查全局颜色对。
4. **密度预算**：字号档位、行高、内边距和组件间距不能同时偏大。
5. **真实布局**：图文固定样稿使用 Chromium 检查溢出、裁切和横向越界。
6. **状态覆盖**：浅色页、深色结尾页、强调色块、长标题和高密度信息组件均需验收。
7. **历史兼容**：旧主题、已发布版本和任务快照缺少 `components` 时保持原效果。

## 11. 风险与取舍

| 风险 | 控制方式 |
|---|---|
| 配置项过多，主题编辑器难用 | 分阶段开放、按页面职责分组、默认折叠 |
| AI 产生低对比度组合 | 只引用颜色角色，并按实际组件表面执行门禁 |
| 字号组合导致固定画布溢出 | 使用字号档位、密度预算和真实浏览器审计 |
| 配方与组件覆盖互相冲突 | 明确优先级，配方声明可覆盖属性 |
| 历史主题失效 | `components` 全部可选，缺失时使用当前配方默认值 |
| 文章和图文契约分叉 | 先验证公共组件属性模型，再扩展文章端 |
| 主题看似丰富但仍然只换色 | 将组件属性纳入视觉签名和相似度判断 |

## 12. 建议决策

建议进入设计评审，但暂不一次性实现全部元素。首个实施批次应限定为 P0 + P1：先建立机器可读元素消费矩阵，再开放封面标题、眉题和可选封面导语的安全属性。

该批次能够验证三个关键问题：

1. 组件属性模型是否比继续增加整体配方更可维护；
2. AI 生成的细粒度组合是否确实提升主题差异；
3. 对比度与固定画布门禁是否足以控制新增自由度。

验证通过后再进入数据卡、步骤、列表和提示卡，避免在数据模型尚未稳定时一次开放全部节点。
