# 两周，153 次提交：我们如何把一个公众号工具做成写作专属 Agents 平台

> 文档性质：项目开发历程与阶段感悟  
> 事实快照：2026-08-02  
> 核心开发集中期：2026-07-20—2026-08-02

从代码仓库的记录看，这个项目真正密集的开发始于 7 月 20 日。

当时它还是一个“公众号写作工作台”：采集热点、筛选选题、生成文章、完成排版。目标很具体，边界也很清楚——解决日常内容生产问题。

两周后，仓库累计了 153 次提交、34 个技能目录和六百五十多个自动化测试用例。项目也不再只是一个串联了几个 AI 接口的写作工具，而是逐渐形成了一套面向写作场景的专属 Agents 平台。

这段历程最值得复盘的，并不是我们做了多少页面，而是系统的核心抽象发生了几次关键变化。

## 第一阶段：先让一篇文章真正走完生产链

项目最初解决的是一个非常现实的问题：内容生产并不等于调用一次大模型。

一篇可以发布的公众号文章，前面需要采集、去重、事件聚类和选题研判；中间需要编辑确认、事实核验和写作；后面还有审阅、自然化、SEO、配图、排版和交付。

因此，我们没有从“聊天框”开始，而是从编辑部工作流开始。

最早的版本逐步建立了每日批次、来源采集、热点全景、选题池、编辑室、文章编辑器、内容日历和模型中心。系统开始记录来源身份、执行状态、失败原因和模型调用，而不是只保存最后一篇文章。

这一步奠定了整个项目的方向：AI 不是替代编辑的黑箱，而是生产流程中一组可以检查、返工和追溯的执行者。

## 第二阶段：从“能生成”走向“有事实、有门禁”

很快我们就发现，生成速度不是最大的风险，失控才是。

模型可能截断 JSON，可能忽略来源，可能把待核信息写成事实，也可能只返回一段门禁说明，却被程序误认为文章正文。文章长度修复还曾连续触发三次，因为程序把目标字数理解得过于机械。

于是，我们开始建设事实基座和质量门禁。

热点不再只是一个标题，而是被整理为事件卡：主体、动作、时间线、已确认事实、分歧、待核内容和来源。编辑室确认的作者观点、实践材料、禁写项和未决问题，也进入后续成稿链。

文章生产则被拆成主写作、标题、自然化、审阅和 SEO 等阶段。每个阶段都有明确输入输出，失败时停止或定向返工。字数门禁也从机械追求某个精确数字，调整为“1500 字，上下浮动 200 字视为正常”。

这背后形成了一个重要经验：质量门禁必须判断“内容是否完成”，不能只判断“接口是否成功”。

HTTP 200 不代表任务成功，模型返回了一段文字也不代表文章完成。真正的成功条件应该来自业务契约。

## 第三阶段：图文生产暴露了“万能技能”的问题

文章链跑通后，我们开始扩展工具图文、事件图文和自定义图文。

最初，事实提取、故事板、页面生成、配套文案、HTML 和 PNG 交付都集中在 `xiaohongshu-article-generator` 中。短期看，这样接入最快；长期看，它逐渐变成了一个什么都负责的万能技能。

问题随之出现：不同内容类型的事实约束不同，故事结构不同，验证标准也不同，但它们被揉在同一份技能说明里，修改一处很容易影响其他入口。

我们最终把它拆开：

- 工具图文故事板负责仓库和产品事实；
- 事件图文故事板负责事件主体、动作、来源与风险；
- 自定义图文故事板负责用户提供的主题和材料；
- 原来的生成器收敛为图文生成与交付。

这次拆分让我们意识到，技能边界不应该按照“最终生成什么文件”划分，而应该按照“它承担什么判断责任”划分。

故事板就是故事板，生成就是生成，事实核验也应该独立存在。一个技能承担的判断越多，它越难替换、测试和复用。

## 第四阶段：从固定流水线走向技能与工具平台

项目真正发生质变，是我们开始实施工具插件化和创作技能可配置化。

过去，程序知道具体抓取器、脚本路径、技能名称和阶段顺序。增加一种能力，往往需要同时修改路由、管线、页面和配置。

后来我们把系统拆成了三个层次：

- 技能决定如何写、如何判断和如何组织内容；
- 工具负责获取信息或执行确定性操作；
- 流程负责安排技能与工具在什么阶段运行。

技能通过 `skill.json` 声明自己的 `kind`、适用入口、内容类型、输入输出契约和工具依赖。工具则通过 capability 暴露能力，例如网页读取、仓库分析、网络搜索和文档检索。

创作流程不再绑定某个具体插件，只声明“我需要什么能力”。

与此同时，我们补齐了技能安装、校验、启停、卸载、版本归档、默认技能和单次覆盖。热点事件、自主写作、批次早报以及三类图文入口，都可以选择兼容技能。

每次任务还会冻结技能 ID、Prompt 哈希、工具实现、插件版本和阶段产物。今天修改配置，不会改变昨天任务的审计结果。

做到这里，项目已经不再是“接了很多 AI 功能的写作软件”，而是一套围绕写作工程建立的 Agents 平台。

它不是通用 Agent 市场，也不追求让 Agent 任意调用一切。它的价值恰恰来自聚焦：所有扩展都服务于资料获取、事实组织、文章创作、质量加工和内容交付。

## 第五阶段：开源之后，第一公里比第一百个功能更重要

7 月底完成开源治理后，我们做的第一批事情不是新功能，而是"第一公里"。

首次安装引导把"装依赖、建配置、填 Key、装 RSSHub"收进一个交互脚本，RSSHub 缺失时自动浅克隆续装；编辑室在对话前先备料，把事件来源原文一次性抓齐；本地段落检索让长正文不再靠截断进上下文；搜索槽位落地后，此前规划里的网络搜索、新闻搜索和文档检索全部从待办变成了可切换的能力实现。

这一阶段的体会是：开源不是终点，而是把"我自己能跑"变成"别人也能跑"的开始。安装脚本必须幂等、失败可重跑，因为新环境里没有你脑子里的那套前置知识。

## 第六阶段：主题从写死的样式变成可经营的资产

开源后最大的一块结构性投入是主题体系。

过去主题只是编译器里的内置样式，改一个封面、调一种骨架都要动代码。我们先用一次完整的样式能力盘点摸清家底，然后分几步走：主题 JSON 化（注册表 + 主题目录 + 基线校验）、主题编辑器（元素级配置、覆盖率校验、发布门禁、生产级实时预览）、主题中心 AI 创建（候选确认、受控发布），最后把封面标题、骨架、节奏这些编译器里的硬编码视觉决策，逐一迁移成主题 JSON 的显式字段。

图文密度问题也在这个过程中收敛。与其渲染失败后修补，不如在规划阶段就做确定性预防：故事板密度预算在生成前裁剪块数和列表条目，双列网格只在真正适用的页面生效，稀疏页有确定性兜底。封面标题的强调色块断行则交给 AI 语义切分，规则上对齐小红书与公众号两个渠道。

这一步让我们确认了一件事：**凡是需要被经营的资产，都必须从代码里走出来变成数据。** 主题如此，后面选题阶段的 prompt 和评分参数也是如此。

## 第七阶段：选题链的最后一块硬编码被打开

成稿链早已技能化，但选题链的五个 LLM 环节——热点打标、事件卡、探索脑暴、综合研判、编辑会——prompt 一直内联在代码里，改一个倾向就要改代码、发版本。

这次把它们原样提取为五个项目技能，走标准技能运行时加载，自动获得配置覆盖层和 prompt 哈希快照；代码保留内联原文作为兜底，技能缺失时行为完全不变。编辑会的账号上下文改为占位符注入，数据和 prompt 保持分离。

评分参数也跟着走出代码：F=H×60%+B×25%+P×15%−S 的权重、账号契合加分、分类偏好和基分，都可以在账号配置里按键覆盖。这里有一条清晰的边界——**模型产出的评分原料归技能管，加总成最终分的公式归确定性代码管**。判断可以演进，算术必须可复现。

同一批改动里还有一件来自真实运营的小事：复盘公众号流量主后台数据后，我们发现留言区广告的 eCPM 约为文中广告的四倍却曝光率极低。这个结论没有写成一篇文章，而是写进了成稿技能的契约——每篇文章结尾必须有一个具体可答的留言引导问题。数据复盘直接变成了生产规范。

## 我们踩过的坑，比功能列表更有价值

高效率并不意味着一路顺利。

前端从单体脚本迁移到 ESM 时，出现过模块加载顺序、全局状态、懒加载依赖和函数回退问题。`providerOptions is not defined` 就是典型例子：代码被拆开了，但依赖关系没有被完整表达。

我们也遇到过重复变量导致服务无法启动、模板字符串替换破坏语法、固定最小列宽撑出水平滚动条，以及隐藏面板仍然占据布局空间。

更隐蔽的问题来自数据和界面的错位。事件图文的事实与来源实际已经存在，但页面只读取单一热点 URL，于是用户看到的却是“没有事实来源”。这不是数据缺失，而是展示模型仍停留在旧的数据结构里。

远程 API/MCP 页面也曾写成“连接远程 API / MCP”，让人自然以为粘贴一个地址就能连接。实际上，它接收的是完整 Manifest，而且只支持固定 JSON POST 和 MCP Streamable HTTP。能力没有错，但产品语言错了，同样会造成失败体验。

这些问题共同说明：系统架构、运行契约和界面表达必须使用同一套概念。任何一层仍在使用旧概念，用户最终都会感受到裂缝。

## 为什么我们能推进得这么快

首先，我们一直围绕真实任务验收，而不是围绕抽象架构自我满足。

文章能不能写完、来源能不能追溯、技能能不能真正被调用、故事板能不能生成图片，这些问题都有明确结果。

其次，我们采用了阶段化实施。先定义契约，再接运行时；先完成只读查看，再开放安装；先建立默认路由，再支持单次覆盖。每一步都可以独立验收，也可以随时停下来修正方向。

第三，我们把踩过的坑转化成了自动化测试。编译错误、路由加载、技能兼容性、事实门禁、布局契约和管理能力都逐步进入回归测试。修复不再只是“这次能用了”，而是“以后不应该再坏”。

最后，也是最重要的一点：产品判断和工程实现一直在同一条反馈链上。发现技能页面不好找，就重新分类；发现故事板职责过重，就拆技能；发现提示误导，就修正产品语言。很多架构升级，其实都来自一个具体的使用不顺。

## 这段开发经历留下了什么

我们最终得到的不只是一套功能，而是一组可以复用的方法：

- 先设计事实和契约，再设计 Prompt。
- 按判断责任拆分技能，不制造万能 Agent。
- 流程依赖 capability，不依赖服务商名称。
- 把历史快照当成核心数据，而不是附加日志。
- 失败要明确，不能用静默降级制造虚假成功。
- 用户界面的命名，本身就是架构的一部分。
- 高效率来自短反馈闭环，而不是省略设计和测试。
- 需要被经营的资产（主题、Prompt、评分参数）都要从代码里走出来变成数据。
- 判断归技能，公式归代码：模型的产出可以演进，聚合的算术必须可复现。

项目现在的位置是成功的，但还没有结束。

普通 REST API 与 MCP 还需要更友好的连接向导；技能调用链值得被可视化，让用户看清一次创作到底调用了什么、为什么返工、在哪里降级；事件事实基座的来源明细和跨任务的性能与失败分析也还在待办里。

不过，最难的一步已经完成了：我们已经找到这个项目真正应该成为的东西。

它不是另一个套着聊天框的 AI 写作工具。

它是一间可以安装能力、安排分工、保留证据、执行门禁，并持续进化的数字编辑部——一套真正为写作而生的 Agents 平台。
