# 写作专属 Agents 平台开发记录

> 文档性质：内部工程复盘  
> 记录范围：项目启动至 2026-08-02  
> 统计口径：当前 Git 仓库与工作区代码快照

## 1. 项目缘起、目标与定位

### 1.1 缘起：为什么做这个项目

本项目起源于 openclaw 的编排技能（如 `hotspot-to-topics-orchestrated`）。在通用工具协作平台上执行这类编排技能时，暴露了两个绕不开的问题：

- **长链路总会中断**：编排技能要求多步骤连续自主执行，而通用 Agent 平台无法保证全程不中断，一次失败往往意味着从头再来；
- **Token 消耗不可控**：热点抓取与总结在对话上下文中进行，每轮都携带大量原始内容，成本随轮次快速膨胀。

结论是需要一个专门的应用：把流程状态、中间产物和人工确认点沉淀到本地数据库与文件中，让 AI 调用成为可恢复、可审计、可单独重跑的阶段任务，而不是一段随时会断的对话。

### 1.2 目标：写作专属 Agents 平台

本项目的目标从一开始就很明确：做一个聚焦写作能力的 Agents 平台。其他 Agents 平台的通用模式一概不用，不追求大而全，做到专而精——只把热点采集、事实研判、编辑决策、成稿、排版、图文交付这条写作链路做深做透。

### 1.3 思路转折历程

整个过程是边实践边思考，主线经历了五次转折：

1. **第一版：采集 + 评分 + 脑暴选题**（2026-07-20 项目初始化）。通过 RSS、浏览器抓取技能规定的数据源，对拉取的热点排名评分，从排名最高的十条热点中脑暴产生选题。此时小红书图文与「热点采集写公众号文章」是两条完全无关的链路，图文只能根据 GitHub 仓库生成相应的介绍图文。见 [2026-07-20-project-init.md](2026-07-20-project-init.md)。
2. **技能执行器与编排器**。后续考虑功能拓展时，参考现有 AI 工作流平台，优先做了技能执行器和编排器，并将提示词从编排器中拆分出来放到单独的技能中。见 [typeset-pipeline-optimization-plan.md](typeset-pipeline-optimization-plan.md)。
3. **热点到选题的升级**。从单热点评分改进为「热点—事件—维度」聚合：一个维度聚合多个事件，一个事件聚合多个热点来源。维度从 5W1H 产生（Who / What / Where / When / Why / How）；事件聚合时更关注 who、where、what，即主体、地点和动作，从而更全局地看清热点背后的事件。见 [optional-feature-implementation-roadmap.md](optional-feature-implementation-roadmap.md)、[event-deep-fetch-and-fact-base-plan.md](event-deep-fetch-and-fact-base-plan.md)。
4. **双内容池与图文生产**。热点选题优化后，开始做小红书图文生产。见 [dual-content-pools-and-social-card-pipeline.md](dual-content-pools-and-social-card-pipeline.md)；随后继续拓展自定义图文等能力，见 [optional-feature-todos.md](optional-feature-todos.md)、[custom-content-and-xiaohongshu-design.md](custom-content-and-xiaohongshu-design.md)。
5. **技能化与插件化改造**。整体功能完善后，才进行功能的技能化和插件化改造，把内置能力开放为可安装、可替换的扩展。见 [social-card-storyboard-skill-extension-plan.md](social-card-storyboard-skill-extension-plan.md)、[skill-and-tool-extension-plan.md](skill-and-tool-extension-plan.md)。

### 1.4 定位的变化

#### 初始定位

项目最初是一套本地优先的公众号编辑工作台，目标是把热点采集、选题、编辑确认、文章生成和排版交付放进同一个工作环境。

#### 当前定位

项目已经演化为面向写作工程的专属 Agents 平台：

```text
创作入口
  → 流程编排
  → 技能选择与阶段执行
  → 信息工具与确定性工具
  → 事实基座与质量门禁
  → 历史快照、审计与交付
```

当前平台并不追求通用 Agent 自由编排，而是把扩展范围收敛在：

- 外部信息获取；
- 事实组织与来源追溯；
- 文章及图文创作；
- 标题、审阅、自然化和 SEO 加工；
- 配图、排版和交付；
- 运行状态、失败原因和历史审计。

## 2. 核心设计思路

### 2.1 从终稿倒推生产流程

我们没有把“模型返回文字”定义为完成，而是从可发布终稿倒推必要步骤：

1. 来源可用且可追溯；
2. 热点被聚合为事件；
3. 编辑命题和作者立场被确认；
4. 事实、观点和待核信息有明确边界；
5. 文章经过主写作和加工阶段；
6. 质量门禁通过；
7. 配图、版权、排版和交付条件满足。

### 2.2 将系统拆成技能、工具和流程

| 层次 | 职责 | 不应承担的职责 |
| --- | --- | --- |
| 技能 | 写作规则、判断方法、内容组织和阶段 Prompt | 任意系统权限、具体服务商绑定 |
| 工具 | 信息获取、文件读取、渲染、上传等确定性能力 | 决定文章立场或创作流程 |
| 流程 | 安排执行顺序、选择技能、处理门禁与返工 | 重复实现技能规则或工具逻辑 |

### 2.3 以契约代替隐式约定

技能通过 `skill.json` 声明：

- `kind`；
- `entryPoints`；
- `contentTypes`；
- `inputContract`；
- `outputContract`；
- `requiredCapabilities`；
- `optionalCapabilities`；
- App 兼容范围。

工具通过 capability 被流程解析。流程声明需要什么能力，而不是直接指定某个插件。

### 2.4 用历史快照保证可追溯

一次生成任务需要冻结：

- 请求技能和最终选择技能；
- 选择来源：手动、入口默认或内置兜底；
- Prompt 哈希；
- 工具插件及版本；
- 模型配置；
- 阶段输入输出摘要；
- 质量门禁和返工记录。

历史结果不能随当前配置变化而改变。

## 3. 阶段开发记录

### 阶段一：工作台骨架与完整文章入口

主要事项：

- 建立每日批次和状态流转；
- 接入 Reddit、RSSHub 和直连 Feed；
- 建立来源身份、执行状态、耗时和错误记录；
- 建立热点历史、热点全景和选题池；
- 建立编辑室和结构化编辑决策；
- 建立文章编辑器、内容日历、产物索引和模型中心；
- 增加本地优先配置、SQLite 数据和任务恢复。

阶段判断：

- 单次模型调用无法代表内容生产；
- 必须以编辑部工作流作为产品主结构；
- 从一开始记录过程数据，避免后期只剩不可解释的终稿。

### 阶段二：事件、事实基座和文章质量链

主要事项：

- 将原始热点聚合为语义事件簇；
- 建立事件卡和事件级事实基座；
- 增加已确认事实、来源增量、分歧、时间线和待核内容；
- 将编辑室回答拆分为事实、观点、实践、禁写项和未决问题；
- 统一热点事件、自主写作和批次早报的文章阶段；
- 补齐主写作、标题、自然化、审阅和 SEO；
- 增加字数、引用、事实覆盖和正文完整性门禁；
- 为失败阶段增加定向返工和明确停止。

关键决策：

- 字数目标调整为 1500 字，上下浮动 200 字不触发修复；
- 模型只返回门禁说明时，不得被视为正文；
- 引用覆盖必须基于事实基座，而不是关键词表面匹配；
- HTTP 成功与业务成功分离。

### 阶段三：双内容池与图文生产

主要事项：

- 建立工具图文、事件图文和自定义图文入口；
- 支持公众号与小红书渠道；
- 建立图文事实基座、故事板和生成交付三阶段；
- 支持逐页内容编辑、版式选择和整组生成；
- 建立固定画布、智能混排、布局审计和交付门禁；
- 生成配套文案、HTML、PNG 和交付报告；
- 调整三类图文页面在全屏和中等宽度下的布局。

关键重构：

早期 `xiaohongshu-article-generator` 同时承担事实、故事板、文案、生成和交付。后续拆分为：

- `repository-card-storyboard`；
- `event-card-storyboard`；
- `custom-card-storyboard`；
- `xiaohongshu-article-generator` 仅保留生成与交付职责。

经验：

- 技能应按判断责任拆分，而不是按最终文件格式拆分；
- 不同事实来源应使用不同故事板技能；
- 隐藏评分栏或辅助栏时，布局列也必须同步移除。

### 阶段四：工具插件化与技能可配置化

主要事项：

- 建立统一工具注册中心；
- 将 URL 抓取、本地读取、Mermaid、ECharts 和图片上传注册为 capability；
- 建立技能发现、清单解析、Prompt 哈希和兼容性检查；
- 建立技能详情、只读 `SKILL.md` 和文件查看；
- 建立技能安装、预检、启停、卸载、归档与恢复；
- 建立默认技能和单次技能覆盖；
- 建立工具插件安装、优先级、健康检查和执行历史；
- 建立远程 API/MCP 声明式工具连接；
- 将技能与工具管理拆为独立一级页面；
- 将技能列表严格按 `kind` 分组。

阶段实施方式：

1. 先完成内置能力注册；
2. 再接技能发现和历史兼容；
3. 再接运行快照和调用审计；
4. 然后开放第三方技能安装；
5. 最后开放受信本地工具和受控远程工具。

安全边界：

- 内置技能只读；
- 第三方技能安装不执行包内代码；
- 本地工具仅限管理员审查；
- 远程工具只能通过 HTTPS；
- 拒绝内网、保留地址、危险重定向和本地绝对路径；
- 凭据只存服务端，不回传页面和备份；
- 外部写入继续要求明确授权。

### 阶段五：UX 收敛与产品语言统一

主要事项：

- 重构热点事件、自主写作和批次早报的创作配置；
- 统一三个文章入口的技能选择流程；
- 重构三类图文页面为事实基座—故事板—生成交付工作台；
- 优化全屏和中等宽度响应式布局；
- 将“技能与插件”统一为“技能与工具”；
- 技能按 `kind` 分组，故事板保持独立分类；
- 明确远程工具入口实际接收 Manifest，而不是单独 URL；
- 修复模型中心固定列宽导致的页面级水平滚动。

产品语言原则：

- 页面名称应描述用户正在做的事情；
- 技术限制必须在用户输入前说明；
- “连接地址”“导入 Manifest”“安装技能包”不能混用；
- 状态提示必须区分未实现、未连接、不可用和执行失败。

### 阶段六：开源后的上手体验与链路补强

主要事项：

- 首次安装引导 CLI 与跨平台脚本（`npm run setup` / `setup-workbench.cmd`），RSSHub 缺失时自动浅克隆并安装依赖；
- 编辑室两步备料：对话前幂等抓取全部事件来源原文，失败不阻断、可跳过；
- 新增本地段落检索插件，编辑室长正文按「头部 + BM25 相关段落」摘录注入；能力槽位从固定 6 个信息槽位推广到注册表全部工具能力；
- 搜索槽位落地：tavily-search、document-folder-search 插件，自主写作与自定义图文接入联网 / 新闻 / 本地知识库检索，创作表单的搜索开关移除、检索自动执行；
- 文章配图支持可生成类别：IMG-DATA 结构化占位与 timeline / datacard 确定性生成管线；
- 批次早报展示最近生成记录，失败可见可重试，执行中刷新自动续接；
- 模型网关健壮性：超时不再误报空内容、默认超时提升至 5 分钟，对齐 DeepSeek 最新接口（`content_filter` / 资源不足明确报错、`reasoningEffort` 透传）。

### 阶段七：主题体系拓展

主题从「内置写死的排版样式」演进为「JSON 化、可编辑、可 AI 创建的资产」，是开源后最大的一块结构性投入：

- **主题 JSON 化**：文章排版与图文主题迁移为注册表 + 主题目录 + 基线校验，排版管线与前端统一从主题目录消费；
- **主题可配置化**：主题编辑器、样式能力清单与覆盖率校验、发布门禁与生产级实时预览；随后细化到元素级——区分外围背景与图文页背景、强调色块对比度门禁随配方联动、隐藏无实际作用的字段；
- **主题中心 AI 创建**：AI 生成主题候选、确认后受控发布，并修复配套缺陷；
- **视觉增强与配方显式化**：封面标题 / 骨架 / 节奏 / 封面承载配方从编译器硬编码迁移为主题 JSON 显式字段，骨架支持全页型与同骨架组内第二层视觉差异，主题选择器按内容场景与阅读密度辅助决策；
- **图文密度与封面标题收敛**：故事板密度预算（规划阶段确定性裁剪块数与列表条目）、双列网格适用范围收紧、稀疏页确定性兜底、布局修复穷尽后的失败信息带明细与编辑指引；封面标题强调色块改为 AI 语义断行并补齐诊断，公众号封面标题规则对齐小红书 TITLE_GUIDE。

设计要点：

- 样式能力先盘点再扩展（`theme-style-capability-inventory.md`），每批扩展带逐主题渲染证据与复现脚本，视觉改动不靠目测；
- 布局问题优先在规划阶段确定性预防（密度预算），而不是渲染失败后再修补；
- 凡是编译器里的硬编码视觉决策，能声明化的都迁移为主题 JSON 字段，让主题作者无需改代码。

### 阶段八：选题链技能化与评分可配置化

主要事项：

- 选题阶段 5 个 LLM 环节（热点打标、事件卡、探索脑暴、综合研判、编辑会）的 system prompt 从代码内联常量提取为项目技能，统一经 `lib/llm/selection-prompts.mjs` 走标准技能运行时加载；技能缺失时回退内联原文，行为不变；编辑会的账号上下文改为 `{{ACCOUNT_CONTEXT}}` 占位符由代码注入，数据与 prompt 保持分离。
- 选题评分参数从代码常量变为账号配置：`account-context.json` 的 `scoring` 段可覆盖 F=H×h+B×b+P×p-S 权重、账号契合加分、分类偏好与 pBase/hBase 基分；`resolveScoring` 按键合并、非法值回退默认，生产调用点显式传参，纯函数默认值不受用户配置影响，保证既有测试稳定。
- 成稿技能加入流量主变现配合规则（结尾留言引导问题、商业词汇自然覆盖、文中广告发布侧位置），来自真实账号后台数据复盘（留言区广告 eCPM 约为文中广告 4 倍但曝光率低）。
- 新增 `docs/configuration.md` 配置项参考，收拢此前分散在 README 与各文档中的配置字段；技能与工具的编写安装保持 `docs/extending.md` 单一来源。

设计要点：

- **判断归技能，公式归代码**：模型产出的评分原料（preScores、bScores、竞争修正）由技能 prompt 约束，而加总成 F 分的公式保持确定性代码与配置数据，可复现、可测试。
- **fallback 与占位符是技能化的两个边界处理**：代码内联原文作为技能缺失时的兜底，避免发行包或技能目录被覆盖时功能中断；需要代码注入的动态数据用字面占位符，不做隐式模板引擎。
- **配置只写差异键**：评分覆盖采用按键合并而非整表替换，未配置的键永远跟随代码默认演进。

## 4. 典型踩坑与处理
### 4.1 ESM 迁移后依赖关系没有同步显式化

现象：

- 按需模块加载后出现函数未定义；
- 全局 `state` 与模块内状态不同步；
- 页面需要的模块尚未加载；
- `providerOptions is not defined`；
- 部分视图只能临时回退旧系统函数。

原因：

- 代码完成了文件拆分，但依赖关系仍依靠原来的加载顺序和全局变量；
- 模块边界与运行边界没有同时重建。

处理：

- 建立 `public/src` 模块结构；
- 统一核心 UI、HTTP、state 和 DOM 依赖；
- 使用显式 import；
- 为懒加载建立可靠入口；
- 将模块加载和页面数据加载纳入回归测试。

经验：

模块化不是切文件。只有依赖、状态和生命周期都被显式表达，迁移才算完成。

### 4.2 机械编辑造成语法和重复声明错误

现象：

- 多余 `}` 导致渲染函数提前结束；
- 模板字符串换行或引号被破坏；
- `channelMode` 重复声明导致服务无法启动；
- 替换边界错误留下重复代码块。

处理：

- 增加路由模块 `node --check`；
- 修改后执行针对性测试和 `git diff --check`；
- 减少大范围字符串替换；
- 优先以结构化、小范围补丁修改。

经验：

生成式开发速度越快，越需要廉价且高频的语法检查。编译检查应成为每次修改的默认动作。

### 4.3 数据存在，但页面显示“没有来源”

现象：

事件候选已经关联多个热点、事件卡和来源文档，页面仍显示“尚无事件来源”。

原因：

- 页面顶部只读取单一 `candidate.url`；
- 综合事件候选没有单一 `hotspot_id`；
- 新的数据模型已经是多来源事件，展示层仍按单热点设计。

处理方向：

- 事实基座按关联事件和来源集合展示；
- 主要来源与补充来源分层；
- 页面状态不得仅通过单个 URL 是否存在推断。

经验：

数据模型升级后，要逐项检查查询、API、状态判断和 UI 文案。仅修改后端并不会自动完成产品升级。

### 4.4 门禁过严或判断目标错误

现象：

- 文章长度连续修复三次；
- 门禁说明被当成正文继续审阅；
- citation coverage 为零但事实可能已被改写使用；
- 审阅阶段重复返工却没有信息增量。

原因：

- 把精确数字当成质量；
- 只检查形式，不检查产物角色；
- 返工没有针对失败原因限制范围。

处理：

- 使用合理长度区间；
- 增加正文结构与可见内容检查；
- 返工提示只修复失败维度；
- 超过返工上限明确失败；
- 事实引用和观点表达分别判断。

经验：

质量门禁应该减少错误，而不是制造循环。每次返工都必须有明确目标和停止条件。

### 4.5 技能职责过大

现象：

一个图文技能包含仓库事实、自定义内容、事件故事板、配套文案、HTML 和图片交付。

风险：

- Prompt 修改互相影响；
- 输入输出契约模糊；
- 无法为不同入口设置默认；
- 测试只能覆盖整个大流程。

处理：

- 将三类故事板拆成独立技能；
- 生成器只负责确定性生成与交付；
- 入口通过 `kind` 和契约解析兼容技能。

经验：

判断职责是技能拆分的第一依据；流程阶段和文件目录只是辅助依据。

### 4.6 固定宽度在真实工作区中溢出

现象：

- 图文全屏下内容区域过窄或右侧留白；
- 批次早报第二步集中在过小卡片中；
- 模型中心出现页面级水平滚动条。

原因：

- 只按浏览器总宽度设计，没有扣除固定侧栏；
- Grid 子项默认 `min-width:auto`；
- 多列同时设置固定最小宽度；
- 响应式断点设置得太晚。

处理：

- 使用 `minmax(0,1fr)`；
- 为 Grid/Flex 子项显式设置 `min-width:0`；
- 提前切换单列；
- 长文本截断或换行；
- 对全屏、中等宽度和移动端分别验收。

经验：

响应式设计必须基于“实际可用内容宽度”，不能只看 viewport。

### 4.7 技术能力与页面提示不一致

现象：

“连接远程 API/MCP”让用户以为可以直接粘贴 URL，但实现实际要求完整 Manifest。

当前能力边界：

- Remote API 只支持固定 endpoint 的 JSON POST；
- MCP 只支持 Streamable HTTP；
- MCP 必须声明 `toolName`；
- 不支持从地址自动执行 `tools/list`；
- 不支持 GET 路径模板 API；
- 不从远端读取技能包。

处理：

- 页面改为“导入远程工具连接声明”；
- 明确不能只粘贴地址；
- 在输入框直接展示完整 Manifest 示例；
- 区分支持和暂不支持范围。

经验：

准确的限制说明不是次要文案，而是功能正确性的一部分。

## 5. 效率方法复盘

### 5.1 小阶段闭环

复杂改造被拆成 P0、P1、P2 等阶段，每阶段都包含：

- 明确问题；
- 最小契约；
- 实施范围；
- 自动化测试；
- 人工验收点；
- 后续边界。

这样可以快速交付，同时避免半成品架构无限扩散。

### 5.2 先诊断，再决定是否修改

对“事实不存在”“工具不可用”“页面空白”等问题，先检查：

- 数据是否真的缺失；
- API 是否返回；
- 页面是否读取正确字段；
- 状态文案是否准确；
- 是否只是响应式布局问题。

这避免了为展示问题重复生成数据，或者为数据问题只修 CSS。

### 5.3 把用户反馈当成架构测试

多次关键重构都来自实际使用反馈：

- 技能不好找 → 建立 `kind` 分组；
- 技能不能使用 → 打通入口路由和默认技能；
- 故事板职责过重 → 拆成独立技能；
- 来源显示为空 → 检查多事件数据模型；
- 远程连接误导 → 重新定义入口语言；
- 全屏布局失衡 → 调整内容宽度和断点。

实际操作中的困惑，往往比抽象代码审查更早暴露系统边界问题。

### 5.4 修复必须进入回归

已经纳入或应持续纳入测试的内容：

- 路由模块语法检查；
- 技能 Manifest 和兼容性；
- 默认技能与单次覆盖优先级；
- 工具 capability 解析；
- 远程工具权限和地址安全；
- 文章阶段和门禁；
- 图文故事板契约；
- 页面关键文案和布局约束；
- 备份恢复与历史兼容。

## 7. 可复用经验

1. 先定义事实和契约，再写 Prompt。
2. Agent 的边界应由判断责任决定。
3. 流程依赖 capability，不依赖具体服务商。
4. 安装能力和启用能力必须分离。
5. 默认选择和本次覆盖必须有明确优先级。
6. 业务成功必须有确定性门禁，不能依赖 HTTP 状态。
7. 返工必须有目标、次数上限和停止条件。
8. 历史快照是核心业务数据，不是附属日志。
9. 数据模型、API 和 UI 必须使用同一套概念。
10. 产品提示必须准确描述当前能力边界。
11. 响应式布局要基于实际内容宽度。
12. 高速迭代必须配套高频、低成本的回归检查。

## 8. 阶段结论

项目当前最重要的成果，不是增加了多少 AI 功能，而是形成了一套稳定的写作能力组织方式：

```text
事实可追溯
  + 技能可替换
  + 工具可扩展
  + 流程可审计
  + 失败可解释
  + 产物可交付
```

它已经从一个公众号写作工具，演化成面向写作工程的专属 Agents 平台。后续扩展应继续保持这个聚焦，不为了“通用”牺牲事实边界、安全控制和内容生产质量。
