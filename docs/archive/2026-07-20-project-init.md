# [$hotspot-to-topics-orchestrated](C:\\Users\\Administrator\\.codex\\skills\\hotspot-to-topics-orchestrated\\SKILL.md) 我想把这个技能和排版技能封装成一个应用，你觉得可行吗？

可行，而且很适合产品化。我的判断是：

- 做成个人/团队内部应用：可行性高。
- 做成公开 SaaS：可行，但采集稳定性、浏览器登录态和凭据隔离会明显增加复杂度。
- 不能只把两个技能首尾相接，中间必须纳入 `wechat-mp-topic-to-article` 成稿链。

正确的产品主链应该是：

````
```mermaid
flowchart LR
    A["热点采集"] --> B["聚类、评分与风险标记"]
    B --> C["人工选题"]
    C --> D["编辑讨论 / 补证 / 实验"]
    D --> E["锁定 article-brief.md"]
    E --> F["生成并审核 09-FINAL.md"]
    F --> G["公众号排版"]
    G --> H["本地 HTML / 复制页预览"]
```
````

最适合的产品形态不是“一键生成文章”，而是“公众号编辑工作台”。因为现有技能里有几个不能删掉的人机节点：

- 数据源失败后，决定重试还是跳过。
- 查看热点全景、评分和风险后选择题目。
- 编辑会确认作者立场，必要时补实验或资料。
- 确认正文后再进入排版。
- 本地模式与图片上传、预览模式分开。

我建议应用设计成六个页面：

1. 今日热点：采集状态、失败源重试、国内/海外筛选。
2. 热点全景：词云、多媒体覆盖、事件聚类。
3. 选题池：爆款榜、风险、评分依据、文章/贴图分流。
4. 编辑室：逐个关键问题、材料补充、状态恢复。
5. 文章编辑器：事实来源、标题、正文、审稿状态。
6. 排版预览：设计方案、公众号 HTML、复制页链接。

实现上，我最推荐“本地优先 Web 应用”：

- 前端：Next.js/React。
- 后端：Node.js/TypeScript 编排服务。
- 状态：SQLite 保存任务、检查点和人工决定。
- 产物：继续保留 Markdown、JSON、HTML 文件，数据库只管理索引和状态。
- 执行器：本地 Worker 调用 Python、Chromium、RSSHub、图表渲染和上传脚本。
- AI：把现有技能当作经过验证的流程规范，逐步迁移成结构化工作流；不要把 `SKILL.md` 当作可直接调用的 API。

Codex 技能本身很适合保存和复用工作流；官方也把技能定位为可重复使用的工作流能力。[Codex Use Cases](https://developers.openai.com/codex/use-cases?search=Workflow) 如果未来希望在 ChatGPT 内提供交互界面，则可以进一步做成“Web 组件 + MCP 服务”的应用形态；官方资源页也提供了 Apps SDK 与 MCP 示例。[OpenAI Resources](https://developers.openai.com/resources)

建议按三个版本推进：

- V0：现有技能外面包一层任务面板，显示进度、产物和人工确认点。
- V1：把选题、编辑室、文章、排版真正做成结构化 UI。
- V2：再增加多人协作、定时采集、模板市场、公众号发布接口和数据复盘。

其中 V0 最值得先做：保留现有技能能力，只解决“难操作、状态看不见、暂停后不好恢复”的问题。当前工作区基本是空仓库，也很适合直接从这个方向搭骨架。

一句话结论：值得做，但产品边界应从“两技能封装”升级为“热点到公众号预览的完整编辑工作台”，而不是一个黑盒式的一键按钮。

# 梳理AI调用，支持模型自定义配置

目前采集完成后，AI 不会自动连续运行。现阶段只有以下操作会调用模型：

1. 模型中心 → AI 打标当前批次

每 20 条热点调用一次模型，生成：

- 主题分类
- 国内 / 海外 / 全球范围
- 中国受众相关度及理由
- 内容风险等级及理由
- 公众号选题相关度分数

结果写回热点数据库。这里的分数只是相关度，不等于完整的 H/B/P/S/D/F 爆款评分。

1. 文章编辑器 → AI 生成 / 改写

只有选题经过编辑室并锁定 `article-brief.md` 后才能调用。模型会读取：

- 锁定命题和文章角度
- 已确认事实与来源
- 作者观点和真实经历
- 反证与适用边界
- 禁止写入内容
- 当前草稿
- 本轮修改要求

生成结果先放进编辑器，不会自动保存。

1. 上下文压缩

这不是单独按钮。当创作请求接近模型限制时，会额外调用一次模型压缩旧稿和早期讨论，再执行正式创作。因此一次“AI 生成”可能产生：

```
压缩摘要调用 → 正式创作调用
```

事实、来源、作者确认和禁写项不会进入可压缩范围。

1. 模型连接测试

“模型中心 → 最小请求测试连接”也会调用模型，但只要求回复 `OK`，用于验证密钥和模型配置。

目前还没有接入 AI 的环节：

- 热点语义事件聚类
- 核心 8 条 + 黑马 2 条预选
- H/B/P/S/D/F 完整评分
- 两阶段热点脑暴
- 编辑室主动提问与选题共创
- 事实研究和事实基座生成
- 标题、大纲、审稿、去 AI、SEO
- 公众号排版设计

所以当前实际链路是：

```
Reddit / RSSHub 采集
        ↓
AI 热点打标（手动启动）
        ↓
人工加入选题池
        ↓
人工编辑会并锁定简报
        ↓
AI 生成或修改草稿（手动启动）
        ↓
人工审阅保存
        ↓
排版流程
```

也就是说，已经接入的是“基础打标 + 锁定简报后的创作”，而完整的 `hotspot-to-topics-orchestrated → topic-to-article → article-typeset` AI 工作流还没有真正串起来。下一步最有价值的是先补上“热点研判”按钮，把语义聚类、核心/黑马预选、脑暴和 H/B/P/S/D/F 评分一次跑通。

# 第一版落地

总体判断：项目已经从 MVP 进化成了一个可日常使用的“公众号内容生产工作台”。采集、选题、编辑决策、成稿、配图、排版、归档这条主链基本贯通。当前短板主要在工程收口和任务可靠性，不是核心功能缺失。

## 已实现的主要功能

- 热点采集：Reddit 专用 Chrome/CDP、RSSHub、直连 RSS/Atom，支持单源隔离、时间窗口过滤、人工补热点、跨批次去重。
- 热点研判：AI 语义打标、增量/全量重跑、事件聚类、热词云、多来源覆盖、国内/全球分类、核心 8 条＋黑马 2 条＋候补。
- 选题池：H/B/P/S/D/F 评分、未入池原因、人工补选、多热点综合选题。
- 编辑室：抓取原始来源、流式 AI 追问、结构化沉淀事实/观点/实践/禁写项、相似历史文章提示、简报锁定门禁。
- 完整成稿链：文章规划、作者素材、大纲、标题、初稿、去 AI、审稿、SEO、2000 字门禁、终稿，共保留 `00`～`09` 阶段产物。
- 文章编辑：草稿和终稿可手工修改、预览、保存，也可以针对现有内容再次调用 AI。
- 配图与排版：AI 识别必要资料图、保存本地图片、明确授权后上传 CDN、生成公众号 HTML、样式内联、无 `div` 门禁、富文本复制。
- 资产管理：热点档案、产物柜、按批次筛选、文章统计、内容日历。
- 模型中心：DeepSeek、MiniMax、Kimi 兼容网关，连接测试、流式响应、调用审计、上下文压缩。
- 运维能力：SQLite WAL、任务日志、订阅源管理、采集环境检查、服务重启后的中断状态恢复。

主要功能说明和 API 已分别整理在 [README.md (line 3)](E:/Documents/write-assistant/README.md:3) 和 [API.md (line 1)](E:/Documents/write-assistant/API.md:1)。
