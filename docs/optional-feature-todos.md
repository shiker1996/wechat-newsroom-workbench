## 1. 非仓库类自定义图文

> 状态：第一批已完成（2026-07-25，教程/清单/观点 × 公众号/小红书）；第二批（种草/生活/经验）暂不实施——经评估可直接映射到现有类型（种草→清单、经验→观点/教程），体验真实性三来源等级已覆盖其主要风险，等出现真实种草需求再评估是否加专门类型与功效词约束  
> 设计与实施记录：[自定义图文 + 小红书渠道设计评审](./custom-content-and-xiaohongshu-design.md)

### 当前限制

当前图文生产链面向 GitHub 和其他公开仓库设计，依赖仓库地址、README、License、Release、安装入口和权限边界建立事实基座，适合生成工具推荐、开源项目介绍和技术产品卡片。

目前不能直接创建以下内容：

- 种草图文
- 生活方式图文
- 经验分享
- 清单推荐
- 教程图文
- 观点图文

### 可选方案

- 在图文选题池增加“创建自定义图文”，与仓库候选明确区分。
- 支持填写主题、目标受众、使用场景、核心观点、素材链接、作者体验、限制说明和期望页数。
- 为自定义图文建立独立事实与素材基座，不强制要求 README、License、Release 或安装命令。
- 根据内容类型切换故事板模板和门禁，例如种草、生活、教程、清单、经验、观点。
- 继续复用现有视觉主题、逐页 HTML、布局审计、PNG 截图、配套文案和 ZIP 交付能力。
- 对体验性表述明确区分“作者真实体验”“用户提供素材”和“模型建议”，禁止模型虚构亲测、效果或收益。

### 实施前需要设计

- 自定义图文的选题和素材数据模型
- 图片、链接、文本和作者体验的素材上传方式
- 不同内容类型的事实门禁
- 不同内容类型的故事板契约
- 种草和生活类内容的广告、功效与体验真实性边界
- 自定义内容与仓库图文共用执行器还是拆分执行器

### 初步判断

- 潜在价值：高，可把图文能力从“开源工具卡”扩展为通用内容生产。
- 改动规模：中到大，主要成本不在截图和排版，而在输入模型、事实门禁和类型化故事板。
- 当前优先级：待评估，不纳入 P0–P4 仓库图文闭环。

## 7. 网站抓取与事件总结升级

> 状态：P0 已完成（2026-07-23）；P1 启发式质量评分 + P2 抓取路由已完成（2026-07-25）；P2 事件内精选深抓待实施

### 当前问题

- 常规热点研判主要使用 RSS 标题、摘要和 AI 标签完成事件聚类。
- 热点全景的综述以热词为单位，模型输入主要是文章标题和来源，不是完整网页正文。
- “AI”“技术”“公司”等宽泛热词覆盖大量不同事件，直接总结容易得到空泛结论。
- Firecrawl MCP 目前主要用于候选进入编辑室后的来源抓取和突发专题素材抓取，并未为常规研判全量提供正文。
- 当前抓取成功条件偏重正文长度，缺少正文相关性、导航噪声、登录墙、重复内容和来源可信度检查。

### 目标流程

```text
报道标题、RSS 摘要与原文
  → 单篇报道事实卡
  → 同事件聚类
  → 事件事实总结
  → 议题簇归纳
  → 热词导航与跨事件综述
```

热词只承担发现和导航职责；事件卡成为热点全景的核心信息单元；跨事件总结应建立在事件卡之上，而不是直接根据标题生成。

### P0：事件总结优先

> 实施状态：已完成（2026-07-23）。打标输入注入 RSS 摘要；研判管道在事件聚类后生成事件卡（`sources/event-cards.json`），热词综述改以事件卡为依据，关联事件数 ≥8 的泛词降级为筛选词；热点全景事件条目可展开事件卡。

- 为每个事件生成独立事件卡，包含事件结论、背景、已确认事实、来源增量、分歧、时间线、待核内容和可写角度。
- 模型输入由“文章标题 + 来源”升级为“标题 + RSS 摘要 + 来源 + 时间”。
- 热词综述改为读取事件卡生成。
- 对覆盖范围过大的泛词，只用于筛选，不直接充当总结主题。
- 预计改动量：小到中。

### P1：统一网页快照与抓取质量评分

- 统一保存 URL、最终 URL、标题、作者、发布时间、摘要、正文、抓取方式和抓取时间。
- 增加正文质量评分：标题相关性、有效段落、正文/导航比例、重复率、登录墙或错误页识别、关键词覆盖度。
- 区分完整正文、RSS 摘要、标题级信息等证据等级。
- Firecrawl 结果质量不足时自动回退本地抓取或标记待补抓。
- 复用缓存，避免同一来源反复消耗额度。
- 预计改动量：中。

### P2：多抓取器路由与事件内精选深抓

- 优先利用 RSS/RSSHub 已有全文或摘要。
- GitHub 使用 API 与 README；高频新闻站点、官方公告和普通网页采用适配器或本地正文提取。
- Firecrawl 作为动态网页和复杂页面的主力回退方案。
- 浏览器渲染只用于 X、复杂 JavaScript 页面和反爬页面的按需补抓。
- 不深抓全部报道：先全量轻抓和聚类，再为每个事件选择 2～3 个代表来源深抓；出现来源冲突时才追加。
- 候选进入选题池后，再升级为完整事实基座。
- 预计改动量：中到大。

> 实施状态：抓取路由部分已完成（2026-07-25）。`lib/domain/source-quality.mjs` 启发式评分（长度 40 + 段落 20 + 标题相关性 20，登录墙/错误页直接 5 分），纯规则不调模型；`lib/integrations/source-fetcher.mjs` 路由顺序：① twitter 热点直接用 RSS 摘要（推文即全文，fetch_method `rss-tweet`），长摘要视为可用正文（`rss-content`）；② GitHub 仓库 URL 走 API + README（`github-api`）；③ Python 本地抓取优先，质量分不足才升级 Firecrawl 并保留分高者，全失败时长摘要 `rss-summary-fallback` 兜底。每条来源记录附 `quality` 评分与 `evidence_level` 证据等级（hotspot_sources 表新增 `quality_json`/`evidence_level` 列）。四个路由阈值（升级分 55、免抓摘要 800 字、兜底摘要 200 字、README 最少 200 字）统一在 `config.local.json` 的 `sourceFetch` 段配置（默认值见 `lib/core/config.mjs`）；评分权重与拦截词表在 `lib/domain/source-quality.mjs` 内。事件内精选深抓（每事件 2～3 个代表来源）尚未实施，验证与推进计划见 `docs/event-deep-fetch-and-fact-base-plan.md`。

### 验收标准

- 热点全景中的每个事件都有独立、可追溯的事件摘要。
- 摘要能明确区分已确认事实、媒体主张、作者观点和待核内容。
- 热词综述引用事件卡，不再只依赖报道标题。
- 抓取结果可显示内容质量和证据等级。
- 300 条级别批次不需要对全部链接调用 Firecrawl。
- 同一事件的多来源增量和分歧可以在事件卡中查看。

### 启动条件

- 模型调用和 Firecrawl 额度足以支持事件级事实提取测试。
- 先选取一个真实批次建立质量基线，对比旧热词综述与新事件卡。
- P0 验收后再决定是否进入 P1、P2，避免先投入复杂抓取基础设施却没有改善总结质量。
