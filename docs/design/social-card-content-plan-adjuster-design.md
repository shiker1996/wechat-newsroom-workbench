# Social 图文内容计划调整器实施方案

## 1. 结论

当前流程并不是“AI 不够强”，而是 AI 介入得太晚：故事板生成后，页面结构基本被冻结，渲染失败时只能做构图回退、间距调整和受限的文字缩写/扩写。因此它无法稳定达到技能生成结果中那种“内容计划和页面承载同时合适”的效果。

本方案新增一个“内容计划调整器”（Content Plan Adjuster）。它不是另起一套图文生成链路，而是在现有故事板和模板渲染之间增加一个可审计的计划编排层：

```text
素材 / 事实基座
  ↓
语义故事板：决定讲什么
  ↓
内容原子化：把事实拆成可移动、可拆分、可合并的内容单元
  ↓
内容计划调整器：结合模板容量安排页面如何承载
  ↓
确定性预检
  ↓
模板 HTML 渲染 + 浏览器布局审计
  ↓
根据审计结果再次调整内容计划
  ↓
最终文字微调和交付
```

核心目标是让 AI 在“页面结构和内容分配”层面参与，而不是只在最后修改几段文字；程序仍然负责事实边界、模板能力、操作合法性和最终像素门禁。

文章主题、文章生成链路和封面主题不在本方案范围内。

## 2. 当前流程与问题

### 2.1 当前流程

```text
事实基座
  ↓
AI 生成 card_plan
  ↓
模板容量静态预检
  ↓
必要时拆分可拆内容块
  ↓
HTML 渲染
  ↓
浏览器布局审计
  ├─ 结构溢出：程序拆页 / AI split_page
  ├─ 内容不足：舒展排版 / AI 扩写已有文字
  └─ 文字过密：AI 缩写已有文字
```

现有链路已经具备以下能力：

- 故事板按 `cover`、`concept`、`feature`、`steps`、`evidence`、`risk` 等角色组织页面。
- 模板角色声明 `supportedBlocks`、`maxBlocks`、`maxItems` 和部分容量 profile。
- `social-card-reflow` 可以对列表、步骤、时间线、对比表等结构化块进行确定性拆页。
- 浏览器布局审计可以识别 `overflow`、`clipped`、`underfilled`、`text_too_small` 等问题。
- 当前已经增加同一故事板分组的过短续页合并，作为内容不足的第一步修复。

### 2.2 当前流程的根本限制

#### 限制 A：故事板只知道结构上限，不知道真实承载高度

故事板提示词能看到“最多几个内容块、几个条目”，但无法准确感知主题的字体、行高、边框、阴影、内边距、卡片间距叠加后的实际高度。因此“数量合法”不等于“渲染后好看”。

#### 限制 B：布局修复阶段结构被冻结

现有 AI 布局修复被限制为：

- 只能修改已有文字；
- 不能增加内容块或列表条目；
- 不能合并页面；
- 不能移动内容块；
- 不能改变页数、页序和页面角色。

这对事实安全是稳妥的，但当页面本身规划不合理时没有解决路径：过多只能缩写，过少只能扩写同一段文字。

#### 限制 C：内容不足和内容溢出没有统一的内容计划层

当前“拆页”由结构门禁触发，“扩写/缩写”由文字门禁触发，两者没有共同的数据模型，也无法把相邻页面重新编排成更均衡的计划。

## 3. 与内容计划调整器的区别

| 维度 | 当前流程 | 内容计划调整器流程 |
|---|---|---|
| AI 介入时机 | 故事板生成一次，失败后才做文字修复 | 故事板之后、渲染之前和审计失败后都可调整计划 |
| AI 负责内容 | 页面标题、内容块和文字 | 页面主题、内容原子、页面分配、结构操作和文字 |
| 页面结构 | 生成后基本冻结 | 可在受控范围内合并、拆分、移动和补充 |
| 内容不足 | 调大间距，扩写已有段落 | 先合并页面，再从事实基座补充合适内容，最后扩写 |
| 内容过多 | 拆页或缩写文字 | 先移动/拆分原子块，再缩写局部文字 |
| 模板信息 | 主要提供块数和条目数 | 提供角色、可用高度、目标利用率、可拆类型和操作限制 |
| 事实安全 | 通过故事板结构门禁保护 | 每个内容原子和新增块都绑定事实来源引用 |
| 终止条件 | 固定若干轮文字修复 | 每轮计划操作都校验并重新审计，达到门禁即停止 |

两者不是“让 AI 随意改页面”的区别，而是把 AI 的工作对象从“几段字符串”提升为“可验证的内容计划”。

## 4. 目标数据模型

### 4.1 保留现有 `card_plan`

现有 `card_plan` 继续作为渲染器和编辑器的兼容输入，不要求历史图文迁移。内容计划调整器内部增加中间层，最终仍编译为 `card_plan`。

### 4.2 内容原子（Content Atom）

将故事板内容拆成可追踪的最小事实单元：

```json
{
  "id": "atom-steps-install",
  "type": "step",
  "text": {
    "title": "安装",
    "content": "在 AI 代理中粘贴安装命令，或运行 npx 命令。"
  },
  "source_refs": ["README:How to install"],
  "priority": "core",
  "can_split": false,
  "can_move": true,
  "can_merge": false
}
```

原子必须具备：

- 稳定 ID；
- 内容类型；
- 来源引用；
- 是否允许拆分、移动、合并；
- 核心程度；
- 原始文本和当前文本版本。

这样 AI 可以建议“把步骤 2 移到下一页”，但不能凭空生成一个没有 `source_refs` 的步骤。

### 4.3 模板容量合同

在现有 capacity profile 上补充可供计划器使用的字段：

```json
{
  "role": "steps",
  "visual": {
    "bodyHeightPx": 406,
    "targetUtilization": [0.58, 0.88],
    "minUtilization": 0.50,
    "maxUtilization": 0.94,
    "maxTitleLines": 3,
    "maxTextLines": 8,
    "maxItemLines": 3
  },
  "structural": {
    "maxBlocks": 4,
    "maxItems": 9
  },
  "split": {
    "allowed": true,
    "blockTypes": ["steps", "list", "text"],
    "preserveAtomicItem": true
  },
  "operations": {
    "mergeContinuation": true,
    "moveBlock": true,
    "addFactBlock": true
  }
}
```

`targetUtilization` 是计划目标，不是硬门禁；最终仍以浏览器审计为准。

### 4.4 受控计划操作

AI 不直接返回 HTML 或完整任意 `card_plan`，而是返回结构化操作：

```json
{
  "operations": [
    {"op": "merge_pages", "pages": [6, 7], "reason": "同一快速上手故事线，P7 只有注意事项"},
    {"op": "split_block", "page": 3, "block": 0, "groups": [[0, 1, 2], [3, 4, 5]]},
    {"op": "move_block", "from_page": 5, "to_page": 6, "block": 1},
    {"op": "add_fact_block", "page": 4, "slot_id": "output", "source_refs": ["README:Usage"], "block": {"type": "note", "title": "输入输出", "content": "来源支持的补充说明"}},
    {"op": "rewrite_text", "page": 4, "block": 0, "mode": "compress"}
  ]
}
```

操作约束：

- `merge_pages` 只能合并相邻、同故事板分组或同主题页面；
- `split_block` 必须覆盖全部原子，不得遗漏或重复；
- `move_block` 只能移动完整原子块，不得截取半个事实；
- `add_fact_block` 必须引用事实基座中存在的来源；
- `add_fact_block` 如携带 `fact_ids`，必须能回指候选事实及其来源；
- `rewrite_text` 只能改变表达，不得改变事实含义；
- 封面和结尾页默认不可被普通内容计划操作影响；
- 所有操作执行后都要重新进行结构、事实和布局校验。

## 5. 目标运行流程

### 阶段 A：生成语义故事板

故事板 AI 继续负责：

- 选择故事线；
- 决定每页的主题和角色；
- 识别事实来源；
- 生成初始内容块。

但输出时同时生成内容原子和来源引用，不再把一整段文字当作不可解释的字符串。

### 阶段 B：首次内容计划调整

程序把以下信息传给内容计划调整器：

- 事实基座和来源引用；
- 初始语义故事板；
- 当前主题和模板包；
- 各角色容量合同；
- 目标页面数和页面上限；
- 当前页面的预计利用率。

AI 只需要决定“哪些内容放在哪一页”，而不是生成 HTML 或 CSS。

随后由确定性编译器把操作应用到 `card_plan`。

### 阶段 C：确定性预检

程序检查：

- 页面数量是否在范围内；
- 每页角色和模板是否匹配；
- 内容块和条目是否超出结构上限；
- 所有原子是否都被保留；
- 所有原子是否至少有一个来源引用；
- 是否存在重复、遗漏或非法操作；
- 静态估算利用率是否落入目标区间。

预检不通过时，优先生成新的受控操作，不直接进入文字改写。

### 阶段 D：浏览器真实审计

渲染后继续使用现有 `layout-audit.mjs`。审计结果按优先级处理：

#### 内容过多

1. 同组续页合并检查是否误合并；
2. 移动完整内容块；
3. 拆分列表、步骤、时间线或对比表；
4. 只缩写超出的文本；
5. 最后才调整间距或构图，正文不得低于 11px。

#### 内容不足

1. 合并相邻同主题续页；
2. 从同一事实基座补充已有示例、限制、配置或操作步骤；
3. 将同组页面的内容重新均衡分配；
4. 最后扩写已有段落。

#### 结构异常

结构异常仍由程序优先处理，AI 只能返回受控结构操作。不能拆分时，不再重复调用无效的 `split_page`，而是进入内容计划调整或明确提示用户修改故事板。

### 阶段 E：最终文字微调

只有页面结构已经稳定、内容利用率接近目标区间时，才调用现有 AI 文本修复：

- `compress`：去除重复和赘述；
- `expand`：补足事实基座已有的细节；
- 禁止新增来源、列表项和内容块；
- 每次修改后重新审计。

## 7. 分阶段实施

### 阶段 0：基线与可观测性

- 记录每次生成的原始故事板、最终计划、模板容量、浏览器报告；
- 统计页面不足、页面过载、拆页、合并和文字修复的真实比例；
- 为每个页面记录 `page_group_id`、角色、块数、条目数和利用率；
- 不改变现有生成行为。

验收：能够回答“某页为什么被拆、为什么被合并、哪次修复改变了什么”。

### 阶段 1：内容原子和来源引用

- 故事板输出规范化内容原子；
- 旧 `card_plan` 无来源字段时由程序生成兼容原子；
- 增加原子守恒、来源引用和重复检测；
- 不开放 AI 新增事实。

验收：任何计划调整后，原子总数和来源边界可复算。

当前已实施：

- 新增 `social-card-content-atoms.mjs`，为结构化条目和普通内容块生成稳定原子 ID；
- 优先读取条目级、内容块级和页面级 `source_refs`；旧故事板缺少引用时使用明确的 `legacy:...` 兼容标记；
- 生成链路输出 `social-card-content-atoms.json`，同时记录原始计划、有效计划、来源覆盖和原子校验结果；
- 故事板契约和三类内置故事板 Prompt 已加入 `source_refs` 字段要求；
- 不修改历史 `card_plan` 的展示和渲染行为，也不允许通过原子层新增事实。

### 阶段 2：确定性计划编排

- 把现有拆页和续页合并统一为计划编排器；
- 增加相邻页面的块移动和同组均衡；
- 先用静态容量预检，浏览器审计做最终确认；
- 不调用 AI，先验证程序能解决多少真实案例。

验收：候选 820 类似案例中，过短续页减少，事实不丢失，页面利用率提升。

当前已实施：

- `social-card-reflow.mjs` 将拆页后的续页均衡和过短续页合并统一纳入 `rebalanceContinuationPages`；
- 同组相邻内容页在硬容量校验通过时，可按原始顺序移动完整内容块，支持前页向续页或续页向前页两种方向；
- 移动、拆分、合并均写入计划操作记录，保留页码、角色、估算高度和续页元数据，浏览器审计仍是最终门禁；
- 该阶段不调用 AI、不改写文本、不删除事实，单元测试覆盖正向/反向块移动、续页合并和原子顺序保持。

### 阶段 3：AI 受控计划调整

- 增加 `social-card-content-planner` 用途；
- AI 只返回受控操作，不返回 HTML/CSS/完整任意故事板；
- 程序校验后才应用操作；
- 每次调整后重新编译和审计。

验收：AI 可以在不改事实的前提下完成合并、拆分、移动和基于来源的补充。

当前已实施：

- 新增 `social-card-content-planner` 契约和 JSON Schema，模型只返回 `split_page`、`move_block`、`merge_pages`、`add_fact_block` 四类操作；
- 结构修复策略扩展为顺序可回放的受控操作执行器，统一校验页面角色、故事线、操作数量、页面上限和内容块安全边界；
- 所有操作在应用前执行来源引用守恒校验；补充内容块必须引用已登记的事实来源，禁止 HTML/CSS/脚本等字段；
- Prompt 明确禁止完整故事板、任意代码、事实删除和无来源新增，未产生安全操作时允许返回空操作；
- 目前仍保持独立契约与程序校验，尚未把 AI 调整器自动接入整组生成主循环，接入和编辑器记录留在阶段 4。

#### `add_fact_block` 扩展：第一步（已实施）

本步只落地“事实补充槽位契约”，不接入事实索引、候选事实筛选或自动填充调用：

- 新增 `social-card-supplement-slots.mjs`，按 `concept`、`feature`、`steps`、`data`、`compare`、`evidence`、`timeline`、`risk` 声明允许的补充槽位；封面和结尾页不开放槽位；
- 每个槽位声明 `id`、展示名、允许的内容块类型、条目上限和优先级，作为角色级合同，不把模板的 CSS/坐标暴露给 AI；
- `add_fact_block` JSON Schema 现在必须携带 `slot_id`，可选 `slot_label`；程序校验角色、槽位、内容块类型、条目上限和 `supplement_slot_id` 标记一致性；
- 模板能力目录和 capacity profile 会向故事板/计划器提示可用槽位；自定义模板未声明时继承角色默认槽位；
- 应用后的新增块保留 `supplement_slot_id`，便于后续事实填充、审计和撤销；
- 事实来源仍必须来自已登记 `source_refs`，本步不允许无来源新增，也不改变现有生成链路的自动调用时机。


#### `add_fact_block` 扩展：第二步（已实施）

- 新增 `social-card-fact-index.mjs`，将仓库、事件和自定义事实基座规范化为带稳定 ID、文本、标签、来源和优先级的候选事实；未核实主张不会进入候选；
- 按“页面角色 + 槽位 + 内容块类型”执行确定性候选排序，候选结果会进入内容计划调整器 Prompt，但不把原始事实对象全部暴露给模型；
- `add_fact_block` 支持 `fact_ids`，程序会确认候选存在、候选来源被携带且来源仍在事实基座登记；
- 当页面审计为 `underfilled`、AI 没有返回安全操作时，程序可从当前角色的高优先级槽位选择候选事实，生成一条有来源的补充操作；
- 自动补充仍受页面角色、模板块类型、块数上限、槽位条目上限和原子守恒校验约束；封面、结尾页和无来源候选不会被补充；
- 生成产物新增 `social-card-fact-index.json`，并在内容计划调整记录中保留 `fact_ids` 和来源，便于回放和排查。

本步仍不允许模型编造事实，也不把自动补充升级为无限扩写；候选不足时继续走原有人工修改提示。

#### `add_fact_block` 扩展：第三步（已实施）

- 生成产物通过 `social-card-fact-index.json` 保存候选事实快照，图文列表和故事板编辑接口同时返回该索引，便于回放“候选事实 → 补充块 → 来源”的完整链路；
- 内容计划调整记录保留轮次、目标页、操作来源（AI 内容计划、程序自动补充、程序结构修复）、`slot_id`、`fact_ids` 和 `source_refs`，故事板界面以可读标签展示这些信息；
- 故事板编辑器在补充块上显示槽位、事实候选数和来源数；保存本页或切换内容块类型时，程序继续携带 `supplement_slot_id`、`fact_ids`、`source_refs`，不丢失溯源元数据；
- 本步只增加可观测性、回放和编辑保护，不改变候选筛选、自动补充上限或布局审计门禁。

### 阶段 4：接入生成链路和编辑器

- 生成整组图文时自动执行内容计划调整；
- 布局失败时展示“内容计划调整记录”，而不是只展示“AI 改写”；
- 故事板页面显示页数变化、被移动的内容块和来源；
- 单页重新生成复用同一调整器，但限制在目标故事板分组内。

验收：用户可以理解页面为什么变化，也可以在故事板中继续人工调整。

当前已实施：

- 整组生成的浏览器审计失败后，先执行确定性重排，再调用 `social-card-content-planner`，最后才进入文字微调；
- AI 调整结果经程序校验后重新编译模板计划、写回故事板并重新渲染/审计；
- 每轮调整记录目标页、操作、校验结果、重编排操作和最终页数，最多 3 轮、每轮最多 4 个操作；
- 生成产物新增 `social-card-content-plan-adjustments.json`，同时纳入计划基线、模板指标和候选产物清单；
- 失败时不回退旧模板，错误信息明确区分内容计划调整失败和后续文字修复失败。

### 阶段 5：灰度和默认切换

- 先对 `clean-v1` 和 `editorial-v1` 灰度；
- 对 `brutalist-v1`、`neon-v1` 使用更保守的容量和操作预算；
- 比较旧链路和新链路的成功率、平均页数、利用率、事实变更数和修复轮次；
- 新链路稳定后，将文字修复降为最后兜底。

当前已实施：

- 新增 `social-card-plan-rollout.mjs`，为 `clean-v1`、`editorial-v1` 建立灰度档案，为 `brutalist-v1`、`neon-v1` 建立更保守的计划轮次、操作数和结构重排预算；未知模板保留兼容档案，不改变文章/封面链路。
- 生成链路读取模板档案，内容计划调整和浏览器结构预检使用同一组预算；文字修复最多执行档案规定的轮次，并继续作为最后兜底。
- `social-template-metrics.json`、`social-card-content-atoms.json` 和 `social_template_metrics` 统一记录计划调整轮次、拆分/合并/移动/补事实操作、平均利用率、来源原子损失和 rollout 档案。
- 新增 `buildSocialCardPlanRolloutReport`，按模板与灰度模式比较成功率、页数、利用率、溢出率、计划/文字修复轮次；样本不足、事实原子损失、成功率下降或溢出率上升时禁止扩大灰度。
- 数据库迁移版本升至 v10，旧库通过幂等列补丁自动补齐新增指标字段；阶段 5 专项测试覆盖策略档案、推广门槛和指标落库。

## 8. 门禁与失败处理

### 8.1 不允许的操作

- 删除核心事实；
- 新增未在事实基座中出现的事实；
- 通过缩小正文、隐藏溢出或空白卡规避审计；
- 修改封面标题事实、页面顺序或内容角色；
- 用合并操作跨越不同故事线；
- 让同一内容原子同时出现在两页。

### 8.2 操作轮次

建议将计划调整和文字修复分开计数：

- 计划调整最多 3 轮；
- 每轮最多 4 个结构操作；
- 文字微调最多 2 轮；
- 同一计划哈希或同一审计签名重复出现时立即停止；
- 最终失败报告记录最后一个可解释的计划版本和建议人工修改页。

这样可以避免无限调用 AI，也避免当前“结构问题没有路径却反复尝试文字修复”的情况。

## 9. 用户交互调整

第一版不新增一个必须点击的“内容计划调整”按钮。生成整组图文时自动执行，并在进度中显示：

```text
内容计划检查：P6/P7 合并
内容计划检查：P3 列表拆为两页
内容计划检查：P4 从事实基座补充 1 个限制说明
浏览器审计：通过
```

在故事板编辑器中增加可展开的“计划调整记录”：

- 原页数 / 新页数；
- 合并、拆分、移动和补充的页面；
- 每个新增内容的来源；
- 调整前后利用率；
- 撤销本次自动调整并恢复原计划。

用户仍然可以直接编辑故事板；自动调整不会覆盖人工修改后的事实内容。

## 10. 验收标准

### 事实与结构

- 所有核心事实原子均保留或有明确人工删除记录；
- 不产生无来源的新增事实；
- 页面角色、页序和故事线关系保持合法；
- 结构操作可完全回放和撤销。

### 视觉与布局

- 无 `overflow`、`clipped`、横向溢出和正文过小；
- 内容页利用率优先落在模板目标区间；
- 同组续页不出现单独承载一个短 note 的空页，除非合并后确实会溢出；
- 合并后页面仍保持主题构图和层级关系。

### 生成效果

- 图文成功率高于当前文字修复链路；
- 平均修复轮次下降；
- 页面总数不会因保守拆页无故增加；
- 与技能生成的内容密度和页面均衡度接近；
- 失败时能明确告诉用户是事实不足、模板容量不足还是故事板结构不足。

## 11. 最终建议

这次改造不应继续扩大“AI 缩写/扩写本页”的权限，而应把它降级为最后一步。真正需要新增的是一个受模板容量约束、以事实原子为输入、以浏览器审计为反馈的内容计划调整器。

这样可以保留当前系统的事实安全和程序门禁，同时获得技能生成链路的关键优势：在内容计划阶段解决页面如何承载，而不是等 HTML 已经失败后才修改文字。
