# 能力接入配置化与开发规范化方案

状态：已实施完成（阶段 1-4，2026-08-14）  
日期：2026-08-14  
上游文档：consumer-capability-adaptation-design.md（阶段 0-6 已实施）、consumer-capability-expansion-design.md（阶段 A-D 已实施，含 §9 接入清单）  
现状汇总：能力拓展的操作视图见 [capability-expansion-guide.md](./capability-expansion-guide.md)（2026-08-15）

## 1. 背景：五种情形的现状

消费者接入一项能力的成本，取决于两个变量：**能力是否已在目录**、**消费者类型**。现状矩阵：

| 情形 | 现状 | 当前路径 |
|---|---|---|
| S1 技能 + 已有能力 | ✅ 已配置化 | skill.json 声明 + 白名单放行（页面可开关） |
| S2 Agent + 已有纯参数能力 | 🟡 半配置化 | 改三个文件（能力常量、登记、Manifest），无适配逻辑，页面不可操作 |
| S3 Agent + 已有资源类能力 | ❌ 需开发 | 六件清单（§9.2，阶段 A 已实战验证） |
| S4 任意消费者 + 新能力 | ❌ 需开发 | 先定义能力（目录+实现+威胁模型），再走 S1/S2/S3 |
| S5 添加全新能力 | ❌ 开发为主 | 目录定义 + 插件实现；远程 API/MCP 可经扩展工作室 Manifest 半配置化接入，但目录登记仍需改文件 |

另有一个顺序规则缺口（2026-08-14 核实）：设计顺序是"先定义能力 → 再提供实现 → 最后消费者接入"，消费者侧已被门禁强制，但**实现侧存在宽容通道**——插件可声明目录外能力，系统以 `registered: false` 占位（`capability-catalog.mjs:17`），导致能力能被实现却不能被正经消费的半吊子状态。

## 2. 目标：配置化分级

不搞"一切皆可页面"的一刀切。按工作性质分四级，每种情形归到合理的最低级：

| 级别 | 含义 | 归宿情形 |
|---|---|---|
| L0 页面配置 | 页面上完成，不写文件 | S1、S2（均已达成，2026-08-14） |
| L1 登记文件 | 改 config/ 下 JSON 即生效，无代码 | S5 的远程实现接入（目录草案确认入库） |
| L2 接线开发 | 按固定清单接线，无新组件设计 | S3（已达，六件清单） |
| L3 新能力立项 | 目录定义 + 实现 + 安全评估，单独立项 | S4/S5 的能力定义部分 |

判定原则（沿用上游方案第一原则）：**配置只表达声明与授权，不制造适配与调用**。凡是涉及资源语义、业务结果解释、调用点的，保留开发通道；凡是通用层已覆盖的，收敛到 L0。

## 3. 核心机制一：能力生命周期状态机

把"先定义后实现再消费"落成显式状态机，作为所有情形的公共框架：

```text
draft（草稿/未登记）
  ↓ 目录定义（capabilities.json 条目，含名称/描述/分类/风险级别）
registered（已定义）
  ↓ 至少一个实现通过健康检查且被允许启用
implemented（可提供）
  ↓ 消费者登记 + 适配就绪 + 技能授权
consumable（可消费，按消费者逐个计算）
```

规则：

- **R1 消费者门禁（已有）**：消费者登记/技能 Manifest 引用非 registered 能力 → 审计报错或警告。维持不变。
- **R2 实现侧收口（新增）**：`registered: false` 的能力的实现允许存在（调试期宽容），但**不得启用、不得设为路由首选**；图谱与页面标注"未登记 · 仅调试"。从调试转生产必须先补目录条目。
- **R3 目录草案辅助（新增）**：远程工具 Manifest 导入时，若声明了目录外能力，校验通过后在响应中生成**目录条目草案**（从 Manifest 的 capabilities + description 推导），用户确认后写入 `capabilities.json`——把 S5 的目录登记从手写 JSON 降为确认操作（仍是 L1，需人工确认，不自动入库）。
- **R4 门禁新增（新增）**：图谱存在 `registered: false` 能力 → `check-consumer-capability-gates.mjs` 输出 warning（不阻断，CI 可见）。

## 4. 核心机制二：Agent 目录登记驱动（S2 配置化的关键改造）

现状：Agent 工具目录由 Adapter 代码常量（`*_AGENT_CAPABILITIES`）决定，登记文件只做一致性校验。这是 S2 无法页面化的唯一结构性原因。

改造：**权威反转为登记驱动**。

- Adapter 目录构建从 `capability-consumers.json` 的登记依赖派生（保留常量作为启动期一致性校验：常量 ⊆ 登记，超集报错——常量此后只表达"本 Adapter 有适配代码的能力上界"）；
- 纯参数能力无需适配代码，因此不在常量上界约束内：登记了即生效；
- 资源类能力仍受常量上界约束：登记了但常量未含 → 页面显示"缺少适配"，与现状语义一致。

安全性：一致性校验从"双向相等"放宽为"纯参数能力允许登记超出常量"，其余不变；阶段 0 的快照测试继续锁运行时行为。

## 5. 各情形的目标路径

### S1 技能 + 已有能力（维持 L0，补一处入口统一）

- 现状已配置化，不改机制。
- 页面"添加能力"入口与 S2 共用：技能卡片的候选 = 目录中该技能未声明的纯参数能力；操作 = 写 skill.json 声明 + 白名单放行（一次完成，替代现在"改文件 + 开开关"两步）。
- resourceId 类能力不出现在技能候选中（安全边界：技能单独运行无适配层）。

### S2 Agent + 已有纯参数能力（目标 L0）

- 前提：机制二（登记驱动）落地。
- 页面：Agent 卡片增加"添加能力"入口，候选 = 目录中本 Agent 未声明、且非资源类的能力；操作后服务端写登记 + 同步 skill.json +（如该 Agent 常量约束收紧）更新常量校验豁免。
- 即时生效：新会话目录即包含该能力；历史 run 快照不受影响（既有冻结机制）。

### S3 Agent + 已有资源类能力（维持 L2，规范化已达标）

- 六件清单（§9.2）已是固定路径，阶段 A 验证过工作量。不改。
- 可选增强（不排期）：默认适配档案——页面声明时按登记的 resourceKinds/triggerPolicy 套默认档案（标准资源注册、标准门禁、结果一律进【素材】的最保守边界），先跑起来再代码精化。此增强依赖机制二，且需为每种 resourceKind 定义默认档案 Schema，建议等第二次资源类接入需求出现时再做。

### S4 消费者 + 新能力（拆为 S5 + S1/S2/S3）

- 无独立路径。方案约束：任何"想要新能力"的需求必须先走 S5 立项，再回到对应消费者路径。文档与页面引导明确这一点，避免把新能力诉求误当接入诉求。

### S5 添加全新能力（L3 定义 + L1 实现接入）

- 能力定义：永远 L3 人工立项（目录条目 + 风险级别 + 威胁模型评估），但 R3 的目录草案辅助把远程场景的文件编写降为确认操作。
- 实现接入：
  - 远程 API/MCP：扩展工作室 Manifest 导入（已有）+ R2 收口（未登记不得启用）+ R3 草案；
  - 本地插件：管理员安装（已有），受 R2 同样约束。

## 6. 页面改动汇总

1. **能力页签**：未登记能力（`registered: false`）单独分区，标注"未登记 · 仅调试"，附目录草案引导（远程来源的）。
2. **消费者页签**：Agent/技能卡片增加"添加能力"入口（候选=未声明的纯参数已登记能力）；资源类未适配能力保持锁定提示不变。
3. **扩展工作室**：远程 Manifest 校验结果中，目录外能力给出"生成目录条目草案 → 确认入库"的操作流。

## 7. 分阶段实施

```text
阶段 1：顺序规则收口（R2 + R4 + R3）
  1.1 registered:false 实现禁止启用/禁止首选路由（registry 启用校验 + 路由校验）
  1.2 门禁 R4 warning；能力页签未登记分区
  1.3 远程 Manifest 导入的目录草案生成与确认入库
  验收：目录外能力的实现无法被启用；草案确认后能力进入 registered

阶段 2：Agent 目录登记驱动（机制二）
  2.1 Adapter 目录从登记派生；常量降级为适配代码上界校验
  2.2 一致性校验放宽（纯参数能力允许登记超出常量）+ 快照测试适配
  2.3 全量回归（阶段 0 快照安全网）
  验收：不改 Adapter 代码，仅改登记即可让纯参数能力进入 Agent 目录

阶段 3：页面添加入口（S1 统一 + S2）
  3.1 服务端写入接口：登记 + Manifest 同步（复用授权写入的版本机制与 dryRun 影响预览）
  3.2 Agent/技能卡片"添加能力"交互；候选过滤（排除资源类、排除已声明）
  验收：S1/S2 全程页面完成；门禁零违规；历史快照不受污染

阶段 4：收尾
  4.1 更新上游两份方案文档状态与 §9 清单（S2 从半配置化改记 L0）
  4.2 基线重跑；API.md 同步
```

顺序理由：阶段 1 是规则修正，独立且小，先行防止口子扩大；阶段 2 是结构性反转，风险最高（动运行时目录构建），放在快照安全网之上单独做；阶段 3 依赖 2 的登记驱动，纯增量。

## 8. 测试与验收清单

- R2：registered:false 实现启用被拒、设首选被拒，页面标注正确；
- R3：目录外能力的远程 Manifest 导入产出草案，确认后入库且门禁转绿；
- 机制二：仅改登记文件即让某 Agent 多出纯参数能力（测试模拟）；常量超出登记仍报错；
- S1/S2 页面添加：版本协商、影响预览、409 回退复用既有语义；resourceId 能力不出现在候选；
- 全程全量 npm test 0 失败（基线 1021）；npm run capability:gates 零违规。

## 9. 明确边界

- 不做 S3 的默认适配档案（等第二次资源类接入需求再评估）；
- 能力定义（目录条目 + 威胁模型）永远保留人工环节，不做全自动入库；
- 不改变技能单独运行时不可用 resourceId 能力的安全边界；
- 不改 pipeline-runtime 快照冻结语义；
- feature 消费者的"页面声明接入意图"（gaps 化）不在本方案，维持登记文件操作。
