# 流程节点级模型配置方案（评审稿）

## 1. 目标与范围

在不改变现有业务 Agent、Skill 契约、程序化渲染和已有门禁行为的前提下，将以下流程节点纳入独立模型配置范围：

> 采集、打标、事件卡、研判、编辑室、成稿、排版、封面、图文分析、故事板生成、图文生成

本文作为评审与实现基线；配置接口、系统配置页、运行时路由和生成快照记录已按本文方案实施。

核心目标不是让每一次模型调用都换一个模型，而是把现有流程中具有不同吞吐特征、不同质量要求、不同失败代价的调用分组，使模型选择可解释、可回放、可独立调优。

## 2. 现状判断

当前大多数生成任务仍以一次运行绑定一个 `provider/model`。阶段和子技能可以不同，但模型通常由整次运行共用。

不过，业务代码中的“流程节点”并不等于“单次模型调用”：

- 采集主路径由采集插件完成，只有字段补齐和候选排序可能调用模型。
- 研判同时包含稳定事件解析、事件卡、事件研究、脑暴和综合复排，其中部分是确定性程序。
- 成稿包含事实基座、规划、写作、标题、改写、审稿、SEO 和多个质量门禁。
- 排版默认主路径是确定性渲染，但自动主题和设计方案生成仍可能调用模型。
- 封面标准模式是主题编译和截图；AI 视觉封面是另一条模型驱动路径。
- 图文生成同时包含文案生成、内容计划调整、布局修复和确定性 HTML/截图。

因此，配置设计必须同时保留“用户看到的 11 个流程节点”和“节点内部真正需要单独路由的子环节”。

## 3. 拆分依据

每个环节是否独立配置模型，按以下五个维度判断：

### 3.1 吞吐量

是否面向全量热点、全量候选或批量页面执行。全量、高并发、可缓存的任务优先使用高速低成本模型。

### 3.2 推理深度

是否需要多步因果分析、反证、跨来源比较、观点取舍或长上下文整合。推理深度高的环节使用高能力模型。

### 3.3 输出风险

模型输出是否会决定事实边界、选题方向、作者立场、文章结论或发布合规。越接近最终发布，错误代价越高，越需要高质量模型和严格门禁。

### 3.4 调用形态

是否存在联网搜索、原生工具调用、长上下文、结构化 JSON、短文本改写或视觉 HTML/CSS 生成。调用形态不同，不能只按“文本生成”统一配置。

### 3.5 是否本来就是确定性程序

如果环节已经由脚本、编译器、渲染器、截图器或门禁完成，则不应为了“支持模型配置”而引入模型。模型配置只能作用于该环节实际存在的模型调用。

## 4. 11 个节点及子环节划分

### 4.1 采集

| 子环节 | 当前性质 | 划分依据 | 建议配置键 |
|---|---|---|---|
| 来源插件采集 | 程序化/外部接口 | 不属于模型能力，不配置模型 | `collection.fetch` |
| 字段补齐 | 可选短 JSON 调用 | 单页候选少、输出短、吞吐高 | `collection.field-enrichment` |
| 候选排序 | 可选短 JSON 调用 | 只做相对排序，错误可回退确定性排序 | `collection.candidate-ranking` |

结论：采集节点整体应以程序化为主；两个可选模型子环节归入高速低成本档位。

### 4.2 打标

| 子环节 | 当前性质 | 划分依据 | 建议配置键 |
|---|---|---|---|
| 全量语义标注 | LLM 批量调用 | 覆盖全部有效热点，支持分块和并发 | `tagging.semantic` |
| 失败条目重试 | LLM 重试调用 | 输入小、目标是恢复结构化输出 | `tagging.retry` |
| 结果字段写入和完整性检查 | 程序化 | 只做字段校验和持久化 | 不配置模型 |

结论：打标是典型的高吞吐、低到中等推理任务。默认不使用高能力模型；重试可以沿用同一模型，也可以单独设置更稳定的模型。

### 4.3 事件卡

| 子环节 | 当前性质 | 划分依据 | 建议配置键 |
|---|---|---|---|
| 事件摘要与事实卡生成 | LLM 批量调用 | 按事件分块生成，可缓存、可增量补齐 | `event-card.generate` |
| 事件卡结构化校验 | 程序化 | 负责字段、来源和分类格式检查 | 不配置模型 |
| 单事件重试 | LLM 重试调用 | 只修复无效或失败事件 | `event-card.retry` |

结论：事件卡比打标需要更完整的事实整理，但仍然是批处理任务，建议使用高速或平衡模型，不与深度研判共用高档模型配置。

### 4.4 研判

研判是模型配置最需要独立出来的节点之一，但内部不能只用一个配置覆盖所有调用。

| 子环节 | 当前性质 | 划分依据 | 建议配置键 |
|---|---|---|---|
| 稳定事件解析、聚类、热度计算 | 程序化 | 需要可复算和守恒，不应受模型波动影响 | 不配置模型 |
| 单事件深度研究 | LLM，可能联网搜索 | 需要事实补充、机制、影响和分歧分析 | `research.event-analysis` |
| 事件间关系研究 | LLM，可能联网搜索 | 需要跨事件比较和关系推断 | `research.inter-event` |
| 研究结果验证 | LLM，可能联网搜索 | 需要核验来源和边界，错误代价较高 | `research.verify` |
| 选题脑暴 | LLM 批量调用 | 需要角度和反证，但输入已被裁剪 | `research.brainstorm` |
| 全局综合复排 | LLM | 需要跨候选竞争、受众和重复判断 | `research.synthesis` |

结论：研究、验证和综合复排使用高质量模型；脑暴可以使用平衡模型。程序化评分、排序和守恒逻辑不参与模型配置。

### 4.5 编辑室

| 子环节 | 当前性质 | 划分依据 | 建议配置键 |
|---|---|---|---|
| 编辑问题回答 | 交互式 LLM | 面向人类编辑，需理解上下文和历史讨论 | `editorial-room.chat` |
| 研究点选择建议 | LLM + 程序化约束 | 会影响最终文章命题和证据范围 | `editorial-room.research-selection` |
| 编辑简报整理 | LLM/程序化混合 | 输出会锁定成稿输入和作者立场 | `editorial-room.brief` |
| 简报状态、字段和并发门禁 | 程序化 | 负责锁定和持久化 | 不配置模型 |

结论：编辑室属于低吞吐、高上下文、高决策风险任务，建议固定使用高质量模型。它不应与批量打标共用模型配置。

### 4.6 成稿

成稿是最终发布链，建议作为高质量模型节点；但其内部调用仍按职责区分。

| 子环节 | 当前性质 | 划分依据 | 建议配置键 |
|---|---|---|---|
| 事实基座 | LLM 结构化调用 | 决定文章允许使用的事实范围 | `drafting.fact-base` |
| 文章规划 | LLM 结构化调用 | 决定文章结构、核心命题和标题方向 | `drafting.planning` |
| 初稿生成 | LLM 长文本调用 | 影响正文质量和表达 | `drafting.body` |
| 初稿质量门禁与事实修订 | LLM + 程序化扫描 | 影响事实和合规风险 | `drafting.draft-gate` |
| 标题生成 | LLM 结构化调用 | 需要传播性，但事实风险也高 | `drafting.title` |
| 去 AI、审稿、SEO | LLM | 直接影响发布文本 | `drafting.review`、`drafting.seo` |
| 终稿门禁和发布合规 | LLM + 程序化扫描 | 发布前最后防线 | `drafting.final-gate` |
| 图表/配图规划 | LLM 结构化调用 | 需要理解正文，但不应改写正文事实 | `drafting.visual-plan` |

结论：初期可以让上述子环节共享一个高质量模型配置，保留子键是为了以后针对成本和稳定性单独优化，不要求第一版全部独立暴露到 UI。

### 4.7 排版

排版必须明确区分“排版节点”和“排版中的模型调用”。

| 子环节 | 当前性质 | 划分依据 | 建议配置键 |
|---|---|---|---|
| Markdown 预渲染 | 程序化 | 脚本执行 | 不配置模型 |
| Mermaid/ECharts/统计卡/时间线转图 | 程序化 | 图表渲染和图片登记 | 不配置模型 |
| 设计方案与 Tokens | LLM | 只生成视觉参数，不应改写正文 | `typeset.design` |
| HTML 初稿 | 默认程序化 | 默认 `deterministic` 路径直接拼装 HTML | 不配置模型 |
| HTML 模型初稿 | 可选旧路径 | 仅 `draftMode=llm` 时使用 | `typeset.html-llm` |
| 样式内联和 HTML 门禁 | 程序化 | 浏览器计算和确定性检查 | 不配置模型 |

结论：`typeset` 默认配置为 `deterministic`。只有 `typeset.design` 和显式启用的 `typeset.html-llm` 需要模型配置，不能因为排版存在一个设计调用，就把整个排版节点改成模型驱动。

### 4.8 封面

| 子环节 | 当前性质 | 划分依据 | 建议配置键 |
|---|---|---|---|
| 标准主题选择 | 程序化或自动主题 LLM | 固定主题映射可复算，`auto` 可能请求模型 | `cover.theme-routing` |
| 标题语义分析 | 可选 LLM | 只提取高亮词和视觉母题 | `cover.semantic-analysis` |
| 标准封面构图、HTML、截图 | 程序化 | 主题编译器固定生成 | 不配置模型 |
| AI 视觉封面 Agent | LLM/工具调用 | 另一条视觉生成路径，失败边界不同 | `cover.ai-visual` |

结论：标准封面默认不需要高质量模型；AI 视觉封面单独配置，不能与标准封面混用一个“封面模型”概念。

### 4.9 图文分析

| 子环节 | 当前性质 | 划分依据 | 建议配置键 |
|---|---|---|---|
| 事件图文深度分析 | LLM 结构化调用 | 需要从事件事实和来源提炼机制、影响、分歧 | `graphic-analysis.event` |
| 仓库事实复用/自定义事实整理 | 主要程序化 | 当前主要读取已有事实基座 | `graphic-analysis.facts`（默认 `deterministic`） |
| 分析结果事实门禁 | 程序化 | 检查事实、来源和故事板前置条件 | 不配置模型 |

结论：图文分析不能与普通打标合并。事件分析质量要求较高，但只处理候选事件，不是全量高吞吐任务。

### 4.10 故事板生成

| 子环节 | 当前性质 | 划分依据 | 建议配置键 |
|---|---|---|---|
| 故事线和页面职责规划 | LLM/编辑输入 | 决定页面顺序、叙事关系和信息承载 | `storyboard.plan` |
| 内容块事实绑定 | LLM + 程序化校验 | 需要保持事实守恒和来源绑定 | `storyboard.fact-binding` |
| 模板感知重排、拆页、合页 | 程序化 | 受页面容量和模板契约约束，必须可复算 | 不配置模型 |
| 页面容量、重复、结构门禁 | 程序化 | 防止溢出、重复和丢事实 | 不配置模型 |

需要注意：现有图文生成链会读取已经形成的 `card_plan`，并对其做程序化重排和审计。因此“故事板生成”和“图文生成”在业务上相邻，但不能把程序化重排误认为模型生成。

### 4.11 图文生成

| 子环节 | 当前性质 | 划分依据 | 建议配置键 |
|---|---|---|---|
| 配套文案 | LLM | 面向发布渠道，要求事实边界和表达质量 | `graphic-generation.copy` |
| 内容计划调整 | 可选 LLM | 只允许在页面容量内补充或移动内容 | `graphic-generation.content-plan` |
| 布局文字修复 | 可选 LLM | 只改已有内容文字，不得改变结构和事实 | `graphic-generation.layout-repair` |
| HTML/CSS 渲染 | 程序化 | 模板渲染器完成 | 不配置模型 |
| 截图、浏览器审计、交付门禁 | 程序化 | 输出尺寸、溢出和交付检查 | 不配置模型 |

结论：图文生成默认使用平衡模型生成文案；内容计划和布局修复可以使用更快模型，但必须继续受现有程序化校验约束。

## 5. 第一版配置粒度

页面不直接要求用户逐个配置 11 个节点或所有子环节，只配置四个质量档位。节点到档位的映射由运行时按本方案维护：

```json
{
  "modelProfiles": {
    "fast": "provider-id",
    "balanced": "provider-id",
    "quality": "provider-id",
    "deterministic": "deterministic"
  }
}
```

运行时内部将采集字段补齐、打标、事件卡等批量环节映射到 `fast`，研判、编辑室、成稿和图文分析映射到 `quality`，故事板和图文文案映射到 `balanced`，排版主链路映射到 `deterministic`。必要的子环节仍保留独立稳定 ID，但第一版不做成公开 UI。

内部保留以下高级覆盖位，不在普通配置页暴露：

```json
{
  "stageModelOverrides": {
    "research.verify": "quality",
    "drafting.final-gate": "quality",
    "graphic-generation.layout-repair": "fast",
    "collection.field-enrichment": "fast"
  }
}
```

解析优先级建议为：

```text
子环节配置 > 一级节点配置 > 任务级默认模型 > 系统默认模型
```

其中 `deterministic` 不是 provider，而是明确表示该环节不得调用模型。

## 6. 快速、平衡、高质量三档的使用边界

### fast

适合采集字段补齐、候选排序、打标、事件卡、简单布局修复等任务。特点是批量、短输出、可重试、错误有程序化回退。

### balanced

适合脑暴、故事板初步规划、图文配套文案、视觉设计 tokens 等任务。需要一定理解能力，但不直接决定最终事实结论。

### quality

适合事件深度研判、研究验证、综合复排、编辑室、成稿、终稿审查和 AI 视觉封面等任务。特点是调用次数少、上下文长、错误代价高。

### deterministic

适合采集插件、事件聚类、评分、排版渲染、截图、模板重排、HTML 门禁和事实字段校验。不应通过模型配置覆盖成 LLM 调用。

## 7. 快照、重试与兼容原则

为避免同一任务重试时模型发生漂移，运行快照需要记录每个实际执行子环节的 provider 和 model，而不只是记录一个全局模型。

```json
{
  "stageModelsResolved": {
    "tagging": { "provider": "...", "model": "..." },
    "research.event-analysis": { "provider": "...", "model": "..." },
    "drafting.body": { "provider": "...", "model": "..." },
    "typeset.design": { "provider": "...", "model": "..." },
    "typeset.html-llm": null
  }
}
```

兼容原则：

1. 旧任务只有一个模型快照时，继续按旧的全局模型执行。
2. 新配置未指定子环节时，继承一级节点或任务级默认模型。
3. 已存在的 Skill 选择、工具授权、门禁、重试和业务 Agent 输入输出保持不变。
4. 不通过模型名称转换、工具注入或业务 Agent 分支来实现兼容；模型差异只由运行时路由层处理。
5. 没有模型调用的程序化子环节不生成虚假的模型记录。

## 8. 建议评审重点

本方案需要重点确认三件事：

1. 11 个一级节点是否符合实际业务认知，尤其是“图文分析 / 故事板生成 / 图文生成”的边界。
2. 第一版是否只开放一级节点配置，还是同时开放 `typeset.design`、`cover.ai-visual`、`graphic-generation.layout-repair` 等少量子节点。
3. 配置值是直接填写 provider/model，还是先使用 `fast / balanced / quality / deterministic` 逻辑档位，再由系统映射到具体模型。

在这三点确认前，不建议开始改运行时路由和 UI，避免配置粒度再次反过来影响现有业务流程。
