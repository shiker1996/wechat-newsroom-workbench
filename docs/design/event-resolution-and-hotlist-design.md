# 事件归并与事件热榜设计

状态：设计提案，尚未实施  
日期：2026-08-23  
相关现状：[架构总览](../architecture.md)、`lib/llm/research-pipeline.mjs`、`lib/domain/hotspot-atlas.mjs`

## 1. 背景与结论

当前系统已经能把多条热点报道聚成“主体动态”“横向对比”“场合盘点”等维度组，但维度组同时承担了三件不同的事：

1. 判断多条报道是不是同一件事；
2. 组织事件之间的关系；
3. 直接生成文章候选。

这会产生两个问题：

- 同一事件因模型生成的 `what` 不同而被拆成多个事件；
- 维度组的规模和主体活跃度影响排名，导致同一主体连续占位。

例如张丹丹“灵活就业是福利”的多条报道，本质上是同一场争议，但当前不同批次分别出现了不同的 `eventKey`，随后又被“张丹丹近期动态”重新聚在一起。主体聚合掩盖了事件去重不足。

本方案的核心结论是：

> 先把报道归并为稳定的事件，再识别事件增量并生成事件热榜；主体、动作、场合维度组只作为事件热榜之上的观察和选题组织方式。

目标流水线：

```text
采集
  → 批次内事件聚类
  → 跨批次事件身份归并
  → 事件增量识别
  → 事件热榜（T：事件价值）
       ├─→ 维度组/关系图（早报与观察）
       └─→ 账号契合校验
             → 读者利益校验
             → 综合研判（F：文章成稿价值）
             → 文章选题池
```

## 2. 目标与非目标

### 2.1 目标

- 同一件事在热榜中只占一个事件位；
- 同一事件的多个报道、来源和后续进展可追溯；
- 区分“新事件”“同一事件新进展”“持续讨论”和“旧闻复述”；
- 跨日保留稳定事件身份，支持热度衰减和历史重复判断；
- 维度组建立在去重后的事件之上，不再承担事件去重职责；
- 热榜排名和文章选题排名分离，避免热点主体固定占文章池席位；
- 保留人工合并、拆分和纠错入口。

### 2.2 非目标

- 不在本阶段重写已有文章和候选内容；
- 不把同一主体的所有新闻强行合成一个事件；
- 不把同一行业趋势、同一产品线或同一公司自动判成同一事件；
- 不用热榜分数替代文章的爆点、账号契合、读者利益和证据门禁。

## 3. 核心概念

### 3.1 报道（hotspot）

采集器得到的一条原始热点记录，仍然保留在现有 `hotspots` 表中。它是事件的证据和来源，不是热榜排名的最终单位。

### 3.2 事件（event record）

一个可被编辑部单独描述、跟踪和排名的现实事件。例如：

> 张丹丹“灵活就业是福利”言论引发争议

事件下面可以挂原始发言、媒体评论、当事人回应和事实补充。

### 3.3 事件进展（event update）

同一事件的新事实或新阶段，例如正式回应、删文、处罚、新数据、新来源。进展不会新建热榜事件，但会提高事件的新鲜度和增量分。

### 3.4 维度组（dimension group）

对多个已归并事件的组织视角：

- `who`：同一主体的多个不同事件；
- `what`：多个主体的同类动作或对象；
- `where`：同一场合或会议下的多个事件。

维度组可以生成聚合文章候选，但不直接作为事件热榜的排名单位。

## 4. 数据模型改造

当前事件聚类主要是运行时从 `hotspots.raw_json.aiTags.eventKey` 计算，无法稳定跨批次复用。建议增加持久化事件层。

### 4.1 `event_records`

| 字段 | 说明 |
|---|---|
| `id` | 稳定事件 ID，跨批次不变 |
| `canonical_key` | 规范事件指纹 |
| `title` | 当前规范标题 |
| `who` | 核心主体 |
| `action_type` | 粗粒度核心动作分类，仅用于匹配特征和动作维度分组 |
| `object` | 作用对象或议题对象 |
| `first_seen_at` | 首次出现时间 |
| `last_seen_at` | 最近出现时间 |
| `last_update_at` | 最近一次有事实增量的时间 |
| `status` | `active / cooling / stale / merged` |
| `confidence` | 事件身份置信度 |
| `event_state` | `new_event / new_update / continuing / stale` |
| `legacy_ids_json` | 旧批次 `E...` ID 映射，兼容历史产物 |

### 4.2 `event_hotspots`

事件与报道的归属关系单独持久化：

| 字段 | 说明 |
|---|---|
| `event_id` | 稳定事件 ID |
| `hotspot_id` | 现有热点 ID |
| `batch_id` | 报道所属批次 |
| `relation` | `primary / duplicate / update / correction` |
| `match_method` | `exact / structured / semantic / manual` |
| `match_confidence` | 匹配置信度 |
| `is_new_information` | 是否带来新事实 |
| `created_at` | 归属建立时间 |

同一条热点允许被修正，但默认只能归属一个主事件，避免报道在热榜中重复计数。

### 4.3 `event_updates`

用于保存事件进展摘要：

| 字段 | 说明 |
|---|---|
| `event_id` | 稳定事件 ID |
| `update_key` | 进展指纹，防止同一进展重复写入 |
| `update_type` | `new_fact / new_response / new_source / duplicate` |
| `summary` | 增量摘要 |
| `source_hotspot_ids_json` | 支撑该进展的报道 |
| `novelty_score` | 新信息分 |
| `first_seen_at` | 首次发现时间 |

如果不希望第一阶段引入独立表，也可以先将 `event_updates` 放进事件产物 JSON；但跨日热度和人工修正最终仍需要持久化。

## 5. 事件归并算法

归并采用“确定性优先、模型裁决兜底”的分层策略，不再直接使用自由文本 `who|what` 作为唯一事件身份。

### 5.0 算法输入与输出

每次处理一个批次时，算法输入分为两部分：

**当前报道输入**：

- 当前批次的有效 `hotspots`；
- `aiTags.eventParts`、关键词、标题、摘要、来源和发布时间；
- 当前批次内已经完成的初步聚类结果。

**历史事件输入**：

- 最近 14 天的 `event_records`；
- 历史事件的规范主体、对象、动作、标题和最近进展；
- 已归属的热点集合及其来源。

算法输出不是一个简单的分组数组，而是三类结果：

```text
resolvedEvents       当前批次涉及的稳定事件
memberships          报道 → 事件的归属关系
reviewQueue          无法安全自动判断的候选合并/拆分
```

每个 `membership` 必须带上匹配方法、置信度和是否为新信息，保证结果可解释、可回放。

### 5.1 第 0 层：确定性规范化

从现有标注提取并规范化：

- 主体名称：别名、英文名、公司简称归一；
- 动作：使用 `actionType` 枚举；
- 对象：去除形容词、数量和标题噪声；
- 时间：使用事件发生月份或更细时间窗口；
- 地区：作为筛选属性，不单独决定事件身份。

初步匹配指纹（不是最终事件 ID）：

```text
normalized(who) + normalized(actionType) + normalized(object) + timeWindow
```

这里的 `actionType` 只是匹配特征，不能单独决定“是不是新事件”。同一事件的报道可能分别被标成“其他”“争议回应”或“产品更新”，仍需结合主体、对象、触发事实和时间窗口判断。

规范化至少包含以下规则：

| 字段 | 规范化规则 |
|---|---|
| `who` | 小写、去公司后缀和标点、应用别名表；例如 `Moonshot AI` 与 `月之暗面` 映射到同一实体 |
| `object` | 去数量、情绪词和泛化后缀；保留产品、议题或赛道核心名 |
| `what` | 拆出“触发事实”与修辞，不直接把整句标题作为指纹 |
| `actionType` | 映射到固定枚举；只作为辅助特征 |
| `when` | 统一到事件发生日/月和时间窗口，不使用抓取时间替代事件时间 |
| 标题/摘要 | 分词、实体抽取、数字和关键短语保留；用于后续相似度计算 |

规范化结果建议保存为中间结构：

```json
{
  "whoKey": "zhangdandan",
  "objectKey": "灵活就业社保",
  "triggerKey": "灵活就业是福利言论",
  "actionType": "争议回应",
  "timeWindow": "2026-08",
  "entityKeys": ["张丹丹", "灵活就业", "社保"]
}
```

### 5.2 第 1 层：结构化候选匹配

当两个事件满足以下条件时进入同事件候选：

- `who` 相同或属于已知别名；
- `object` 高度相似；
- 动作相同或属于同一争议/回应链；
- 时间窗口接近；
- 标题或摘要存在相同事实实体。

这一步用于合并张丹丹三种不同 `what` 表述，避免依赖模型是否恰好输出相同措辞。

#### 候选召回（blocking）

不能让每条报道和全部历史事件两两比较。先按以下任一条件召回最多 50 个候选事件：

1. `whoKey` 相同；
2. `objectKey` 相同；
3. 共享至少一个高信息量实体或关键词；
4. 标题/摘要的实体集合有明显交集；
5. 当前事件来自历史事件的同一来源或同一 URL。

候选召回只负责“不要漏掉可能的同事件”，不负责最终合并。

#### 结构化匹配分

对每个候选事件计算确定性分数：

```text
M = 30 × whoMatch
  + 25 × objectMatch
  + 20 × triggerMatch
  + 10 × actionCompatibility
  + 10 × timeCompatibility
  +  5 × entityOverlap
```

各分量取 0–1：

- `whoMatch`：规范主体相同为 1，别名为 0.9，否则为 0；
- `objectMatch`：规范对象相同为 1，同义/父子对象为 0.7，否则为 0；
- `triggerMatch`：触发事实相同或标题事实短语高度重合；
- `actionCompatibility`：同动作为 1，兼容动作（如“发布”→“争议回应”）为 0.6，冲突动作为 0；
- `timeCompatibility`：同一事件窗口内为 1，跨 1 个窗口为 0.5，明显不相容为 0；
- `entityOverlap`：人物、产品、政策、地点等实体交集比例。

建议阈值：

| 分数 | 处理 |
|---:|---|
| `M >= 82` | 自动归并到已有事件 |
| `65 <= M < 82` | 进入语义裁决或人工复核 |
| `M < 65` | 不自动归并，作为新事件候选 |

阈值不是永久常量，第一阶段应通过历史样本校准；安全原则是宁可暂时拆开，也不要把两个独立事件强行合并。

### 5.3 第 2 层：语义裁决

对结构化相似但不能确定的候选，调用轻量事件归并判断，只回答：

```json
{
  "sameEvent": true,
  "confidence": 0.92,
  "reason": "同一发言争议的不同评论与回应",
  "updateType": "new_source|new_fact|new_response|duplicate"
}
```

模型只负责判断事件身份和增量类型，不负责决定热榜分数。

语义裁决输入必须同时包含“当前报道”和“候选事件摘要”，而不是只把两条标题丢给模型：

```text
当前报道：标题、摘要、来源、发布时间、结构化 eventParts
候选事件：规范标题、首次/最近时间、已有事实、已有报道标题
要求：判断是否同一现实事件；如是，判断是重复来源还是新进展
```

模型结果还要经过确定性门禁：

- 模型说“同事件”，但 `who` 完全不匹配时拒绝自动合并；
- 模型说“新进展”，但没有新的事实实体、时间、数字或来源时降为 `continuing`；
- 模型置信度低于 0.75 时进入 `reviewQueue`；
- 模型输出不得直接覆盖人工已经确认的合并/拆分关系。

### 5.4 新事件与事件进展判定

事件身份确认后，才判断本次报道属于哪种状态：

| 状态 | 含义 |
|---|---|
| `new_event` | 找不到已有事件身份，创建新事件 |
| `new_update` | 已有事件出现新事实、新回应、新决定或新数据 |
| `continuing` | 同一事件仍有讨论，但没有实质增量 |
| `stale` | 旧闻复述、换标题或低增量转载 |

该状态不能复用 `actionType`。例如“回应”“质疑”“断章取义”通常是同一事件中的报道角色或进展类型，不应因为措辞变化而创建新事件。

对已匹配到事件的报道，再计算增量判定：

```text
newFact = 新实体/新数字/新决定/新时间节点/新官方来源
newResponse = 当事人、机构或监管方首次回应
newSource = 新的独立来源，但没有新事实
duplicate = 标题改写、转载或同事实复述
```

判定优先级：

1. 有新决定、回应、数字或明确时间节点 → `new_update`；
2. 只有新的独立来源 → `continuing`，增加来源扩散但不增加事件数量；
3. 事实和实体均无变化 → `stale` 或 `duplicate`；
4. 发现原事件归并错误 → 进入拆分复核，不直接新建孤立事件。

### 5.5 可执行伪代码

```text
resolveBatch(batch):
  reports = loadEligibleHotspots(batch)
  normalized = normalizeReports(reports)
  currentClusters = clusterWithinBatch(normalized)
  history = loadRecentEventRecords(days=14)

  for cluster in currentClusters:
    candidates = recallCandidates(cluster, history, currentResolvedEvents)
    scored = candidates.map(candidate => deterministicMatch(cluster, candidate))
    best = max(scored, by=matchScore)

    if best.score >= 82:
      event = attach(cluster, best.event, method=best.method)
    else if best.score >= 65:
      decision = semanticJudge(cluster, best.event)
      if decision.sameEvent && decision.confidence >= 0.75:
        event = attach(cluster, best.event, method='semantic')
      else:
        reviewQueue.add(cluster, best.event, decision)
        event = createProvisionalEvent(cluster)
    else:
      event = createNewEvent(cluster)

    updateType = classifyUpdate(cluster, event)
    saveMemberships(cluster.hotspotIds, event.id, updateType)
    saveEventUpdate(event.id, cluster, updateType)

  assertHotspotConservation(batch)
  return { resolvedEvents, memberships, reviewQueue }
```

### 5.6 张丹丹示例

以下报道应该先通过候选召回进入同一比较组：

```text
北大张丹丹教授能不能主动去享受灵活就业的“福利”？
你的颠沛流离，成了张丹丹教授口中的“特殊福利”
张丹丹失言背后，真问题是谁来缴社保
谁在断章取义张丹丹，断了什么章取了什么义？
```

结构化结果虽然 `what` 文案不同，但共享：

```text
who：张丹丹
object：灵活就业/社保
trigger：灵活就业是福利相关言论
timeWindow：2026-08
```

因此归并为一个稳定事件；前三条可能是 `duplicate` 或 `new_source`，如果出现正式回应或新的社保事实，再生成 `new_update`。热榜只给这个事件一个排名。

### 5.7 人工修正层

提供合并和拆分操作：

- 合并事件：选择主事件、迁移热点关系、重建事件卡；
- 拆分事件：把错误归并的报道移到新事件；
- 标记误报：保留报道，但从事件热榜和文章研判中排除。

人工操作需要写审计记录，不能静默覆盖模型结果。

## 6. “同一事件”与“同一主体”的边界

以下情况应视为同一事件：

- 同一次发言引发的不同评论；
- 同一次发布的不同媒体报道；
- 同一争议的官方回应、删文和事实补充；
- 同一收购或人事变动的后续报道。

以下情况仍应拆成不同事件：

- 同一公司当天降价和收购两件事；
- 同一主体不同产品的独立发布；
- 同一行业内不同公司的融资；
- 同一争议结束后，数月后重新发生的新事件。

主体聚合只能把这些不同事件放在同一主体下展示，不能替代事件归并。

## 7. actionType 词典治理

当前 `actionType` 保持有限枚举：

```text
发布、开源、融资、收购、裁员、诉讼、合作、获奖、政策、
人事、产品更新、研究突破、争议回应、其他
```

它只回答“这条事件主要是什么动作”，用于动作维度分组和匹配辅助，不回答“这是新事件还是旧事件”。

新增枚举必须同时满足：

1. 在多个批次中反复出现；
2. 与现有动作有稳定、可解释的边界；
3. 能提供正例和反例；
4. 对编辑分组或文章组织有实际价值；
5. 经过人工样本验证后分类稳定。

“评论”“质疑”“后续”“复述”等更适合放进 `update_type` 或报道角色，不应扩充为新的 `actionType`。

## 8. 事件热榜生成

事件归并完成后，对 `event_records` 排名。热榜分数建议拆开显示，不使用不可解释的单一分数：

| 分量 | 含义 |
|---|---|
| 新鲜度 | 距最近事实增量的时间 |
| 增量 | 新事实、新回应、新数据数量 |
| 来源扩散 | 独立来源和来源类型数量 |
| 传播动量 | 最近窗口内新增报道速度 |
| 影响范围/公共相关度 | 事件对覆盖人群、国内市场或公共议题的客观关联；不读取账号定位 |
| 证据完整度 | 可核验来源和事件卡完整程度 |
| 历史衰减 | 已连续出现但无新事实的扣分 |

建议输出：

```json
{
  "eventId": "EVT-...",
  "rank": 1,
  "eventValue": 82,
  "t": 82,
  "noveltyScore": 68,
  "state": "new_update",
  "reportCount": 4,
  "sourceCount": 3,
  "newReportCount": 2,
  "firstSeenAt": "2026-08-22T11:20:00Z",
  "lastUpdateAt": "2026-08-23T08:10:00Z",
  "repeatDays": 2,
  "reason": ["出现正式回应", "新增 2 个独立来源"]
}
```

现有接口中的 `heatScore` 在迁移期保留为兼容别名；四层方案正式以 `eventValue/T` 表示事件热榜分，避免与文章阶段的最终 `F` 或历史表现 `H` 混淆。

同一事件可以因为新进展重新升温，但不会因为换了 3 个标题就获得 3 个热榜位置。

## 9. 维度组和文章选题的关系

### 9.1 维度组不参与事件热榜排名

事件热榜排名单位是事件。维度组保留独立的 `groupScore`，用于发现文章组织方式：

- 主体近期动态；
- 同类动作横向对比；
- 同一场合盘点。

`groupScore` 不能与 `heatScore` 混用，也不能因为主体有很多报道就直接获得固定文章席位。

### 9.2 文章选题使用四层单向筛选

四层是由宽到窄的连续筛选，不是四个相互独立的总分，也不允许后层重新改写前层的事实判断：

```text
全量稳定事件
  → L1 事件价值 T：是否值得进入今日观察范围
  → L2 账号契合：是否值得由本账号承接
  → L3 读者利益：是否能说明具体读者为什么要关心
  → L4 成稿价值 F：在可承接、可解释的候选中，哪一个最值得现在写
```

#### L1：事件价值 T（事件层初筛）

T 是事件热榜的主排序分，只回答“这个事件现在是否值得继续看”，不读取账号定位，也不因为某个账号偏好而改变事件热榜名次。

输入只允许来自事件及其历史轨迹：热度和传播动量、最近事实增量、独立来源与证据完整度、影响范围、时效、新旧事件状态、跨日重复和过时衰减。输出事件热榜、排名理由和候选宇宙边界（默认前 50 个稳定事件）。

T 不负责标题吸引力、账号栏目匹配、通知资格或文章写作质量。T 高只表示“值得进入下一层”，不承诺最终一定成为文章。

#### L2：账号契合（账号层校验）

账号契合只回答“这个事件是否属于本账号应该承接的内容范围”，输入为冻结的 `account-context.json`：读者画像、内容支柱、账号定位、作者资产和长期栏目方向。

输出结构化的 `accountFit`（内容支柱命中、承接理由、探索项标记和必要的素材条件），用于：

- 在 T 已通过的候选中排序同分项或设置轻量优先级；
- 标记“适合本账号”“可探索”“不建议承接”；
- 为后续文章包装提供内容支柱，不直接制造热度。

账号契合不能再次计算事件热度，也不能替代读者利益。原有 `accountFitBonus` 与最终评分中的 P 必须基于同一份账号契合结果，不能先加一次 `+6`、最终再以 P 重复加分。

#### L3：读者利益（受众层验证）

读者利益只回答“具体读者会因为这个事件改变什么判断、决策或行动”。必须结构化为：目标读者、变化对象、可能动作，以及工作/收入/岗位/效率/成本/选择等具体后果，并记录事实依据和不确定性。

输出两个结果但只使用一套判断：

- `readerStakeScore`：作为文章 B 中的受众相关性输入，只计算一次；
- `readerStake`：可读解释，并作为通知池的硬门槛和推荐/实验池分流依据。

读者利益不参与事件热榜排序，不因为“开发者直接影响”给 T 额外加分；这类信号应在本层转化为具体后果。没有具体读者后果的候选可以保留观察或实验状态，但不能仅凭主体知名度进入高优先级通知。

#### L4：成稿价值 F（文章层终筛）

F 只在前三层通过后计算，回答“在今天真正可承接、可解释的候选中，哪一个最值得写”。F 必须以 L1 的事件价值 T 为底座，但不能把 T 里的热度、时效和增量再次拆进文章分；否则会出现“事件热榜一遍、文章评分又一遍”的重复计分。

先计算不含事件价值的文章化质量 `A`：

```text
A = H × 60% + B × 25% + P × 15%
F = A × 70% + T × 30% − S − D
```

其中：

- `H`：历史表现与题材基线；
- `B`：角度独特性、情绪/传播性、标题钩子、`readerStakeScore`、事实支撑；
- `P`：L2 账号契合的最终分值映射，不再另设一套“业务偏好”加分；
- `S`：全局同题饱和度；
- `D`：同一事件、同一论点和跨日重复修正。

默认 `T` 权重为 30%，作为迁移期配置项校准；T 只进入 F 一次，且已经在 L1 之外的候选不会被 F 重新“救回”。F 负责最终文章榜、成稿门槛和编辑会排序，不反向改变事件热榜的 T，也不因维度组规模、主体知名度或固定分类配额强行抬分。默认 `F < 55` 不进入文章选题池；若所有候选都低于门槛，只保留最高分作为人工参考并明确标记。

#### 四层之间的单向约束

- T 高但账号契合低：可以留在事件热榜，但不优先作为本账号文章；
- T 高、账号契合高但读者利益不具体：可以做观察或实验，不进入通知池；
- T 中等但前三层通过、角度和证据突出：只要位于候选宇宙内，仍可由 F 排到前面；
- F 低不能反向降低事件热榜 T，只说明“事件值得看，但当前不值得按文章写”；
- 维度组只在 L1 之后作为早报/观察组织方式，不参与事件 T，也不绕过 L2–L4 占用文章席位。

## 10. 热点全景 UI 改造

热点全景采用两个可切换 Tab：

1. **事件热榜**：默认视图，显示前 50 条排名、状态、热度分、增量和来源；完整排名保留在接口中，避免一次铺开数百条事件；
2. **事件全景**：承载主体/维度视图与 `who/what/where` 关系图，用于查看报道覆盖和发现横向选题。

两个 Tab 共用国内/国外、来源数、关键词等筛选条件，避免把“按热度排序”和“按关系观察”误认为同一排名。

事件卡需要提供：

- 事件规范标题（由主体、动作、对象、触发事实或事件描述确定性生成，不直接采用报道标题）；
- 报道和来源列表；
- 新增事实摘要；
- 首次出现和最近增量时间；
- 历史批次覆盖；
- “进入文章研判”按钮；
- 合并/拆分/标记误报入口。

现有国内/国外、来源数、关键词筛选应作用于事件热榜、关系图和维度列表三者，而不是只作用于顶部统计。

## 11. 流水线实施方案

### 阶段 0：影子运行与双写准备

这一步必须先于正式切换，避免把归并误差直接传递给热榜和文章池：

- 保留现有 `clusterItems(eventKey)` 作为兼容基线；
- 新增 resolver 以影子模式运行，只生成 `event-resolution-shadow.json`，不改变现有排名和选题池；
- 对当前批次同时输出旧聚类、新归并和差异清单：自动合并、自动拆分、待复核、未归属；
- `event_records/event_hotspots/event_updates` 先采用幂等双写，所有记录带 `resolver_version` 和 `algorithm_version`；
- 新增 `triggerKey`、规范化实体和匹配解释等字段时，保留旧 `eventKey/eventParts`，保证旧接口和历史产物可读；
- 连续观察至少 2–3 个批次后，再决定是否开启正式热榜消费。

影子阶段的最低门禁：有效热点守恒率 100%；人工抽样确认的自动合并不能出现明显跨事件误合并；所有低置信度结果必须可追溯到 `reviewQueue`，不能静默丢失。

### 阶段 A：事件身份与归并基座

- 增加 `event_records`、`event_hotspots`；
- 保留现有 `E...` 作为 `legacy_event_id`；
- 实现结构化规范化和确定性匹配；
- 对无法确定的匹配记录 `needs_review`，暂不自动合并；
- 增加张丹丹、同主体不同事件、同事件多来源测试夹具。

### 阶段 B：历史回填与事件卡迁移

- 回填最近 7–14 个批次；
- 先处理高频主体和高重复事件；
- 回填先生成 dry-run 报告，人工确认合并/拆分后再提交正式归属；
- 生成合并报告：合并数量、待复核数量、拆分候选、未归属热点；
- 事件卡改用稳定 `event_record_id`；
- 校验报道守恒：每条有效热点必须有且仅有一个主事件归属。

### 阶段 C：事件热榜

- 新增 `event-heat-ranking.json` 产物；
- 在热点全景新增事件热榜区域；
- 增加新事件/增量/持续/过时状态；
- 排名使用确定性分数，模型只补充增量摘要和匹配解释；
- 记录历史排名和排名变化。

当前实现将总分固定为 100 分再扣历史衰减：新鲜度 25、事实增量 25、来源扩散 15、传播动量 15、影响范围/公共相关度 10、证据完整度 10，历史衰减最多扣 20。来源和报道先按稳定 `event_id` 聚合，当前批次一条事件只生成一条排名项；连续批次出现但 `is_new_information=0` 的事件进入 `continuing` 或 `stale`，不因换标题重新获得增量分。`event-heat-ranking.json` 同时保存 `previousRank`、`rankDelta`、各分项、来源/报道数、状态和可解释原因，便于编辑复核和后续用运营结果校准权重。

### 阶段 D：综合研判接入

- 文章池改为由 `selectArticlePool` 消费事件热榜前 50 个稳定事件，按 L1→L2→L3→L4 四层单向筛选；
- 维度组由 `selectBriefPool` 单独输出为早报/行业盘点候选，不再默认占用文章池席位；
- 文章候选和早报维度组分别保存来源关系与候选类型，避免把“主体近期动态”误当成文章题；
- 将 `duplicatePenalty` 和跨批次历史重复纳入文章评分；
- 修复综合候选在排行榜中的成员命中判断。

当前实现保留旧 `event-clusters.json` 和事件卡作为兼容产物，但在进入预选、维度池和脑暴前，将 `event-resolution-shadow` 投影成稳定事件簇：`event_id` 使用 `S...` 稳定 ID，报道成员仍保留原 `hotspot_id`，事件卡通过报道成员回挂。热榜元数据以只读字段传入文章候选（`eventHeatScore`、`eventHeatRank`、`eventHeatState`、`eventHistoryRepeatDays`），不替代 H/B/P/S/F。文章 F 评分新增 D 扣分：过时事件固定扣分，跨日重复出现按重复天数递增扣分；维度组若全部由过时事件组成则不再进入文章池。这样热榜负责“是否值得继续看”，文章评分仍负责“是否值得写”。

进一步明确文章池入口：常规文章预选只从事件热榜前 50 个稳定事件构成候选宇宙，再执行单事件核心 8 条和黑马 2 条竞争；热榜之外的事件保留在事件全景和完整排名中，但不直接占用当日文章池席位。维度组仍在同一候选宇宙内生成 `brief-pool.json`，供早报和行业盘点使用。热榜生成失败时才回退旧预选流程，并在进度与产物中留痕。

#### 11.4 四层研判改造

现有实现把 T、账号契合和开发者直接利益混在文章预选阶段，再由 F 进行第二次排序，容易出现同一信号重复计分或“前面筛掉、后面又救回”的口径冲突。本阶段改为严格的单向链路：

```text
稳定事件全量
  → 事件热榜 T（只判断事件价值，生成前 50 候选宇宙）
  → 账号契合 accountFit（只判断账号承接关系）
  → 读者利益 readerStake（只判断具体读者后果与分发资格）
  → 综合研判 F（只对通过候选做文章质量和竞争终筛）
  → 文章选题池
```

实施约束如下：

1. 事件热榜的 `T` 统一承接事件热榜的客观排名信号；移除账号内容支柱加分和“开发者直接利益 +4”等账号/受众专属信号。开发者成本、效率、接口和额度等词只能作为 L3 的待验证线索，必须转化为具体读者后果后才生效。
2. `accountFit` 由 `account-context.json` 的内容支柱、读者画像、作者资产和栏目方向计算，保留结构化理由。它可以用于 L1 通过候选的轻量优先级、探索项标记和 F 中的 P 映射，但不能在预选和 F 中重复叠加。
3. `readerStake` 必须同时产出 `readerStakeScore`、目标读者、具体决策/动作、后果和证据边界。`readerStakeScore` 只进入 B 的受众相关性一次；文字版用于通知池硬门槛和推荐/实验池分流，不单独增加总分。
4. F 改为“两段式”公式：先计算文章化质量 `A = H×60% + B×25% + P×15%`，再计算 `F = A×70% + T×30% − S − D`。其中 `P` 改为 L2 `accountFit` 的最终映射，B 的受众项改为 L3 的 `readerStakeScore`。删除独立的“业务偏好 P”来源，避免账号契合被计算两次。
   迁移期间页面仍可将现有 P 标为“业务偏好 P”；待 P 完成向 `accountFit` 的统一后，页面和报告统一改为“账号契合 P”，并保留字段迁移说明，避免历史批次产生歧义。
5. `F < 55` 只影响文章选题池，不回写事件热榜，也不改变事件的 T、事件身份或增量状态。所有被 L1 选入但 F 未达线的事件仍保留在事件热榜，可作为快讯、观察或后续增量跟踪。
6. 开发者直接利益保护位、工具工程最低席位等结构性约束只能发生在 L2/L3 之后的文章候选组合阶段，且必须记录为“组合约束”，不能伪装成 T 或 F 分数。

四层产物必须分别落盘，便于解释候选在哪一层被收窄：

| 产物 | 关键字段 | 用途 |
|---|---|---|
| `event-heat-ranking.json` | `eventValue/T`、分项、状态、增量理由 | 事件热榜和 L1 候选宇宙 |
| `account-fit.json` 或候选内 `accountFit` | 命中支柱、承接理由、探索项、素材条件 | L2 账号校验与 F 的 P 映射 |
| `reader-stakes.json` 或候选内 `readerStake*` | 读者、动作、后果、证据、通知资格 | L3 读者验证与分发分流 |
| `topics-ranked.md` / 候选记录 | H/B/P/S/D/F、终筛原因、L1→L4 路径 | L4 文章榜和编辑会审计 |

验收时必须能回答：候选是否进入热榜、是否通过账号契合、是否具备具体读者利益、最终 F 为何达标或未达标。不能只返回一个最终分数而丢失中间层结论。

#### 11.5 代码与数据改造清单

改造按“先统一 T，再接入 F，最后切换候选池”的顺序实施，避免中间版本同时存在两套事件价值口径：

1. **统一事件价值来源**
   - `lib/domain/event-heat-ranking.mjs` 将 `heatScore` 增加兼容别名 `eventValue`/`t`，事件热榜的分项成为 T 的唯一来源；
   - `lib/llm/research-pipeline.mjs` 的 `topicValueParts()` 不再重新叠加账号相关或开发者专属信号，候选的 `topicValue` 直接读取事件热榜 T；
   - `selectArticlePool()` 先按 T 构造候选宇宙，再把 `accountFit` 作为 L2 的结构化结果和轻量同分排序依据，不再使用 `T + accountFit` 伪装成新的事件分。
2. **把 T 接入 F，而不是只作为入围条件**
   - `scoreCards()` 接收候选的 `eventValue/T`，先计算 `articleValue=A`，再按 `eventValueWeight`（默认 0.30）计算最终 F；
   - `scoring.weights` 增加 `eventValueWeight` 配置和范围校验，迁移期间允许按批次实验 0.25–0.40；
   - 报告和候选记录同时保存 `T`、`A`、`H/B/P/S/D/F`，可以解释“事件很热但文章化不足”与“事件中等但角度优秀”的排名差异。
3. **统一账号契合和 P**
   - 将 `focusedCategories` 命中、作者资产、内容支柱和探索项整理为一个 `accountFit` 结果；
   - `P` 只从该结果映射，移除 `pBase` 作为独立业务偏好来源；
   - 删除预选阶段独立的 `accountFitBonus` 累加，保留必要的组合约束并单独记录。
4. **统一读者利益和 B 的受众项**
   - 在脑暴/综合输出中增加结构化 `readerStakeScore`，与读者、动作、后果、证据边界一起保存；
   - `scoreCards()` 的 B 受众项只读取该分值一次；`readerStake` 文字只负责解释和通知池门禁，不再额外加分；
   - 将“计费、价格、额度、接口、效率”等关键词从 T 的直接加分改为 L3 的线索，必须经过具体读者后果验证。
5. **调整候选持久化和前端说明**
   - `candidates` 增加 `event_value/T`、`article_value/A`，保留 `topic_value` 兼容字段，并保存 `f_score/F` 及分层淘汰原因；
   - 选题页同时展示 `T`、`A` 和 `F` 的含义，避免把 F 看成热榜分；
   - P 完成统一后，将页面文案从“业务偏好 P”迁移为“账号契合 P”，历史批次保留旧标签说明。
6. **测试与回放**
   - 新增高 T/低 A、低 T/高 A、重复事件高 D、无具体读者利益四类回放样本；
   - 验证 F 只能在 L1 候选宇宙内排序，不能让热榜外事件通过 F 进入文章池；
   - 对同一批次同时输出旧 F 与新 F，比较 T 权重变化、F<55 淘汰率、核心 8 条变化和通知池变化，确认没有因 T 重复计分导致热门大厂事件垄断。

### 阶段 E：人工校正与运营闭环

- 提供事件合并/拆分和误报处理；
- 统计人工修正率、重复事件率、跨日重复入池率；
- 分层统计 T 前 50 的事件有效率、账号契合承接率、读者利益具体化率、F 达标率和各层淘汰原因；
- 检查同一信号是否同时出现在 T、`accountFit`、`readerStakeScore` 和 F 中，发现重复计分立即回溯字段来源；
- 以最近 7 天运营结果校准热榜权重和文章池门槛。

当前第一轮实现先建立“审计层”，不直接改写自动归并结果：`event_resolution_decisions` 记录批次、稳定事件、校正类型（`merge`/`split`/`misreport`）、目标事件、涉及报道、原因、操作者和撤销时间。热点全景通过 `GET /api/batches/:id/event-resolution-review` 读取当前批次的合并/拆分/待复核差异，通过 `POST /api/batches/:id/event-resolution-decisions` 写入人工决定，DELETE 仅做软撤销；后续 resolver 才消费这些决定形成 override。

运营指标按最近 7 天（可调整窗口）确定性计算：

- `manualCorrectionRate = activeDecisions / (reviewQueue + merges + splits)`，没有待校正项时为 0；
- `duplicateEventRate = max(legacyEventCount - shadowEventCount, 0) / legacyEventCount`，用于衡量同批次重复事件被压缩的比例；
- `crossBatchRepeatPoolRate = 含稳定事件的重复入池候选 / 含稳定事件的候选`，只统计候选能映射到稳定事件的样本。

`GET /api/event-resolution-metrics?days=7` 返回总计、逐批次明细和最近人工决定。指标先用于编辑复核和权重实验，不自动改变热榜分数；累计至少 7 天并完成抽样复核后，再把人工决定转成 resolver override 并校准文章池门槛。

## 12. 兼容与验收

### 12.1 兼容原则

- 不删除现有 `hotspots`；
- 不重写历史候选 ID；
- 旧产物保留，新增稳定事件 ID 映射；
- 归并失败时回退为当前批次独立事件，不阻塞整批流程；
- 人工拆分优先级高于后续自动匹配。

### 12.2 必测场景

- 张丹丹三条报道跨两天归并为一个事件；
- 同一事件不同来源不重复占热榜名次；
- 同一事件出现正式回应时仍是一个事件，但状态变为 `new_update`；
- 同一主体的降价和收购保持两个独立事件；
- 过时事件热度衰减，不因主体聚合重新升高；
- 热榜筛选后关系图和维度组只展示筛选事件；
- 一个单事件进入文章池时生成普通候选，多事件才生成综合候选；
- 报道总数、事件成员数和来源数守恒；
- 合并/拆分可审计、可回滚。

## 13. 首批实施建议

首批不建议立刻重写所有评分。建议先完成三件事：

1. 建立稳定事件身份和跨批次热点归属；
2. 用张丹丹案例验证“同一事件只占一个热榜位”；
3. 在热点全景先上线事件热榜，暂时把现有文章选题池作为下游结果继续运行。

等事件热榜和历史归并稳定后，再调整 Anthropic/OpenAI 的主体重复惩罚、文章池席位和爆点评分。这样可以先解决“同一事件被拆开排名”的基础问题，再讨论编辑偏好和配额。
