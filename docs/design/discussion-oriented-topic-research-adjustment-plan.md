# 面向高讨论度选题的研判层改造方案

状态：阶段 0、阶段 1、阶段 2 已实施；事件内/事件间语义研判改为模型完成，程序只做范围裁剪与证据门禁；发布后效果复盘沿用公众号现有复盘数据，不在本流程单独记录
日期：2026-09-01  
关联设计：[四层选题筛选改造方案](./four-layer-topic-selection-refactor-plan.md)

## 1. 目标

在不改变事件热度 T、事件卡事实边界和成稿门禁的前提下，升级 T 排名之后的研判层，使系统能够从高热度事件中发现：

- 事件内部的反常、利益冲突和可发散方向；
- 事件之间的前后关系、回应关系、对比关系和趋势关系；
- 由上述关系形成的候选选题，而不是停留在事件摘要或新闻复述。

本方案解决的是“哪些高热度事件值得进一步组合和解释”，不是重新定义“什么事件热度高”。

目标链路：

~~~
全量热点
  → 轻量语义标注
  → 事件卡
  → 事件热度 T 排名
  → Top-K 深度研判范围
  → 模型事件内研判
  → 模型事件间关系研判
  → 模型候选选题生成
  → 候选选题级排序
  → 核心 8 + 黑马 2
  → 编辑会确认最终角度
~~~

## 2. 当前基础与问题

### 2.1 已有能力

当前系统已经具备：

- 全量热点的语义打标和事件卡；
- 稳定事件归并；
- 事件级 T 排名；
- 事件卡中的确认事实、来源增量、来源分歧、时间线和待核信息；
- who、what、where 维度分组；
- 文章候选的账号契合、读者利益、文章化质量和编辑会。

T 当前只回答“这个事件是否值得进入进一步分析”，不负责判断文章是否具有讨论度。

### 2.2 当前缺口

现有研判流程主要把事件作为独立候选处理，缺少四类中间产物：

1. **事件内反常**：预期与实际、宣传与结果、前后状态之间的落差；
2. **事件内冲突**：主体、利益相关方或叙事之间的真实分歧；
3. **事件间关系**：前后进展、回应、对比、趋势共振、反例和可能的因果链；
4. **关系驱动的候选选题**：以事件关系为中心，而不是以单条新闻标题为中心。

当前热点全景已有事件节点与主体、对象、地区维度节点的关系图，但它主要用于覆盖和分组展示，还没有把事件时间顺序、回应关系和跨事件关系作为研判输入。

## 3. 设计原则

### 3.1 T 不变

事件内和事件间研判不回写 T，不因为某个角度有传播潜力而提高事件热度。

~~~
T = 事件价值
Q = 候选选题的讨论潜力
F = 文章化质量
~~~

三者分别服务不同决策：

- T：决定是否进入深度研判；
- Q：决定哪些关系和命题值得优先进入编辑会；
- F：决定是否适合写成完整文章。

第一阶段不直接把 Q 加入 F，先作为候选选题的独立指标和同分排序依据，连续复盘后再决定是否参与最终排序。

### 3.2 深分析只针对高 T 事件

全量事件只做轻量标注、事件卡和 T 排名。

默认取 T 前 K 个事件进入事件内和事件间深研判：

- researchTopK 默认建议为 30；
- 上限建议为 50；
- 当前文章候选宇宙的 Top 50 可以作为兼容范围；
- 讨论研判 Top-K 先排除 `github_project` 项目图文，再按原 T 排名取 K 个事件；项目图文继续保留在事件热榜和独立图文池，不占用文章讨论研判名额；
- 低于 Top-K 的事件只保留在事件热榜和原始资料中，不执行深度研判；
- 用户手动补选的事件可以绕过 Top-K，但必须标记为 manual_override。

Top-K 是计算范围，不是最终文章名额。

### 3.3 用户观点是讨论信号，不是事实

评论、质疑、媒体评论和网友体验可以说明“存在讨论”，但不能直接成为事实、因果或行业共识。

所有信号都必须记录来源、来源角色、观察或推断状态、核验状态以及与候选命题的关系。

### 3.4 关系图发现关系，不自动证明因果

时间先后、共同主体或共同对象只能产生候选关系。只有存在足够证据时，才允许把关系标为因果或影响链；否则使用“并行变化”“可能相关”“值得比较”等保守表述。

## 4. 目标流程

### 4.1 L1：全量轻量处理与 T 排名

沿用当前流程：

~~~
采集 → 语义标注 → 事件卡 → 稳定事件 → T 排名
~~~

这一层不增加反常、冲突、关联和发散分，避免模型对低热度事件做无效深分析，也避免把传播包装反向混入事件价值。

### 4.2 L2：Top-K 事件内研判

对 Top-K 中每个事件生成事件内研判卡。输入包括事件卡、时间线、关联报道、来源角色和已有分类证据。

#### 反常

反常必须写出预期基线和观察结果：

~~~json
{
  "expected": "行业原本预期价格会上升",
  "observed": "实际价格下降",
  "gap": "性能提升和价格下降同时发生",
  "evidence": ["source-1", "source-2"],
  "confidence": "medium"
}
~~~

反常类型可以包括预期与结果不一致、宣传与实际信息不一致、前后状态变化、主体动作与既有策略不一致，以及公开解释与可观察结果的落差。

#### 冲突

冲突不是简单的情绪词，而是明确写出双方、争议对象和利益差异：

~~~json
{
  "sideA": "管理层",
  "sideB": "开发者",
  "issue": "AI Coding 是否真正降低了开发成本",
  "interestA": "降低人力成本并提高交付要求",
  "interestB": "减少返工、审核和额外工作量",
  "evidence": ["source-3"],
  "status": "observed"
}
~~~

#### 发散

发散点用于说明事件可能连接到哪些更大的问题，但不得把推测写成已经发生的影响：

- 对行业竞争规则的可能影响；
- 对上下游、开发者或企业采购的潜在影响；
- 对既有行业判断的修正；
- 值得继续观察的后续信号；
- 可以与其他事件进行比较的维度。

事件内研判的输出不是最终标题，而是后续事件间分析的结构化材料。

### 4.3 L3：时间/事件关系图发现候选关系

在 Top-K 事件集合上构建关系图。关系图同时保留现有维度图和新增的时间关系边。

#### 节点

- 事件节点：事件 ID、T、发生时间、最新进展时间、主体、对象、动作、风险和来源数；
- 维度节点：主体、对象、地区和场合；
- 可选信号节点：反常点、冲突双方、关键变化。

#### 关系边

~~~json
{
  "relationId": "R-E1-E2-01",
  "fromEventId": "E1",
  "toEventId": "E2",
  "relationType": "前后变化|事件更新|回应关系|并行对比|趋势共振|反例|可能影响",
  "temporalOrder": "E1_before_E2",
  "claim": "E2 是 E1 后出现的公开回应",
  "evidence": ["E1:source-1", "E2:source-2"],
  "confidence": "medium",
  "status": "candidate|validated|rejected"
}
~~~

重点关系类型：

| 类型 | 说明 | 默认表述 |
|---|---|---|
| 前后变化 | 同一主体或对象在不同时间发生变化 | “先……后……” |
| 事件更新 | 后续事件补充或修正前一事件 | “最新进展是……” |
| 回应关系 | 一方动作引发另一方回应 | “随后……回应” |
| 并行对比 | 不同主体在相近时间采取不同动作 | “两家公司走向相反” |
| 趋势共振 | 多个主体出现同类变化 | “多个主体同时……” |
| 反例 | 某事件与主流趋势方向相反 | “但也有一个反例” |
| 可能影响 | 有时间顺序和机制线索，但证据尚不足以判定因果 | “可能影响……” |

为避免 Top-K 事件两两比较造成无效组合，优先在以下范围内寻找关系：

- 共享主体；
- 共享对象；
- 共享动作；
- 时间窗口相邻；
- 共享场合；
- 事件内研判明确标记了可比较维度；
- 同一读者利益或同一成本、选择问题。

时间关系图只提供事件时间、节点和可追踪来源等输入线索，并负责召回少量关系候选对，不负责根据关键词判定语义关系；关系是否成立、属于前后/回应/对比/趋势中的哪一种，由模型结合来源证据研判。

### 4.4 L4：事件间关系研判

模型只读取时间关系图召回的候选对、对应事件卡、来源摘要/正文和时间顺序，对事件间关系进行研判，输出：

- 共同主题；
- 最强关系；
- 关系证据；
- 可以成立的比较；
- 不能成立的因果或结论；
- 对读者的具体影响；
- 适合形成的候选选题类型。

候选选题可以是：

- 单事件深挖：一个事件内部反常或冲突足够强；
- 双事件对比：两个事件存在明确方向差异；
- 多事件趋势：至少两个主体、两个时间点或两个独立来源支持共同变化；
- 事件链解释：多个事件构成有证据支持的前后变化链；
- 反例修正：一个事件挑战其他事件形成的表面共识。

同一事件的多篇报道仍只占一个事件节点；同一事件的不同角度可以生成多个候选命题，但不能重复占用事件名额。

### 4.5 L5：候选选题生成与命题包装

事件内和事件间研判完成后，才生成候选选题。候选选题的核心不是新闻标题，而是：

~~~
事件事实 + 事件内反常/冲突 + 事件间关系 + 读者具体问题
~~~

候选结构建议为：

~~~json
{
  "candidateId": "TC-001",
  "eventIds": ["E1", "E2", "E3"],
  "candidateType": "multi_event_trend",
  "coreRelation": "模型降价正在削弱低价竞争优势",
  "internalSignals": ["E1.anomaly-01", "E2.conflict-01"],
  "relationEvidence": ["R-E1-E2-01", "R-E2-E3-01"],
  "provisionalQuestion": "AI 价格战最后改变的是模型排名，还是企业采购逻辑？",
  "readerTarget": "正在选择模型或 AI 工具的开发团队",
  "readerAction": "重新评估价格、迁移和整体使用成本",
  "evidenceBoundary": "可以讨论竞争规则变化，不直接断言某家公司失去市场",
  "status": "explore"
}
~~~

provisionalQuestion 只是探索阶段的临时讨论问题。作者最终立场、正式角度和 thesis 仍然必须由编辑会确认，不能由系统自动锁定。

## 5. 讨论潜力 Q

Q 在候选选题层计算，不在事件层计算，也不回写 T。

第一阶段建议采用独立展示、不进入 F 的方式：

~~~
Q = 真实讨论需求 30
  + 关系张力 25
  + 角度空位 15
  + 讨论动量 15
  + 问题可回答性 15
~~~

Q 不重复计入已有的读者利益、事实支撑和标题钩子分。读者利益仍由现有 L3 和 B 评分负责；事实可靠性仍由事件卡和成稿事实门禁负责。

真实讨论需求优先使用已观察到的提问、反驳、踩坑、求建议、用户体验或搜索需求。只有模型推断时，必须标记为 inferred，不能与观察证据同等计分。

关系张力判断事件之间是否存在明确的方向差、利益差、策略差或认知差，不能仅凭共同关键词加分。

角度空位判断主流报道是否都在复述同一个表面叙事，候选是否提供了事实支持的新连接。

讨论动量结合新增来源、最新回应、跨平台新增讨论和关系图中的新增边，识别 emerging、debating、saturated、cooling。

问题可回答性判断读者能否基于自己的工作、成本、工具选择或经历参与回答。泛泛的“你怎么看”不计分。

## 6. 核心 8 + 黑马 2 的调整

当前核心 8 + 黑马 2 的名额逻辑建议调整为：

1. 先按 T 选出 Top-K 事件研判范围；
2. 对 Top-K 事件生成事件内信号和事件间关系；
3. 由关系和信号生成候选选题；
4. 对候选选题进行 F、Q、账号契合和竞争分析；
5. 最后从候选选题中选出核心 8 条和黑马 2 条。

新的名额含义：

- **核心 8 条**：事实基础、关系成立度和文章化价值综合较高；
- **黑马 2 条**：T 不一定最高，但 Q 高、关系稀缺或处于讨论上升期；
- **候补**：关系证据不足、需要补充来源或与其他候选存在竞争时保留。

低热度事件不进入深研判，因此黑马不是低热度事件的免检通道，而是 Top-K 内部的讨论潜力黑马。

| 产物 | 用途 |

| topk-research-scope.json | 记录 T 排名、Top-K 范围、排除事件和人工补选事件 |
| internal-signals.json | 事件内反常、冲突、发散及证据 |
| event-relations.json | 时间/事件关系图的节点、边、证据和置信度 |
| topic-candidates.json | 关系驱动的候选选题和临时讨论问题 |

## 8. 研判内容的统一承接

本次改造不能只生成后台 JSON。研判结果必须同时进入两个消费端：

1. 选题池页面：帮助作者理解“为什么这个候选值得选”；
2. 选题编辑页和编辑会模型：让后续问题围绕已有研判继续推进，而不是重新从事件摘要开始。

### 8.1 候选详情数据契约

候选详情接口在现有候选字段、事件卡和来源列表之外，增加统一的 researchContext（HTTP JSON 使用现有接口风格的 `research_context` 字段）：

~~~json
{
  "researchContext": {
    "scope": "topk|manual_override",
    "eventValue": 82,
    "eventRank": 3,
    "internalSignals": {
      "anomalies": [],
      "conflicts": [],
      "divergences": []
    },
    "relations": [],
    "topicCandidate": {
      "candidateType": "multi_event_trend",
      "coreRelation": "多个事件共同指向竞争规则变化",
      "provisionalQuestion": "这个变化会先影响谁的选择？"
    },
    "discussion": {
      "score": 78,
      "stage": "debating",
      "evidenceStatus": "observed|inferred|missing",
      "signals": []
    },
    "evidenceBoundary": [],
    "openQuestions": []
  }
}
~~~

候选详情的 researchContext 必须由候选关联的事件 ID读取，不能由前端根据标题重新推断。单事件候选只返回一个事件及其事件内研判；综合候选返回全部关联事件、关系边和关系证据。

### 8.2 编辑会模型输入契约

现有编辑会已经把候选、事件卡和来源正文放入模型上下文，但新增的事件内研判、事件间关系和临时讨论问题必须作为独立的结构化输入注入，不要拼接成无法区分的长摘要。

模型上下文建议按以下顺序组装：

~~~
账号上下文
→ 候选基本信息
→ 事件卡与来源
→ 事件内研判
→ 事件间关系图摘要
→ 临时选题候选
→ 当前编辑底稿
→ 本轮用户回答
~~~

模型必须遵守：

- 把研判内容当作编辑分析和待核材料，不把模型推断直接当作事实；
- 优先使用带证据的反常、冲突和关系；
- 发现关系证据不足时，主动提醒作者缩小命题或补充来源；
- 先询问作者是否接受临时讨论问题，再推进 angle 和 thesis；
- 不把 provisionalQuestion 自动写入作者观点；
- 作者明确否定某个关系时，将其记录为 rejected_angles 或 forbidden_claims；
- 继续使用现有的事实 → 观点 → 角度 → 命题 → 实践 → 边界推进顺序。

因此，编辑会的输入不是只增加一句提示，而是增加一份带来源引用和置信度的 researchContext。它必须在每轮对话中保持可追溯，避免模型下一轮忘记前面已经确认的关系。

## 9. 页面调整

### 9.1 热点全景/关系图

增加：

- T Top-K 深研判筛选；
- 事件时间轴；
- 关系边类型筛选；
- 关系置信度；
- 支持来源和事件卡跳转；
- 只看多事件关系子图。

现有主体、对象和地区维度图继续保留，作为关系发现的一部分，不替换为纯时间线。

### 9.2 选题池

选题池候选卡增加“查看研判”入口。点击后打开候选详情抽屉或展开面板，至少显示：

~~~
事件价值 T
讨论潜力 Q
关联事件
事件时间线
为什么这些事件应该放在一起
事件内反常
事件内冲突
事件内发散
事件间关系
关系证据和置信度
为什么现在值得分析
临时讨论问题
事实边界
~~~

事件详情需要支持从关系边跳转到对应事件卡和来源原文；对于综合候选，应明确显示“主事件”“辅助事件”和每条关系的作用，不能只列出一组标题。

候选卡仍保留进入编辑会的主按钮。查看研判是解释入口，不是额外的人工确认步骤。

默认排序仍保留 F 主榜；Q 作为独立列、同分排序和讨论潜力榜，避免把容易争论误认为适合写成长文。

### 9.3 选题编辑页与编辑会

选题编辑页打开候选时，左侧或顶部显示事件与研判摘要，正文区域保留现有编辑底稿、来源和对话。

页面必须允许作者在开始对话前查看：

- 关联事件和时间顺序；
- 事件内反常、冲突和发散；
- 事件间关系；
- 临时讨论问题；
- 关系证据、置信度和事实边界。

编辑会不再从空白角度开始，而是让作者确认：

- 采用哪个事件关系；
- 是否接受临时讨论问题；
- 是否改为单事件或双事件；
- 作者是否有相反经验或补充证据；
- 哪些推断不能写成结论。

作者确认后，才生成最终 angle 和 thesis。

## 10. 分阶段实施

### 阶段 0：冻结 Top-K 范围并执行模型研判，不改排名

- 增加 Top-K 研究范围产物；
- 仅按排除项目图文后的 T 榜冻结 Top-K 事件范围；事件热榜本身仍保留全部内容类型；
- 第 1 阶段按事件隔离调用模型，只生成事件内反常、利益冲突和可发散方向；
- 第 2 阶段先由时间关系图召回候选对，再调用模型判断前后、回应、对比和趋势关系；程序不直接生成语义关系；
- 第 3 阶段只把前两阶段的研判结果交给模型生成候选选题，候选必须引用研判信号、关系和来源；
- 来源输入统一标注 `full_text`、`summary_only`、`repository_meta`、`title_only`，并按证据等级限制确定性输出；
- 程序只执行事件 ID、来源 ID、对比差异、输出结构和重复信号门禁，不再用正则匹配生成语义关系；
- 产物固定写入 `discussion-research-input.json`（三个阶段每次实际模型请求的 system/user messages 快照）、`discussion-research.json`、`topk-research-scope.json`、`internal-signals.json`、`event-relations.json` 和 `discussion-research-report.md`；
- 候选详情接口增加 researchContext（落地字段为 `research_context`）的只读返回；
- 选题池增加“查看研判”入口；
- 编辑会模型先只读取研判内容，不改变现有提问顺序；
- 连续运行 2–3 个批次，检查关系有效率和无效推断率。

### 阶段 1：关系图接入研判

- 扩展热点全景的事件节点和时间关系边；
- 将阶段 0 的 `event-relations.json` 接入热点全景；
- 关系边必须保留事件 ID、时间依据、来源引用和置信度；
- 低于 Top-K 的事件不进入关系图深研判。

### 阶段 2：关系驱动的候选生成

- 生成单事件、双事件和多事件候选；
- 将核心 8 + 黑马 2 从事件级预选迁移到候选选题级预选；
- 增加临时讨论问题，但不锁定作者立场；
- 选题池详情面板按“候选选题 → 事件内研判 → 事件间研判 → 事件事实”展示完整 researchContext；不把关系检测结果直接当作选题；
- 候选详情接口和编辑会输入使用同一份结构化研判数据；
- 保留现有编辑会和文章成稿门禁。

实施记录：

- 新增 `server/features/research/domain/topic-candidate-generation.mjs`，只消费事件热榜 Top-K 研判产物；
- 新增 `skills/discussion-researcher/SKILL.md` 和 `server/features/research/application/research/discussion-research-stage.mjs`；模型按事件内、事件间、候选生成三个阶段调用，程序只负责 Top-K 范围、关系候选对召回、证据等级门禁、证据绑定、结构校验和去重；同时保存每次实际请求的 `discussion-research-input.json`，便于核对模型实际输入；
- 产出 `topic-candidate-generation.json`、`topic-preselection-ranking.json` 和 `topic-candidate-report.md`；
- 常规批次的脑暴输入改为候选选题级核心 8 + 黑马 2，旧事件级排名和维度池仍保留为兼容审计、早报和图文路线；
- 候选支持单事件、双事件关系和关系连通的多事件链；临时讨论问题写入 `research_context.topic_candidate`，明确 `is_author_stance: false`；
- 选题详情和编辑会从同一份批次研判产物恢复事件卡、关系、证据边界和临时讨论问题，F 评分及成稿门禁未改变。

### 发布后复盘边界

- 本选题研判流程止于候选选题生成和编辑确认；
- 发布后的阅读、分享、评论等数据直接使用公众号现有复盘流程，不在候选层重复记录；
- 不新增 Q 指标，不新增候选表现复盘文件或接口；

实施记录：

- 研判详情默认按编辑阅读顺序展示“由研判形成的候选选题 → 事件内部的反常 / 利益冲突 / 可发散方向 → 事件之间的前后 / 回应 / 对比 / 趋势关系 → 关联事件事实 → 写作前还要确认”；内部枚举、事件 ID 和重复信号不直接作为主界面文案，原始证据字段收进高级折叠区；
- 事件内和事件间研判才是选题生成依据；每个候选必须有候选标题、核心问题、切入角度、命题种子和证据边界，不能退化为事件摘要或新闻复述；

## 11. 验收标准

1. T 排名公式和排序结果不因 Q 或文章角度改变；
2. 只有排除 `github_project` 后的 T Top-K 事件进入事件内和事件间深研判；项目图文不占用研判名额；
3. 低热度事件默认不会触发深度模型调用；
4. 每个反常点都有明确预期、观察结果和证据状态；
5. 每个冲突点都有双方、争议对象和利益差异；
6. 每条事件间关系都能回指事件 ID、时间依据和来源；
7. 关系图不把时间先后自动解释成因果；
8. 同一事件的多篇报道不会重复占用事件名额；
9. 候选选题可以明确说明为什么这些事件应该放在一起；
10. 临时讨论问题不会被误写成作者最终观点；
11. 核心 8 + 黑马 2 在候选选题生成之后产生；
12. 选题池点击候选可以看到完整事件信息和研判内容；
13. 候选详情接口返回的 researchContext 与页面展示内容一致；
14. 编辑会模型每轮都能读取研判内容、来源引用和置信度；
15. 研判推断不会被模型当作已确认事实或作者观点；
16. 现有编辑会、事实门禁、F 评分和成稿链保持兼容。

## 12. 暂不纳入本期

- 自动抓取所有平台评论区；
- 用评论数量直接代表真实舆情热度；
- 将 Q 直接并入 F；
- 根据关键词相同自动判定因果关系；
- 让低热度事件绕过 T 进入深研判；
- 由模型自动替作者确认最终立场。
