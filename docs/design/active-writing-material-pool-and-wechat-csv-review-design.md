# 主动写作素材池与公众号导出复盘设计草案

> 状态：讨论草案
>
> 日期：2026-08-31
>
> 目标：让工作台支持「见字」的长期主动写作、真实素材沉淀和公众号后台导出文件的周期性复盘。

## 1. 背景与判断

当前项目已经具备自主写作能力：支持“心得经验”和“使用教程”、对话式补充事实、本地项目只读读取、真实性门禁、标题/审稿/SEO、排版和版本编辑。

当前缺口不是缺少一键成稿，而是缺少成稿之前的长期素材层：

- 没有长期的主动选题和灵感池；
- 没有专门记录 Problem、Options、Verdict、Value 的迭代卡；
- 没有统一保存截图、日志、代码差异、失败结果等证据资产；
- 没有把文章与下一次迭代预告建立关联；
- 没有把主动写作计划纳入内容日历；
- 公众号后台无法通过个人号 API 自动读取，但可以人工导出 CSV。

核心判断：

> 会话记录、阅读笔记和生活经历都可以成为素材；作者负责提供真实发生过的内容，工作台负责整理、筛选、扩展和复盘，不替作者制造经历。

## 2. 目标与非目标

### 2.1 目标

1. 用低负担方式收集开发、阅读、生活和与 AI 的会话素材。
2. 将真实素材整理为可检索的素材卡和「见字迭代记」候选。
3. 支持从素材卡进入现有自主写作流程。
4. 支持将主动文章安排到内容日历，并承接下一篇预告。
5. 支持导入公众号导出的 CSV，按文章和栏目进行周复盘。
6. 提供独立的素材入箱页面，并允许配置多个主动写作栏目。
7. 根据账号定位自动评估素材的账号契合度、写作成熟度和推荐去向。

### 2.2 非目标

- 不实现个人公众号后台 API 登录或自动抓取。
- 不模拟登录、绕过权限或爬取公众号后台。
- 第一阶段不做通用 CSV 解析，只支持已确认的 5 种公众号后台导出格式。
- 不自动把 AI 回复、外部资料或项目文件伪装成作者亲身经历。
- 不把素材采集设计成强制日更或每天必须发布文章。
- 不在第一阶段自动发布到公众号、小红书、知乎或 GitHub。

## 3. 总体流程

```text
会话 / 阅读 / 生活 / 开发现场
              ↓
        快速记录与素材入箱
              ↓
      素材卡整理、标签和证据关联
              ↓
     每周筛选：是否值得写成文章
              ↓
    迭代记简报 / 自主写作事实表
              ↓
       初稿 → 标题 → 审稿 → 排版
              ↓
       发布 → 导入公众号后台导出文件
              ↓
        关联正文与证据 → 按栏目复盘
               ↓
       反哺标题、写作、选题与内容日历
```

## 4. 素材来源与事实等级

| 来源 | 默认类型 | 可支持的写法 | 约束 |
|---|---|---|---|
| 与 AI 的会话记录 | 思考素材 / 作者确认后可转体验 | 决策过程、观点形成、项目复盘 | AI 输出不能自动当事实；需保留作者最终确认 |
| 阅读文章、报告、文档 | 外部资料 | 行业分析、技术认知、观点文章 | 保存标题、来源、URL；事实和观点分开 |
| 生活经历 | 作者经历 | 县城、备考、离职、工作状态观察 | 只能写真实经历；注意隐私与第三方信息 |
| 本地项目文件 | 项目素材 | 功能、代码结构、配置、文档说明 | 文件存在不等于命令已成功执行 |
| 截图、日志、代码差异 | 证据资产 | 支撑结果、失败、前后对比 | 记录产生时间、关联素材和可公开状态 |

## 5. 素材卡设计

素材入箱作为独立页面存在。第一版支持“快速记录”和“完整迭代卡”两层，快速记录允许只填写一句话，后续再补全。独立页面需要支持快速粘贴、保存草稿、筛选、批量标记和进入写作，不要求作者先选择某个栏目。

### 5.1 快速记录字段

- `sourceType`：conversation / reading / life / development / other
- `capturedAt`：记录时间
- `rawText`：原始记录
- `tags`：项目、工具、行业、生活、备考等标签
- `privacyLevel`：private / review / public-candidate
- `status`：inbox /整理中 / ready / used / archived

### 5.2 迭代卡字段

```text
栏目：见字迭代记
发生时间：
具体问题（Problem）：
考虑过的方案（Options）：
最终选择（Verdict）：
放弃了什么、牺牲了什么：
结果或失败结论：
当时真实的感受或判断：
证据资产：截图 / 日志 / 代码差异 / 数据图
读者可复用的结论（Value）：
下一篇准备解决什么：
主要 CTA：
计划发布时间：
```

“活人感”应来自真实场景、犹豫、限制、失败和取舍，不通过额外生成情绪化措辞制造。

## 6. 会话记录的进入方式

第一阶段不依赖会话平台 API，素材入箱只支持 Markdown 和纯文本粘贴，采用显式保存：

1. 在会话中选取有价值的片段；
2. 粘贴到素材入箱；
3. 补充“这是否是我的真实经历/判断”；
4. 由系统生成素材卡草稿；
5. 作者确认后才能进入作者经历事实基座。

后续可考虑支持会话导出文件批量导入，但必须保留来源和作者确认状态。

## 7. 主动写作与现有流程的关系

主动写作不是新建一套文章生产链，而是在现有自主写作入口前增加素材层：

```text
素材卡
  → 筛选为文章候选
  → 生成迭代记简报
  → 进入“心得经验”自主写作
  → 现有标题、审稿、SEO、排版流程
```

使用教程仍适合处理可复现步骤；心得经验适合处理真实使用、项目取舍、失败复盘和个人判断。

需要补强的不是现有写作技能本身，而是：

- 将 `Problem / Options / Verdict / Value` 作为主动文章的结构化输入；
- 要求至少一条作者确认的体验或判断；
- 支持证据资产关联；
- 支持下一篇预告和系列关联；
- 支持从内容日历直接打开待写素材。

主动写作栏目不写死为“见字迭代记”。系统允许创建多个栏目，例如“见字迭代记”“开发现场”“县城备考记录”“工具使用心得”，每个栏目可配置简介、适用写作模式、内容比例和默认 CTA。栏目是内容计划和复盘的归类维度，不改变事实等级规则。

## 8. 内容日历扩展

在当前内容日历上扩展计划态记录，不新建第二套日历。当前已完成的文章和图文产物继续保留，主动写作计划与素材候选作为计划项加入同一视图：

- `planned`：已计划但未开始；
- `inbox`：有素材，尚未决定是否写；
- `drafting`：进入成稿；
- `scheduled`：计划发布；
- `published`：已发布，等待数据；
- `reviewed`：已完成 CSV 复盘。

每个计划项至少关联：栏目、素材卡、目标读者、内容角色、分发池、CTA、计划日期和下一篇预告。

建议的最小节奏不是强制日更，而是：

- 平时随手记录素材；
- 每周筛选一次；
- 每周至少完成一篇主动写作；
- 有真实事件或足够素材时，再增加发布量。

## 9. 公众号后台导出文件导入与复盘

### 9.1 数据边界

公众号后台数据由作者人工导出，工作台不接触账号认证信息。原始导出文件只读保存，清洗结果单独保存，重复导入不重复计数。

实际导出文件并不都是标准 CSV 或同一种 Excel 格式：当前样本中既有真正的 BIFF `.xls`，也有网页表格伪装成 `.xls`。导入器应按文件内容识别格式，不应只按扩展名处理。文件名不能作为唯一业务含义，导入时允许作者确认文件类型。

### 9.2 当前可用的导出文件

| 文件 | 后台含义 | 时间粒度 | 关键字段 | 可支持的复盘 |
|---|---|---|---|---|
| `user_analysis.xls` | 用户分析 | 每日 | 时间、新关注人数、取消关注人数、净增关注人数、累积关注人数 | 日增粉、取关、净增、增长波动 |
| `total_1785458074_1788050074.xls` | 已通知内容分析 | 按文章 | 内容标题、发表日期、阅读人数、分享人数、阅读后关注人数、阅读完成率、内容 URL | 通知内容的阅读、分享和转粉表现 |
| `total_1785458052_1788050052.xls` | 未通知内容分析 | 按文章 | 内容标题、发表日期、阅读人数、分享人数、阅读后关注人数、送达人数、送达完成率、阅读完成率、内容 URL | 非通知内容的推荐/自然传播表现，并可计算送达相关指标 |
| `tendency_1785544400_1788050000.xls` | 内容趋势 | 每日 + 按文章/传播渠道 | 日期、渠道、阅读人数；分享人数、跳转阅读原文人数、微信收藏人数、发表篇数；传播渠道、发表日期、内容标题、阅读人数、阅读人数占比 | 推荐、公众号消息、搜一搜、聊天会话等渠道归因 |
| `activity_analysis.xls` | 常读用户趋势 | 每月 | 时间、常读用户数、常读用户比例 | 常读用户增长和读者沉淀趋势 |

当前样本的时间范围也不一致：用户分析覆盖 2026-07-31 至 2026-08-30，内容趋势覆盖 2026-08-01 至 2026-08-30，常读用户趋势覆盖 2026 年 3 月至 7 月。每次导入必须保存原文件名、导出时间、报告覆盖区间和解析器版本。

样本中用户分析显示 2026-07-31 至 2026-08-30 共净增 340 人，期末累积关注人数为 2262；这与此前策略文档中的 30 天基线不完全一致，后续应以“报告覆盖区间 + 导入批次”为准，不能混用不同口径。

### 9.3 第一版字段

#### 用户日表

- 日期；
- 新关注人数；
- 取消关注人数；
- 净增关注人数；
- 累积关注人数。

#### 文章表现表

- 内容 URL（优先作为稳定文章键）；
- 标题；
- 发表日期；
- 通知状态；
- 阅读人数；
- 分享人数；
- 阅读后关注人数；
- 送达人数、送达完成率；
- 阅读完成率。

#### 渠道趋势表

- 日期；
- 传播渠道；
- 渠道阅读人数；
- 分享人数；
- 跳转阅读原文人数；
- 微信收藏人数；
- 当日发表篇数；
- 文章标题、发表日期、文章阅读人数、阅读人数占比。

#### 常读用户表

- 月份；
- 常读用户数；
- 常读用户比例。

当前文件没有明确的“7 日阅读”字段。第一版把文章指标标记为某次导出的累计快照；若需要 7 日阅读，应在发布后约第 7 天再次导出并按内容 URL 匹配，或从后续趋势数据中补齐，不能把单次阅读人数直接命名为 7 日阅读。

### 9.4 文章关联

优先使用内容 URL 匹配项目文章；没有 URL 时再使用“标题 + 发布时间”。标题被修改、发布时间缺失、一篇文章多次导出或同日同标题存在多个版本时，进入人工确认队列。项目文章需要提前保存栏目和内容角色，不能只依赖标题猜测。

同一篇文章可能同时出现在“已通知”和“未通知”文件中，导入层应保留来源报告和通知状态，不要简单覆盖。若两份报告出现同一内容 URL，以 URL 为文章主键，以报告类型作为表现记录的维度。

### 9.5 复盘指标

- 文章阅读与 7 日阅读；
- 新增关注；
- 文章转粉率（若字段可计算）；
- 分享率；
- 送达完成率；
- 阅读完成率；
- 推荐、搜一搜、公众号消息、聊天会话等渠道占比；
- 每千次阅读带来的关注数；
- 按工具、行业、迭代记等栏目比较中位数；
- 同一系列前后文章的后续阅读和表现。

口径约定：

- 文章转粉率 = 阅读后关注人数 ÷ 阅读人数；
- 分享率 = 分享人数 ÷ 阅读人数；
- 渠道占比优先使用后台给出的“阅读人数占比”，避免把“全部”和各个子渠道重复相加；
- 单次导入的文章指标是截至导出时的快照，重复导入应形成时间序列，而不是覆盖旧值；
- 内容趋势表为横向多块布局，解析时应按块头识别为多张逻辑表，不能把整张工作表当成单一二维表。

第一阶段以“导入后在工作台内查看周报”为主，不生成 Markdown/PDF 周报，不追求实时看板和自动发布。5 种后台导出文件允许逐个导入，系统按报告类型和导入批次合并；导入入口只承诺兼容本设计中列出的 5 种格式，出现未知格式时先提示“暂不支持”，不静默猜测字段。

## 10. 与账号策略的配置关系

如果“见字”与当前 `account-context.json` 中的“橙序员”是同一个对外账号，需要先统一：

- 账号名称与简介；
- 核心读者；
- 内容支柱；
- 内容比例；
- 关注理由；
- 主动写作栏目及其内容比例；
- 分发池和文章角色。

账号上下文仍由选题、编辑会和写作流程读取。素材池应继承该上下文，但不能用账号画像替代作者真实材料。

### 10.1 多主动写作栏目

栏目配置由工作台提供独立的“栏目管理”入口，持久化为工作台自己的栏目数据，不写入 `account-context.json`。账号上下文只负责全局定位、读者画像、内容支柱和整体风格；栏目是可独立增删改、停用和归档的编辑运营对象。

栏目配置建议包含：

- `id`：稳定栏目标识；
- `name`：栏目名称；
- `description`：栏目边界和读者承诺；
- `writingMode`：experience / tutorial / mixed；
- `contentRatio`：栏目在主动写作中的目标比例；
- `defaultAudience`：默认读者；
- `defaultCta`：默认承接动作；
- `active`：是否参与推荐。

素材卡可以先不指定栏目。自动推荐阶段给出一个主栏目和可选备选栏目，作者确认后才进入内容计划。

### 10.2 基于账号定位的自动评分与推荐

主动素材使用独立的 `M`（Material）评估，不复用热点选题的 `F` 分。`M` 不是复杂的算法评分，而是 AI 编辑判断卡，用于快速决定素材是否值得继续加工。

第一版只输出四项：

| 维度 | 输出内容 |
|---|---|
| 账号切合度 | 是否符合 `contentPillars`、`readerProfile` 和账号差异化定位，并说明原因 |
| 内容完整度 | 当前是否具备问题、经历/判断、结果和读者价值；明确列出缺什么 |
| 话题潜力 | 是否值得扩展成文章，判断推荐、搜索、沉淀或系列追更潜力 |
| 深挖方向 | 给出 1–3 个可以继续追问或扩展的方向 |

每项统一使用“高 / 中 / 低”，不显示复杂数字分数，不设计复杂权重，也不允许栏目单独改一套评分公式。必要时可以生成一个用于排序的总体等级，但用户界面只展示四项判断和文字理由。

AI 推荐结果为：

- `write-now`：素材基本完整，建议进入某个主动栏目；
- `整理补充`：方向匹配，但需要补充经历、结果、证据或作者确认；
- `可能形成系列`：当前素材可写，并发现了明确的后续问题；
- `暂不推荐`：账号切合度低、重复度高或事实风险未解决。

对于前三类素材，推荐流程调用标题技能，基于素材卡、栏目配置、目标读者和账号定位生成若干“标题方向”，而不是直接把某个标题视为最终标题。标题方向需要标注包装意图，例如搜索型、推荐型、观点型或系列追更型，并保留事实边界。

推荐必须展示“为什么推荐”“还缺什么”“深挖方向”和“标题方向依据”，并允许作者改选栏目、调整方向或手动跳过。账号画像只影响切合度、推荐顺序和标题包装建议，不得凭空补齐经历、结果或证据。

## 11. 已确认的产品决策与剩余问题

### 11.1 已确认决策

- 素材入箱使用独立页面；
- 第一阶段只支持 Markdown 和纯文本粘贴；
- 公众号数据导入只支持当前确认的 5 种后台导出格式；
- 五种后台导出文件允许逐个导入后合并；
- 允许多个主动写作栏目，不把“见字迭代记”写死为唯一栏目；
- 在现有内容日历上扩展计划态和发布态；
- 根据账号定位做自动评分和推荐，并调用标题技能生成标题方向；推荐必须可解释，作者保留最终决定权；
- 周报第一版只在工作台内查看，不生成 Markdown/PDF 文件。

### 11.2 剩余问题

当前没有影响 MVP 的开放问题；评分界面确定为“高 / 中 / 低 + 文字理由”。后续只需在实现时确认具体文案和排序规则。

## 12. MVP 数据与实体设计

### 12.1 栏目实体

栏目作为工作台数据库中的独立实体，不进入 `account-context.json`。建议字段：

```text
ContentColumn
├── id
├── slug
├── name
├── description
├── writingMode          # experience / tutorial / mixed
├── contentRatio
├── defaultAudience
├── defaultCta
├── active
├── createdAt
└── updatedAt
```

“栏目管理”支持新增、编辑、停用和归档。素材可以暂不归属栏目；自动推荐后由作者确认主栏目，内容计划和数据复盘通过 `columnId` 关联。

### 12.2 素材卡字段

素材入箱使用独立页面。素材卡分为“快速记录”和“可写候选”两层，避免作者每次记录都必须填写完整表单。独立页面需要支持快速粘贴、保存草稿、筛选、批量标记和进入写作，不要求作者先选择某个栏目。

#### 快速记录

| 字段 | 说明 | 是否必填 |
|---|---|---:|
| `sourceType` | conversation / reading / life / development / other | 是 |
| `capturedAt` | 素材发生或记录时间 | 是 |
| `rawText` | 原始记录，允许只有一句话 | 是 |
| `tags` | 项目、工具、行业、生活、备考等 | 否 |
| `privacyLevel` | private / review / public-candidate | 是 |
| `status` | inbox / 整理中 / ready / used / archived | 是 |

#### 可写候选

在快速记录基础上补充：

- `problem`：具体问题；
- `options`：考虑过的方案；
- `verdict`：最终选择及放弃内容；
- `result`：结果、失败或尚未验证的状态；
- `value`：读者可复用的结论；
- `authorConfirmed`：作者是否确认这是本人经历或判断；
- `evidenceAssetIds`：关联截图、日志、代码差异或数据图；
- `nextQuestion`：下一篇可继续解决的问题。

素材卡允许长期保存，不要求最终一定转成文章。进入作者经历事实基座前，必须经过 `authorConfirmed` 确认。

### 12.3 文章与公众号 URL 的关联

文章关联采用分层匹配：

1. 首选 `contentUrl`，作为公众号文章的稳定外部键；
2. 没有 URL 时使用“标题 + 发表日期”；
3. 仍无法唯一匹配时进入人工确认队列；
4. 标题修改后不覆盖原记录，保留历史标题和匹配日志。

项目侧文章需要保存以下发布元数据：

- `contentUrl`；
- `publishedAt`；
- `titleAtPublish`；
- `contentPillar`；
- `contentRole`；
- `distributionLane`；
- `planId`；
- `materialIds`。

同一篇文章同时出现在“已通知”和“未通知”文件中时，以 URL 作为文章主键，以报告类型和导出批次作为表现记录维度，不互相覆盖。

### 12.5 内容日历中的计划态与发布态

内容日历同时展示“生产计划”和“已发布产物”，但两者使用不同状态，不把未发布计划伪装成已完成文章。

```text
inbox       有素材，尚未决定是否写
planned     已确定栏目、主题和计划日期
drafting    已进入自主写作或文章生产
reviewing   正在审稿、SEO 或事实复核
scheduled   已完成，等待人工发布
published   已填写公众号 URL，等待数据快照
reviewed    已完成至少一轮后台数据复盘
archived    暂停或不再推进
```

计划项至少关联：

- 栏目和内容支柱；
- 目标读者；
- 内容角色和分发池；
- 素材卡；
- 主要 CTA；
- 计划发布时间；
- 下一篇预告；
- 发布 URL；
- 最近一次数据快照。

日历视图建议支持按“计划日期”和“发布日期”切换。第一版不要求自动发布，作者发布后手动粘贴 URL 即可完成关联。

发布元数据需要有明确的页面录入入口，不能只作为后台字段存在。建议使用同一套保存接口提供两个入口：

- **内容日历计划详情**：面向从素材进入日历的文章，填写发布 URL、实际发布日期和发布时标题；栏目、内容支柱、内容角色、分发渠道、计划和素材从计划自动带入，允许作者修正；
- **文章编辑器的“登记发布信息”入口**：面向没有关联内容计划的既有终稿，补充发布 URL、实际发布日期和发布时标题，并允许之后再关联栏目或素材。

保存后显示“已登记 / 已发布 / 待导入数据 / 已复盘”等状态。文章编辑器只展示发布信息摘要和跳转入口，日历计划详情作为元数据的主编辑位置，避免两处表单互相覆盖。

### 12.6 公众号复盘反哺创作设计

公众号复盘不只作为数据展示，而是生成一份可供后续创作读取的“历史写作反馈”。反馈默认是软性建议，不直接改写账号定位、技能文件或已排期内容，作者确认后才进入下一轮创作。

#### 反馈输入

- `ArticleMetricSnapshot`：阅读、分享、阅读后关注、通知状态和发布时间；
- `ArticleChannelSnapshot` / `ChannelTrendDaily`：渠道阅读与分享表现；
- 文章标题、题材标签和标题结构识别结果；
- 关联到的本地草稿、终稿、HTML、证据资产和发布元数据；
- 栏目、内容支柱、内容角色、分发渠道和目标读者。

当前数据能判断历史相关性，不能直接证明因果关系。题材标签允许重叠；单篇异常高表现文章必须标记为异常样本，不能单独改变长期策略。

#### 反馈输出

```text
ContentFeedbackSnapshot
├── id
├── generatedAt
├── metricWindow
├── sourceBatchIds
├── confidence                 # low / medium / high
├── topicSignals[]             # 题材表现与适用目标
├── titleSignals[]             # 标题结构、关键词和包装方式
├── bodySignals[]              # 正文结构、证据和兑现情况
├── channelSignals[]           # 渠道阅读信号，关注转化可能为空
├── recommendations[]          # 下一轮选题、标题和写作建议
└── unresolvedQuestions[]      # 数据不足或待人工确认的问题
```

反馈分为六类：

1. **账号内容策略**：哪些题材更适合拉新、分享、沉淀关注或做实验；是否需要观察内容比例变化。
2. **标题生成**：按推荐、通知、实验等分发目标提示可参考的标题结构和关键词。
3. **正文写作**：提示增加真实场景、问题、证据、结果、失败、边界和下一步实验。
4. **图文标题**：根据收藏、分享和信息密度调整卡片标题；使用独立于文章标题的短标题规则。
5. **选题与内容日历**：将历史验证过的题材、结构和未完成问题作为下一轮推荐依据。
6. **账号配置建议**：只生成待确认的 `contentRatio`、栏目偏好和包装策略调整建议，不自动覆盖 `account-context.json`。

#### 反馈可信度

每条反馈必须同时显示来源范围和可信度：

| 内容关联等级 | 可支持的结论 | 默认可信度 |
|---|---|---|
| `metrics_only` | 阅读、分享、关注等结果层信号 | 低 / 中 |
| `title_linked` | 题材与标题结构的历史相关性 | 中 |
| `body_linked` | 正文结构、证据和标题兑现情况的相关性 | 中 |
| `evidence_linked` | 真实截图、日志、代码差异和失败结果的支撑情况 | 中 / 高 |

渠道数据当前主要支持阅读和分享分析，不能在缺少渠道级关注数据时断言“哪个渠道更容易涨粉”。

#### 反哺边界

- 反馈只影响后续推荐、标题方向和写作提示，不自动发布；
- 不根据一篇爆文自动修改账号定位或内容比例；
- 不把抓取到的正文自动认定为作者经历；
- 不把正文特征直接解释为表现原因，只表述为“可验证假设”；
- 所有进入作者经历事实基座的内容仍需作者确认。

### 12.7 正文细节补充的前置工作

正文分析前先解决“数据和文章能否可靠对应”的问题。建议按“本地优先、URL 补充、匹配可回溯”的顺序建设。

#### 前置工作 0：提供发布元数据录入入口

当前页面尚未提供统一发布元数据的录入入口，因此不能把“自动扫描和自动匹配”作为第一步。先在内容日历计划详情增加“发布信息”区，并在文章编辑器增加“登记发布信息”入口；两者写入同一个文章发布关联实体。

第一版只需要支持以下人工录入字段：

| 字段 | 录入位置 | 说明 |
|---|---|---|
| `contentUrl` | 发布信息区 | 公众号文章 URL，允许暂时为空 |
| `publishedAt` | 发布信息区 | 实际发布日期和时间；至少支持日期 |
| `titleAtPublish` | 发布信息区 | 发布时最终标题，默认带入当前标题 |
| `columnId` | 计划详情 / 编辑器补充 | 主动写作栏目，可后补 |
| `contentPillar` | 计划详情 / 编辑器补充 | 账号内容支柱，可后补 |
| `contentRole` | 计划详情 / 编辑器补充 | 拉新、涨粉、讨论、实验等目标 |
| `distributionLane` | 计划详情 / 编辑器补充 | 推荐、通知、实验等分发方式 |

保存时不要求所有字段一次填完。没有 URL 的文章保持“待登记”；有 URL 和发布日期后进入“已发布，等待数据”；导入公众号数据并成功关联后进入“已复盘”。

#### 前置工作 A：统一发布元数据

项目文章在发布或排期完成时，尽量保存以下字段：

- `contentUrl`；
- `publishedAt`；
- `titleAtPublish`；
- `columnId`、`contentPillar` 和 `contentRole`；
- `distributionLane`；
- `planId`、`materialIds`；
- 发布版本文件路径或版本号。

这是后续把后台数据关联回栏目、素材和文章版本的基础。没有这些字段时，才进入标题匹配流程。

#### 前置工作 B：建立本地文章产物索引

扫描项目已有的草稿、终稿、HTML 和文章目录，生成只读索引，不直接修改原文章。索引至少保存：

- 文件路径和产物类型；
- 标题及规范化标题；
- 文章日期；
- 版本号或更新时间；
- 可能的发布 URL；
- 关联计划、栏目、素材和证据资产。

本地匹配优先级：发布 URL 精确匹配 → 标题精确匹配 → 去标点和表情后的标题匹配 → 标题相似度加日期匹配。

#### 前置工作 C：匹配确认和日志

每次匹配都保存：

- 匹配方式；
- 候选文章；
- 匹配置信度；
- 作者确认结果；
- 标题修改和重新匹配记录。

无法唯一匹配的文章进入人工确认队列，不静默关联到相似文章。这样可以避免把一篇文章的阅读数据错误地反哺给另一篇文章。

#### 前置工作 D：URL 补充获取

对于本地找不到、但 CSV 中存在公开内容 URL 的文章，提供手动触发的 URL 获取流程。获取成功后保存正文快照、获取时间、最终 URL 和失败原因；获取不到时保留 `metrics_only` 状态，不阻塞复盘。

URL 获取需要考虑文章删除、改标题、访问限制、跳转和页面结构变化，因此只能作为补充来源，不能覆盖已确认的本地终稿。

#### 前置工作 E：正文特征抽取

正文关联成功后，第一版先做确定性抽取：

- 字数、段落数、小标题数；
- 开头进入问题的段落位置；
- 工具、人物、事件和数字的出现情况；
- 列表、代码、引用、图片和证据占位；
- 结果、失败、限制条件和 CTA 的出现情况；
- 标题承诺是否在正文中有对应段落。

模型可以在此基础上生成“正文结构摘要”和“可验证假设”，但不能替代原文，也不能把推断结果写回作者事实字段。

#### 前置工作 F：生成第一版反馈快照

只有完成文章匹配后，才把正文特征与阅读、分享和关注数据合并。第一版反馈只输出：

- 表现较好的题材和标题结构；
- 可能值得继续验证的正文结构；
- 下一轮标题方向；
- 下一轮写作提醒；
- 数据不足和待人工确认项。

连续积累至少两个内容周期后，再考虑由 AI 读取反馈并生成标题技能、写作技能和内容日历相关调整草案；反馈本身不直接注入 pipeline。

### 12.8 前置工作与反哺工作的实施顺序

实施顺序遵循以下依赖关系：

```text
发布元数据入口
      ↓
本地文章产物索引
      ↓
公众号数据与文章匹配
      ↓
正文细节与证据关联
      ↓
正文特征抽取与反馈快照
      ↓
标题 / 写作提示软反哺
      ↓
选题 / 内容日历推荐
      ↓
栏目与账号策略校准
```

#### 第 1 阶段：建立人工可控的发布关联

先让作者可以在页面上补充发布信息：

- 内容日历计划详情增加“发布信息”区；
- 文章编辑器增加“登记发布信息”入口；
- 保存 `contentUrl`、`publishedAt`、`titleAtPublish`、栏目、内容支柱、内容角色和分发渠道；
- 明确“待登记、已发布、等待数据、已复盘”等状态；
- 支持已有文章补录，不要求重新创建计划。

**阶段产出**：每篇新文章都能稳定记录“计划—实际发布—最终标题—栏目—文章产物”的关系。

#### 第 2 阶段：建立本地文章产物索引

在不修改原文章的前提下，扫描已有草稿、终稿、HTML 和证据目录，生成文章产物索引：

- 标题和规范化标题；
- 文件路径、产物类型和版本时间；
- 发布 URL（如果已有）；
- 计划、栏目、素材和证据关联；
- 索引更新时间和扫描结果。

**阶段产出**：即使没有 URL，也能通过本地标题、日期和计划信息找到候选文章。

#### 第 3 阶段：完成数据匹配和人工确认

将公众号导入数据与本地索引关联，顺序为 URL 精确匹配、标题精确匹配、规范化标题匹配、标题相似度加日期匹配。所有非精确匹配进入确认队列，并保存匹配日志。

**阶段产出**：每条数据都带有 `metrics_only`、`title_linked` 等关联等级，错误匹配可追溯和撤销。

#### 第 4 阶段：补充正文和证据细节

对已经确认的文章关联正文：

- 优先使用本地终稿；
- 本地找不到时，再由作者手动触发公开 URL 获取；
- 保存正文快照和获取失败原因；
- 关联截图、日志、代码差异、数据图和失败结果；
- 区分草稿内容、最终发布内容和外部抓取内容。

**阶段产出**：文章从“有数据”升级为“有数据 + 有标题 + 有正文 + 有证据”。

#### 第 5 阶段：生成正文特征和反馈快照

先使用确定性规则抽取字数、段落、小标题、开头问题、列表、代码、图片、证据、结果、失败、边界和标题兑现情况，再由模型生成结构摘要和可验证假设。

**阶段产出**：生成带来源、样本范围和可信度的 `ContentFeedbackSnapshot`，但暂时只展示，不改变创作流程。

#### 第 6 阶段：接入标题和写作软反哺

先接入风险最低、效果最直接的两个位置：

- 标题技能读取历史题材、标题结构和分发目标表现；
- 主动写作及技术写作技能读取正文结构、证据和结果方面的提醒。

反馈只作为提示和候选排序依据，不直接替换技能规则，不自动生成最终标题，不自动覆盖账号配置。

**阶段产出**：新文章生成时可以看到“历史上可参考的标题方向”和“正文写作提醒”。

#### 第 7 阶段：接入选题推荐与内容日历

在标题和写作软反哺稳定后，再把反馈用于：

- 素材候选排序；
- 推荐题材和标题结构；
- 目标区分为拉新、分享、涨粉或实验；
- 内容日历的下一篇安排；
- 由当前文章生成下一篇预告方向。

**阶段产出**：复盘结果开始影响“下一篇写什么、用什么角度写、安排在什么时候”。

#### 第 8 阶段：生成账号策略调整建议

至少积累两个完整内容周期后，再根据题材、标题、正文和栏目数据生成：

- `contentRatio` 调整建议；
- 栏目优先级建议；
- 推荐 / 通知 / 实验内容比例建议；
- 账号包装和关注理由建议。

该阶段仍由作者确认后写入 `account-context.json`，不允许单次爆文自动改写长期策略。

#### 分阶段验收原则

- 第 1 阶段验收“能录入”；
- 第 2 阶段验收“能找到”；
- 第 3 阶段验收“能正确关联”；
- 第 4 阶段验收“能补正文和证据”；
- 第 5 阶段验收“能解释”；
- 第 6–7 阶段验收“能辅助下一篇创作”；
- 第 8 阶段验收“能提出长期调整建议”。

任何阶段匹配可信度不足，都应降级为数据展示或人工确认，不能继续向下游自动反哺。

## 13. 分阶段建议

### Phase 0：确认输入

- 统一账号上下文；
- 确认当前 5 种公众号后台导出文件的字段和解析样本；
- 收集 5–10 条真实会话、阅读或生活素材作为样本。

### Phase 1：素材闭环

- 独立素材入箱页面；
- Markdown / 纯文本粘贴；
- 素材卡；
- 迭代卡；
- 证据关联；
- 多主动写作栏目；
- 基于账号定位的 M 分自动评分和可解释推荐；
- 从素材卡进入心得经验写作。

### Phase 2：计划与复盘

- 主动写作计划态；
- 扩展现有内容日历；
- 支持 5 种公众号导出文件逐个导入、合并、匹配，并在工作台内查看周报；
- 按栏目比较表现。

### Phase 3：辅助决策

- 根据历史表现提示适合扩展的素材；
- 识别可形成系列的后续问题；
- 根据复盘结果辅助校准标题方向、写作提示、栏目比例、评分提示和推荐规则；
- 生成可供标题技能、主动写作技能和技术写作技能读取的历史反馈摘要；
- 让内容日历显示本次计划可参考的历史题材、标题结构和验证目标；
- 为小红书、知乎、GitHub 生成复用草稿；
- 保持发布动作由作者人工完成。

### Phase 4：正文增强与精细反哺

- 统一发布元数据和本地文章产物索引；
- 通过 URL 或标题匹配把公众号表现关联到正文；
- 建立匹配确认队列、匹配日志和来源可信度；
- 抽取正文结构、证据、结果和标题兑现特征；
- 生成带置信度的 `ContentFeedbackSnapshot`；
- 经作者确认后，再将反馈注入标题、写作、选题和内容日历流程。

## 14. 第一版实施状态（2026-08-31）

已落地：

- 独立“素材入箱”页面，支持会话、阅读、生活、项目和其他文本来源的 Markdown / 纯文本粘贴；
- 栏目独立实体与默认栏目，支持在页面新增栏目，不进入 `account-context.json`；
- 素材保存后自动生成四项高中低判断、文字理由、深挖方向和标题方向建议；
- 素材发展为内容计划后进入现有内容日历，计划态与文章/图文产物分开显示；
- 公众号复盘页面支持五类导出逐文件导入，兼容 HTML 伪 `.xls`、BIFF `.xls`、CSV/TSV，并按日期/文章唯一键合并；
- 工作台内查看阅读、分享、阅读后关注、用户增长、常读用户和渠道聚合。
- 内容日历计划和文章编辑器已提供统一“发布信息”入口，可登记发布 URL、实际发布日期、发布时标题、栏目、内容支柱、内容角色和分发渠道；重复保存会更新同一条关联记录。
- 发布中心已提供本地文章索引，只展示可用于发布关联的文章终稿、批次早报终稿和图文发布文案；产物中心继续保留所有中间产物、草稿、排版 HTML 和原始文件的浏览预览。索引可提取标题、文章日期、版本、URL 及证据线索，并关联已有文章文档、内容计划、栏目和素材；重复扫描幂等，已移除文件的索引会在刷新时清理。
- 公众号匹配已收紧：普通文章只使用 `09-FINAL.md`，批次早报使用 `daily/03-FINAL.md`，两者都作为文章链路的终稿候选；`social-cards/**/copy.txt` 作为独立的“图文发布文案”候选，读取发布文案首行标题并结合日期做近似匹配。图文文案只用于确认图文发布对应关系，不会被误当作文章正文参与正文结构反馈。

暂未在本轮自动化：直接读取会话历史、自动从会话和证据目录生成素材、真实模型调用式标题生成和按栏目历史表现校准。当前已提供人工发布信息登记、本地文章产物索引、基于 URL/标题的公众号数据匹配、本地正文和证据资产关联，以及确定性正文特征和反馈快照；非精确匹配仍需人工确认，公开 URL 获取也必须手动触发；标题模块只输出可供标题技能继续加工的方向，不生成最终标题。账号与技能的自动调整现已提供独立的 AI 草案入口，但仍必须经过 diff 检查和作者确认。

公众号复盘反哺已经完成“数据导入 → 本地文章候选匹配 → 人工确认 → 正文与证据关联 → 确定性特征抽取 → 反馈快照展示 → 标题/写作阶段参考”的阶段性闭环。已确认文章可以优先关联本地终稿，并在复盘页查看正文来源、字数、证据资产和结构信号；本地缺失时可手动尝试公开 URL，失败原因会保留。反馈快照现在可作为标题生成、主动写作和技术写作阶段的一次性参考上下文，但仍不自动注入选题、账号配置或最终标题。

阶段 7 已完成第一版“软反哺下一篇”：素材箱支持按复盘优先级排序，并展示建议目标（拉新、分享、涨粉或实验）、历史题材、标题结构、验证问题和下一篇预告；素材进入内容日历时可同步选择主动写作栏目、标题方向和预告，日历计划项也展示目标提示。该推荐使用确定性规则和历史相关性，不自动替作者锁定选题，不把相关性当作因果，也不改写账号长期配置。

阶段 8 已完成只读策略草案：只有两个不同指标周期且每个周期至少关联 3 篇正文时，复盘页才生成 `contentRatio`、栏目优先级、推荐/通知/实验比例以及关注理由草案。建议明确标注证据周期、样本量和不确定性，不提供自动写回 `account-context.json` 的动作；作者确认后仍需人工修改和保存。

阶段 9 已完成第一版“AI 调整草案”：内容反哺页把账号策略与选题评分、标题生成技能作为固定检查目标；现采用 thinking 开启的两阶段模型调用：第一阶段读取反馈快照、账号上下文和全部候选写作技能摘要，根据题材、文章类型、正文结构和已映射样本自动判定调整目标与正文写作技能；第二阶段只读取被选中目标的完整配置 / 技能文件，把调整意图转换为针对原有章节的 `old_text -> new_text` 精确编辑。正文技能优先使用至少 3 个已映射样本；没有映射但有至少 3 篇正文和正文结构信号时，允许以低置信度进行 AI 推断并明确标记；文章实际 drafting 技能（包括综合热点）和早报子目录产物的技能清单都纳入映射。账号 patch 只在策略达到两个内容周期后生成，且只能修改现有配置键，不修改长期 `followReason`，不新增备注型字段。技能调整草案将复盘依据、修改理由和文件编辑分离：复盘依据只在草案界面解释，技能文件只接受对原有章节的可执行规则修改；不得新增“复盘反馈”章节，不得把样本量、阅读率、非因果结论和“根据反馈”的分析措辞写入技能文件。生成接口以 NDJSON 流式展示“刷新快照 → 第一阶段判断 → 第二阶段生成 diff → 校验保存”的里程碑进度，最后才返回待确认草案。系统先把完整的新旧文件内容及精确编辑记录保存为待确认草案，确认时校验源文件 hash 和草案版本，再原子写入 `account-context.json` 和 `writing-skills/<skillId>/SKILL.md` 覆盖文件；旧版本草案会失效，拒绝、源文件冲突、定位不唯一或模型输出无效都不会改变运行中的配置。运行时优先读取已确认的技能覆盖文件，pipeline 不读取待确认草案，也不接收反馈原文注入。
