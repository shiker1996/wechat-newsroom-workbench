# 微信公众号工具贴图规范

## 目标

把工具热点转成可保存、可搜索、能建立账号专业度的公众号贴图。当前没有采用微信官方贴图写作标准，内容表达先模仿现有小红书工具种草规范：短标题、痛点钩子、emoji、短句分块和末尾标签；公众号事实门禁、权限提示和自然承接优先于流量公式。

## 内容契约

每组卡片至少回答四件事：

1. 工具解决什么具体问题
2. 哪些能力有来源支持
3. 用户如何开始，或去哪里查看官方步骤
4. 哪些人适合、哪些限制需要先知道

推荐页面结构：

| 页面 | 任务 | 必须避免 |
|---|---|---|
| 封面 | 痛点 + 工具动作 + 真实结果 | 空泛“神器”“封神” |
| 是什么 | 一句话定位和核心对象 | 项目介绍堆砌 |
| 能做什么 | 3–4项有证据的能力 | 把愿景写成现成功能 |
| 快速上手 | 官方步骤、命令或入口 | 编造安装命令 |
| 适用场景 | 2–4个具体任务 | “所有人都适合” |
| 限制与权限 | 成熟度、系统、权限、数据边界 | 只讲优点 |
| 结尾 | 目标总结 + 持续价值 | 连续索要关注点赞 |

素材不足时删页，不凑满七页。快速上手没有可靠步骤时，改为“使用前检查”。

## 标题

先按 `TITLE_GUIDE.md` 生成 3–5 个不超过 20 字的标题备选。优先采用：

- `[具体痛点]？这个工具把[对象]变成[可验证结果]`
- `[工具名]：用[动作]解决[具体问题]`
- `[真实数字/事实] + [工具动作] + [适用对象]`

尽量包含具体场景、已核验数字、情绪钩子和具象结果；允许使用 emoji、发现感和种草语气。数字、免费、开源、性能和节省时间都必须有来源。没有真实体验时不用“我用了”“亲测”，没有可靠数字时不为满足标题公式编造数字。

## 文案语气

- 对程序员说人话，但保留必要术语
- 参照 `COPY_GUIDE.md` 使用短句、emoji 和口语化板块；“封神、闭眼冲、天花板”等词只有在不构成事实承诺、且正文能解释具体价值时使用
- 区分项目自述、媒体评价和作者判断
- CTA 只承诺具体持续价值，例如“后续继续实测这类开发工具的权限、成本和使用边界”
- 文案末尾使用 6–8 个标签，组合精准垂直词、技术词和工具种草词

## 增长字段

- `content_role=搜索`：标题、封面和前两页保留稳定关键词
- `content_role=沉淀`：至少提供一页步骤、清单、对比或限制条件
- `content_role=拉新`：可以强化痛点和反差，但不牺牲事实准确性
- `practical_increment`：必须真正出现在卡片中
- `conversion_bridge`：只进入编辑规划；没有真实历史内容时不写具体旧文标题或链接
- `follow_reason`：在结尾转成一句克制的持续价值说明

## 事实门禁

- GitHub Star 等实时数字记录抓取时间
- 开源协议以仓库 LICENSE 为准
- 安装命令以官方 README 或发布页为准
- 项目处于 alpha/beta/实验阶段时必须显式说明
- 仓库代码和第三方 Skill 安装前提醒检查权限、脚本和网络访问
