# 事件图文故事板

只负责 `social-event` 入口中普通 `event` 内容的故事板规划。故事板必须先组织“发生了什么—关键变化—争议与讨论—后续观察”的叙事结构，再决定页面数量和版式；不得把同一事实拆成多个名称不同但内容相同的内容块。

## 输入

输入契约为 `social_card_fact_base`，内容类型必须是 `event` 且未被升级为 `open_source_technology` 或 `open_source_trend`。只使用确认事实、带来源的主张、回应、时间线、来源审计和明确未知项。

## 输出

输出契约为 `social_card_storyboard`。每个页面必须同时返回明确的 `kind` 和 `role`，每个内容块必须带 `source_refs`。传播张力不得高于证据强度：

- 确认事实可以陈述，但关键事实应保留来源编号。
- 未核实主张必须保留说话者和不确定性表达。
- 多方回应或存在事实支持的分歧、影响与开放问题时，组织为“争议与讨论”页；讨论必须服务于事实，不把猜测包装成结论。
- 事件时间线只在存在至少两个有意义的时间节点时单独成页；单一时间点放入“发生了什么”或“当前状态”。
- 每个核心事实只分配一个主叙事页面；来源核验应作为主事实页或讨论页内的内容块，不要把核心事实原样再抄一遍。
- “关键节点”“阶段变化”“事件进展”等标题不能并列承载同一组时间节点；需要补充时必须引入新的事实或新的叙事职责。
- 来源核验、事实边界和开放问题默认并入主事实页、争议讨论页或结尾页，不单独生成免责声明式的“信息来源与核验”或“事实边界和开放问题”页面；只有来源冲突本身就是事件主线时才允许单独保留核验页。
- 至少一页说明事实边界、来源缺口、争议或开放问题，但要转化为读者可讨论的具体问题，而不是泛化免责声明。
- 不得推断动机、违法性、责任或因果关系，不得诱导网暴。

只输出严格 JSON，不输出发布文案、HTML、CSS 或截图指令。具体规则见 `references/storyboard.md`。
