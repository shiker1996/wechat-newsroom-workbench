## 当前运行阶段：技术事实基座到开源技术图文故事板

只依据分类为 `open_source_technology` 的稳定事件事实基座规划故事板。事实基座可能包含发布事实、机制或架构证据、性能证据、来源审计和明确未知项。

技术图文的叙事目标不是复述仓库 README，而是让读者按以下顺序理解一个有事件依据的技术变化：

```text
遇到了什么技术问题
  ↓
机制或架构发生了什么变化
  ↓
哪些证据支持这个判断
  ↓
适用边界和下一步验证是什么
```

只输出严格 JSON，不输出 Markdown、发布文案、HTML、CSS 或截图指令。顶层必须直接返回 `card_plan` 数组，不要返回 `storyboard.pages` 或 `blocks` 这套内部规划结构：

```json
{
  "target_reader": "",
  "pain_point": "",
  "tool_positioning": "开源技术事件的技术定位",
  "must_highlight": "必须突出的一条技术变化",
  "must_disclose": "证据范围、未知项和适用边界",
  "getting_started": "读者理解该技术的最短路径",
  "forbidden_claims": "不得越过证据边界的判断",
  "recommended_pages": 4,
  "card_plan": [
    {
      "kind": "cover|problem|mechanism|evidence|boundary|ending",
      "role": "cover|concept|feature|data|evidence|risk|ending",
      "title": "8–14 字的页面标题",
      "goal": "本页唯一要完成的事实或判断",
      "evidence": ["事实基座中直接支持本页的证据"],
      "content_blocks": [
        {
          "type": "text|list|note|code",
          "title": "可选小标题",
          "content": "仅 text/note/code 使用；内容具体、可核验",
          "items": [],
          "source_refs": ["事实基座中的来源标识"]
        }
      ]
    }
  ]
}
```

## 一、页面结构

### 1. 封面：提出技术变化

- `kind: cover`、`role: cover`。
- 只呈现已被来源支持的技术变化或事件事实。
- 不在封面堆叠机制、性能证据、价格和适用边界。
- 最多 1 个核心内容块，通常只补充版本、来源或时间边界。

### 2. 问题：说明技术痛点

- `kind: problem`、`role: concept`。
- 说明原有方案遇到的具体问题、约束或开发者需求。
- 问题必须来自事实基座，不得把“开源”本身写成技术价值。
- 没有明确问题证据时，可以并入机制页，不单独制造空泛痛点页。

### 3. 机制/架构：解释变化如何发生

- `kind: mechanism`、`role: feature`。
- 说明组件、模型、协议、架构或工作路径的变化。
- 机制、架构和性能数字必须绑定来源；不能用项目宣传语替代原理证据。
- 适合使用 1 个机制摘要块加 1–2 个结构化要点块。

### 4. 证据：列出可核验支持

- `kind: evidence`、`role: data` 或 `role: evidence`。
- 使用官方文档、发布记录、基准结果、实现说明或其他已核验资料。
- 没有可复核基准时，不生成“提升 X 倍”或性能对比结论，改写为已知能力和待验证项。
- 规格、价格或版本列表与机制页相邻时优先合并，不为每个列表单独生成页面。

### 5. 边界：说明适用条件和风险

- `kind: boundary`、`role: risk`。
- 说明版本成熟度、环境依赖、性能证据缺口、适用范围和仍待验证的问题。
- 边界不是免责声明，应写成具体的“在什么条件下成立”“还缺什么证据”。
- 不因为标题含“性能”“模型”或“能力”就改变已给出的 `risk` 角色。

### 6. 结尾：给出后续观察

- `kind: ending`、`role: ending`。
- 总结当前可确认的技术结论，并列出后续版本、测试、文档或生态信号。
- 不新增事实，不把收藏、转发或关注口号当作技术结论。
- 最多 2 个内容块。

## 二、页面选择规则

技术图文优先控制在 4–6 页，不机械生成所有职责页：

| 页面 | 是否默认生成 | 触发条件 |
|---|---:|---|
| 封面 | 是 | 所有合格技术事件 |
| 问题 | 条件生成 | 有明确技术痛点或约束证据 |
| 机制/架构 | 是 | 有机制、架构或工作路径证据 |
| 证据 | 条件生成 | 有独立来源、发布记录或可核验数据 |
| 边界 | 是 | 有明确限制、缺口或待验证项 |
| 结尾 | 是 | 所有技术事件 |

优先采用以下紧凑结构之一：

```text
封面 → 机制/证据 → 边界 → 结尾
封面 → 问题/机制 → 证据/边界 → 结尾
封面 → 问题/机制 → 证据 → 边界 → 结尾
```

相邻职责可以同页，但必须使用不同内容块表达不同职责。只有合并后会超出模板容量、破坏事实边界或造成结构不可读时，才保留独立页面。

## 三、事实分配与防重复

生成前建立内部事实分配表：

```text
fact_id / 事实摘要 / 主页面 / 来源引用 / 是否已作为机制或证据使用
```

分配规则：

```text
技术问题 → 问题或机制页
机制/架构变化 → 机制页
规格、版本、基准和来源 → 证据页或机制/证据合并页
限制、依赖和证据缺口 → 边界页
后续验证动作 → 结尾页
```

同一事实只能有一个页面承担完整叙述。其他页面可以复用来源编号，但不要复制完整事实句。

## 四、内容块与来源规则

- `text`：单一技术结论或事实摘要。
- `list`：多个规格、机制步骤、证据或边界；必须使用 `items` 字符串数组。
- `note`：短事实边界、证据缺口或待验证项。
- `code`：事实基座明确提供的命令或代码片段；不得自行补写可执行命令。
- 每个内容块必须提供 `source_refs`；来源只能来自事实基座。
- `list` 必须使用 `items` 字符串数组，禁止在列表块写 `content` 数组或把多条事实拼成单个段落。
- 公众号渠道不使用 `stats`、`compare` 等未开放结构化块；需要对比时改用带来源的 `list` 或 `text`。

## 五、技术边界与密度

- 不把单一仓库介绍、Star 数或 Trending 排名升级为技术深解结论。
- 不虚构性能测试、成本收益、用户规模、生产效果或作者亲测体验。
- 不把“支持某能力”改写成“效果更好”“效率提升”或“行业领先”。
- 普通内容页通常使用 1–3 个有实质内容的块；封面最多 1 个，结尾最多 2 个。
- 列表条目合计不超过 9 条；相邻规格/价格列表在容量允许时合并为一个列表块，保留全部条目和来源。
- 如果事实不足以支撑目标密度，保留必要留白，不用重复内容填满画布。
- 模板容量、页面绝对上限和后续重排由程序门禁负责，故事板不得静默删除事实。

## 六、合并与禁止合并规则

允许合并：

- 问题 + 机制：问题块和机制块必须分别保留；
- 机制 + 证据：机制说明与直接支持它的证据可以同页；
- 证据 + 边界：证据缺口和适用条件可以作为边界块并入；
- 边界 + 结尾：边界事项与后续验证必须分块表达。

禁止合并：

- 封面 + 普通内容页；
- 不同机制或不同架构路径；
- 已确认技术事实 + 未核实性能主张；
- 机制说明 + 没有来源支持的效果推断。

合并后必须保留全部 `source_refs`、`fact_ids` 和性能证据边界，并重新检查结构化字段与页面容量。

## 七、证据门槛、降级与常见错误

- 没有机制、架构或工作路径证据时，降级为普通事件或工具图文，不继续生成技术深解结构。
- 性能、成本和效果只有在存在对应可核验来源时才能作为结论；否则只能写已知能力和待验证项。
- 单个仓库、单次发布、Star 或 Trending 不能单独支撑技术结论。
- 不把功能列表拆成多个“机制”页面，不把证据列表重复到能力页和证据页。
- 技术事实不足时缩短为 4 页或进入候补，不能用空泛的行业价值和未来影响填充。
