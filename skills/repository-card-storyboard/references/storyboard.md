## 当前运行阶段：README 到工具图文故事板

只依据已核验仓库事实和 README 生成图文决策，不得虚构体验、效果、性能、价格、权限或数字。故事板必须让读者明确回答：它是什么、解决什么具体问题、核心功能如何工作、怎样开始、适合谁、有什么限制。禁止用 GitHub topics 代替功能解释。

先从具体读者任务出发：`target_reader` 写明角色与使用场景，`pain_point` 写明正在完成的任务及当前阻碍或成本，`tool_positioning` 说明工具在该任务中的作用。Star、Trending 和项目知名度只作为证据，不作为读者价值本身。封面主标题优先使用“具体任务或问题 + 结果方向”，陌生项目名作为辅助信息。

返回严格 JSON：

```json
{
  "target_reader": "",
  "pain_point": "",
  "tool_positioning": "",
  "must_highlight": "",
  "must_disclose": "",
  "getting_started": "",
  "forbidden_claims": "",
  "recommended_pages": 4到7,
  "card_plan": [
    {
      "kind": "cover|problem|capability|quickstart|scenario|limitation|ending",
      "title": "具体、有信息量的页标题",

      ]
    }
  ]

```

补充要求：

- 每页内容块遵守固定画布密度预算：封面最多 1 个、内容页 2–3 个、结尾页最多 2 个；同一页最多 2 个列表块，单页列表条目合计不超过 9 条。超出预算的部分会在生成阶段被确定性裁剪。能力页必须写出 README 中的具体能力和工作方式，快速上手页保留真实命令，限制页明确未核验项。
- must_disclose 必须说明“基于项目文档整理，未实际运行”以及未知权限、网络和成熟度。
- 运行时继续允许 4～7 页；内容适合时优先用 5～6 页组织为封面、痛点、能力、可选能力或场景、快速开始、结尾，不为凑页重复内容。
- README、仓库元数据、LICENSE 和 Release 只能表述为“项目文档显示”或“项目提供”；只有输入中存在明确运行记录时，才能写“实测”“跑通”和具体耗时。无法核验的权限、网络、成熟度、兼容性或性能直接标记未知。
- 保留 README 中真实存在的命令和用户参数。`<commit>`、`YOUR_TOKEN`、`$API_KEY` 等参数须说明替换位置和用途，优先改写为 `$COMMIT_SHA` 等语义清晰的变量名；含用户参数时不得宣称“复制即用”或“无需配置”。README 未提供完整命令时写操作说明，不补造命令。
- 结尾优先说明适合哪些角色和场景、不适合哪些约束，以及使用前需要确认的权限、网络、版本、成本或安全事项；不用“点赞、收藏、转发”代替内容结论。
