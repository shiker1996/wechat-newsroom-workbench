## 当前运行阶段：已核验仓库事实到工具图文故事板

只依据 `repository` 事实基座规划故事板。事实基座可能包含仓库元数据、README、代码/配置说明、版本记录、许可信息、实际运行记录和明确未知项。

工具图文的叙事目标不是罗列 README，而是让读者按以下顺序判断这个项目是否值得尝试：

```text
读者要完成什么任务
  ↓
项目提供什么能力，怎样工作
  ↓
怎样开始，哪些步骤和参数是真实存在的
  ↓
适合谁，哪些权限、环境和成熟度边界需要先确认
```

只输出严格 JSON，不输出 Markdown、发布文案、HTML、CSS 或截图指令。每个页面必须同时返回明确的 `kind` 和 `role`，每个内容块必须带 `source_refs`。内容必须放在 `content_blocks` 中，不得使用旧字段 `blocks`。

输出结构必须遵循以下完整 JSON 形状；没有内容时使用空数组或空字符串，不要省略字段，也不要新增未定义的顶层字段：

```json
{
  "target_reader": "",
  "pain_point": "",
  "tool_positioning": "开源工具/项目内容定位",
  "must_highlight": "必须突出的一条已核验能力或使用价值",
  "must_disclose": "版本、权限、环境、证据来源和事实边界",
  "getting_started": "读者开始使用项目的最短真实路径",
  "forbidden_claims": "不得越过仓库事实基座证据边界的判断",
  "recommended_pages": 5,
  "card_plan": [
    {
      "kind": "cover|problem|capability|quickstart|scenario|limitation|ending",
      "role": "cover|concept|feature|steps|risk|ending",
      "title": "8–14 字的页面标题",
      "goal": "本页唯一要完成的事实或判断",
      "evidence": ["事实基座中支持本页的证据摘要"],
      "content_blocks": [
        {
          "type": "{{REPOSITORY_BLOCK_TYPES}}",
          "title": "可选小标题",
          "content": "单一结论、事实摘要、边界说明或代码/命令片段",
          "items": [],
          "headers": [],
          "rows": [],
          "source_refs": ["事实基座中的来源标识"]
        }
      ]
    }
  ]
}
```

字段规则：块类型为 `list` 时使用字符串数组 `items`；`stats` 使用统计项数组 `items`；`steps`、`timeline`、`scenes` 使用对象数组 `items`，其中步骤项统一使用 `{ "title": "步骤名称", "content": "命令、参数、验证条件或说明" }`；`compare` 使用 `headers` 和 `rows`；`text`、`note`、`highlight`、`code` 使用 `content`。具体可用类型由运行时注入的 `REPOSITORY_BLOCK_TYPES` 决定。未使用的字段保留为空数组或空字符串。不要把结构化条目塞进块级 `content`，不要在页面中返回 `blocks`。

### 视觉意图示例

视觉字段只表达“应该突出什么”，不写 CSS。优先标记已有事实中的关键数字、关键能力或使用边界；不要让每个块都高亮。结构化条目也可以单独标记：

```json
{
  "type": "stats",
  "title": "关键变化",
  "items": [
    {"num": "3 个", "label": "核心模块", "visual": {"emphasis": "strong", "tone": "accent", "icon": "metric"}},
    {"num": "需配置", "label": "访问凭证", "visual": {"tone": "warning", "icon": "warning"}}
  ],
  "visual": {"badge": "事实摘要"},
  "source_refs": ["事实基座中的项目说明来源"]
}
```

普通文本需要突出句内数字时，保留完整 `content`，并按原文顺序提供 `content_runs`：

```json
{
  "type": "highlight",
  "content": "首次运行需要配置访问凭证。",
  "content_runs": [
    {"text": "首次运行需要配置 ", "role": "normal"},
    {"text": "访问凭证", "role": "warning", "tone": "warning", "emphasis": "strong"},
    {"text": "。", "role": "normal"}
  ],
  "visual": {"icon": "warning", "badge": "使用前确认"},
  "source_refs": ["事实基座中的配置说明来源"]
}
```

## 一、页面结构

### 1. 封面：提出具体任务或问题

- `kind: cover`、`role: cover`。
- 标题优先表达具体任务或问题，项目名作为辅助信息；不得只用仓库名、Star 或 Trending 排名当标题主张。
- 只呈现事实支持的工具定位，不在封面堆叠能力、命令、场景和限制。
- 最多 1 个核心内容块，通常只补充项目类型、来源或时间边界。

### 2. 痛点/能力：解释项目解决什么

- `kind: problem`、`role: concept`：说明任务、阻碍、重复成本或约束，必须来自事实基座。
- `kind: capability`、`role: feature`：说明核心能力、工作方式和输入输出，不把项目宣传语改写成效果结论。
- 两者可以合并，但必须使用不同内容块分别表达问题和能力。

### 3. 快速上手：保留真实路径

- `kind: quickstart`、`role: steps`。

- 只有事实基座提供真实命令或完整操作路径时才生成；没有完整命令时写操作说明，不补造安装、初始化或验证命令。

- 保留用户参数、环境依赖和权限要求。`<commit>`、`YOUR_TOKEN`、`$API_KEY` 等占位符必须说明替换位置和用途。

- 不得宣称“复制即用”“无需配置”或“已跑通”，除非输入中有明确运行记录。

- 输出示例为：

  ```json
  {
     "type": "steps",
     "items": [
        {
          "title": "安装项目",
          "content": "npm install ..."
        }
      ],
     "source_refs": ["事实基座中的 README 来源标识"]
  }
  ```

能力或限制清单使用 `list` 块时，输出结构参考：

```json
{
  "type": "list",
  "title": "核心能力",
  "items": ["能力一：具体说明", "能力二：具体说明"],
  "source_refs": ["事实基座中的能力来源"]
}
```

### 4. 场景：说明何时使用

- `kind: scenario`、`role: feature`。
- 只有至少两个具体场景，且每个场景都能说明触发条件、用法和边界时才独立成页。
- 只有泛化的人群标签时，合并到结尾或限制页；不得用“开发者、产品经理、企业用户”等标签凑页。

### 5. 限制：说明使用边界

- `kind: limitation`、`role: risk`。
- 说明版本、权限、网络、兼容性、数据安全、维护状态和未核验项。
- 限制必须写成具体条件或待确认事项，不写空泛免责声明。

### 6. 结尾：给出选择结论

- `kind: ending`、`role: ending`。
- 总结适合的任务和不适合的约束，列出使用前需要确认的事项。
- 不新增事实，不使用“点赞、收藏、转发”等传播口号替代内容结论。
- 最多 2 个内容块。

## 二、页面选择规则

工具图文推荐 4–7 页，按仓库原型选择故事线，不机械套用“痛点—能力—安装—场景—总结”：

| 仓库原型 | 优先故事线 | 页面条件 |
|---|---|---|
| `awesome/list/catalog` | 覆盖什么 → 如何选 → 代表性条目 → 收录/更新边界 | 只有仓库本身可运行时才有快速上手页 |
| `library/sdk/framework` | 开发任务 → 核心抽象/API → 最小代码路径 → 取舍 → 兼容性 | 有真实 API/代码路径才生成 quickstart |
| `cli/app/extension/service` | 使用场景 → 能力/机制 → 上手路径 → 设置/工作流 → 权限限制 | 场景和权限有事实支持时分别保留 |
| `template/boilerplate` | 产出物 → 目录约定 → 首次运行 → 可定制点 → 边界 | 没有首次运行事实时合并为操作说明 |
| `dataset/benchmark` | 数据覆盖 → 字段/来源 → 获取使用 → 可做分析 → 许可偏差 | 不把数据规模直接写成质量或效果结论 |

推荐组合：

```text
封面 → 痛点/能力 → 快速上手 → 限制 → 结尾
封面 → 能力 → 场景 → 快速上手/限制 → 结尾
封面 → 覆盖范围 → 代表性条目 → 选用边界 → 结尾
```

相邻职责可以在模板容量允许时合并：痛点与能力、能力与快速上手、限制与结尾。不得合并封面与内容页、快速上手与结尾、不同具体场景。

## 三、事实分配与防重复

生成前建立内部事实分配表：

```text
fact_id / 事实摘要 / 主页面 / 来源引用 / 仓库原型 / 是否已经使用
```

分配规则：

```text
读者任务与项目定位 → 痛点/能力
核心功能与工作方式 → 能力
真实命令、参数和环境 → 快速上手
具体触发条件和用法 → 场景
权限、版本、网络和证据缺口 → 限制
适合/不适合与确认事项 → 结尾
```

同一事实只能有一个页面承担完整叙述。其他页面可以复用来源编号，但不能复制完整事实句、命令或同一组条目。列表型仓库只能把一个具体条目放在一个主页面，不得在“代表性条目”和“能力清单”中重复罗列。

## 四、证据边界与降级规则

- 至少有已核验的项目定位和能力事实，才进入工具图文故事板。
- 只有 README、仓库名、topics、Star 或 Trending 时，可以说明项目文档显示的定位，但不能生成实测效果、性能或成熟度结论。
- 没有机制/架构证据时，不升级为开源技术图文；没有跨主体/跨来源/跨时间信号时，不升级为开源趋势图文。
- 没有真实命令时，快速上手页降级为“操作路径/准备条件”，不能补造命令。
- 事实不足以支撑独立场景页时，删除场景页并把适用人群并入限制或结尾。
- 仓库事实过少时缩短为 4 页或进入候补，不用泛化文案填满页面。

## 五、内容块、来源与密度规则

- `text`：单一定位、事实结论或边界说明。
- `list`：多个能力、场景、参数或限制，必须使用 `items` 字符串数组。
- `steps`：真实操作步骤，使用对象数组并保留命令、参数和验证条件。
- `code`：事实基座明确提供的代码或命令片段，不自行补写可执行内容。
- `note`：短事实边界、未知项或使用前确认事项。
- 每个内容块必须提供 `source_refs`，来源只能来自事实基座或已核验素材。
- 普通内容页通常使用 1–3 个有实质内容的块；封面最多 1 个，结尾最多 2 个。
- 单页最多 2 个列表块，列表条目合计不超过 9 条；结构化条目不得塞进块级 `content`。
- 内容不足时保留必要留白，不重复事实、命令或来源来填充画布。

## 六、合并与禁止合并规则

允许合并：

- 痛点 + 核心能力：问题块和能力块都必须保留；
- 核心能力 + 快速上手：能力说明和真实操作块都必须保留；
- 限制 + 结尾：限制与选择结论必须分块表达；
- 相邻的规格/参数列表：合并后保留全部条目和来源。

禁止合并：

- 封面 + 普通内容页；
- 快速上手 + 结尾；
- 不同具体场景；
- 已核验事实 + 未核实主张；
- 真实命令 + 泛化建议。

合并后必须保留全部 `source_refs` 和 `fact_ids`，并重新检查页面密度和结构化字段。

## 七、常见错误

- 把“开源”写成价值，把 Star 写成用户认可，把 Trending 写成趋势；
- 把项目列表写成可安装的工具，把列表中的单个项目冒充当前仓库能力；
- 把 README 的示例命令改写成“已实测”；
- 把功能支持改写成效果提升、效率提升或行业领先；
- 用“适合开发者”“适合团队”这类空泛标签生成场景页；
- 用多个标题不同但事实相同的页面填充推荐页数。
